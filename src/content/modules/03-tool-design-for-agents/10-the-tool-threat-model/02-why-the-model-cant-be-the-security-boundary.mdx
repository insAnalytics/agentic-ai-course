<Subsection title="SQL injection has a fix. Prompt injection doesn't, yet." variant="a">

Prompt injection was
[named after SQL injection](/03-tool-design-for-agents/10-the-tool-threat-model/01-prompt-injection-through-tool-results/#two-sources-of-instructions),
and the comparison is worth following to its end, because it shows
exactly why this problem is hard.

SQL injection happens when a program builds a database command by gluing
user-typed text into it, so text crafted to look like SQL gets run as SQL.
It has a real, complete fix: **parameterized queries**. The command and
the data travel separately, and the database never treats the data as
part of the command:

<LiveDemo client:load code={SQL_DEMO} />

*`sqlite3` is Python's built-in, file-less database, used here only to
show the idea.*

The typed text was crafted to match every row if it were read as SQL.
Sent through the `?` placeholder, it's only ever a value, the literal
name `x' OR '1'='1`, which no agent has. The separation is structural: no
wording of the typed text can move it from the "data" side to the
"command" side.

A language model has no equivalent. Here's the request from
[the ticket demo](/03-tool-design-for-agents/10-the-tool-threat-model/01-prompt-injection-through-tool-results/#one-injected-instruction-one-real-action),
laid out the way the model actually receives it:

<LiveDemo client:load code={REQUEST_DEMO} />

The system prompt, the user's request and the ticket's text all arrive as
one sequence of tokens.
[Module 1's training pipeline lesson](/01-llm-foundations/07-the-training-pipeline/03-preference-training-and-message-roles/)
explained why the roles don't separate them the way a `?` placeholder
does: the difference between "instructions to follow" and "content to
read" is something the model *learned* in training, as a strong tendency,
not a boundary built into how it processes text. The ticket's words sit
right next to the rule telling the model to ignore them, and whether the
rule wins is a matter of how the model was trained, how the text is
phrased, and chance.

</Subsection>

<Subsection title="Mitigations help, but aren't boundaries" variant="b">

There are real, worthwhile mitigations, and every serious agent should
use them:

- **A clear system prompt,** like the one above, telling the model never
  to act on instructions found in tool results.
- **Labeling untrusted content,** as in
  [the last lesson's `<web_content>` wrapper](/03-tool-design-for-agents/09-web-interaction/04-everything-from-the-web-is-untrusted-input/#one-habit-that-helps-label-what-s-untrusted).
- **Models trained to resist injection.** Model providers now train
  specifically against it, and current models resist far more attempts
  than earlier ones.
- **Detection filters** that scan tool results for text that looks like
  an injection before the model sees it.

Each of these lowers how often an injection succeeds. None of them gets
it to zero, and security is judged by the worst case, not the average. An
attacker who fails can simply try again, rephrased:

<LiveDemo client:load code={ATTEMPTS_DEMO} />

*This assumes each attempt independently has the same 5% chance, a
simplification that makes the point.*

A filter that stops 95% of attempts sounds strong, and against an
attacker who keeps trying, it's a matter of time. This is the reason
Simon Willison describes a guardrail that stops 95% of attacks as a
failing grade: in most of security, "usually" isn't the standard. A
parameterized query stops 100% of SQL injections, not 95%.

</Subsection>

<Subsection title="The shift in thinking" variant="a">

If the model can't reliably be kept from being fooled, then an agent's
safety can't depend on it not being fooled. The question to design around
changes from:

> How do I stop the model from following injected instructions?

to:

> If the model *does* follow an injected instruction, how much harm can it
> do?

That second question has solid, structural answers, because it's about
the agent's tools and permissions, which are ordinary code you control.
The next concept identifies the combination of tools that turns a fooled
model into a data leak, and the least-privilege lesson after this one
builds the structural limits. Keep the mitigations above too: they make
attacks rarer. They're just not the thing to rely on.

</Subsection>
