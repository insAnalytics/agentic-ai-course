<Subsection title="Two sources of instructions" variant="a">

[The last lesson](/03-tool-design-for-agents/09-web-interaction/04-everything-from-the-web-is-untrusted-input/)
ended on a page containing a line written for AI assistants. That's an
example of **prompt injection**: text that arrives in a model's context
from somewhere other than the person it's working for, written to change
what the model does. The term was coined by Simon Willison, who named it
after SQL injection on purpose: the underlying flaw is the same, mixing
trusted instructions and untrusted content in one place.

It helps to separate two kinds:

- **Direct injection** is the user themselves typing something meant to
  override the system prompt. That's a real concern for some
  applications, but the user is typing into their own session, and
  usually can only affect what *they* get back.
- **Indirect injection** is instruction-like text inside something a
  *tool* brought in: a web page, an email, a support ticket, a document, a
  code comment, a calendar invite. Someone other than the user wrote it,
  and the user may never see it.

Indirect injection is the one that matters for agents, because agents read
things constantly, and every tool that brings in outside text is a way for
a stranger's words to reach the model.

</Subsection>

*The model's replies are scripted to follow the injected instruction, so
this demo shows the path the harm takes, not how often a real model falls
for it.*

The user asked for a summary and got one. Their answer says nothing about
any change, because the ticket told the model not to mention it.
Meanwhile `research_agent` has been switched to a different model, by a
stranger, using the agent's own permission to change the registry.

Three things about this are worth noticing:

- **Nothing in the code went wrong.** Every tool did exactly what it was
  written to do. The loop is the correct one from
  [Module 2](/02-the-agent-loop/05-react-and-reasoning-in-the-loop/01-the-react-pattern/).
  There's no bug to fix.
- **The attacker needed no access to anything.** They didn't touch the
  registry, the agent's code or its credentials. They wrote a support
  ticket, which anyone can do.
- **The agent's permissions became the attacker's permissions.** Whatever
  the agent is allowed to do, text in its context can try to get it to do.
  The harm is bounded by the agent's tools, not by the attacker's access.

The demo's change is small and easy to undo. The same pattern, with an
agent that can send email, move money, delete files or push code, is not.
And the same pattern shows up in every tool that brings in outside text:
the fetched page from the last lesson, a document an agent summarizes, an
email in an inbox, the output of
[a code-execution tool](/03-tool-design-for-agents/08-code-execution-as-a-tool/00-intro/)
running code that printed something unexpected.

</Subsection>
