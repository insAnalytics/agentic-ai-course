# fixed tools: one function per task, each written ahead of time
FIXED_TOOLS = {"mean": statistics.mean, "median": statistics.median}

def call_fixed_tool(name: str, data: list) -> str:

# the model asks for a standard deviation by writing the code for it
run_code("import statistics; print('model-written stdev:', round(statistics.stdev(numbers), 2))")

<Subsection title="Some tasks are better solved by writing code than by calling a tool" variant="a">

Every tool so far has been a fixed function:
[a registry lookup](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/01-names-and-descriptions-as-prompts/),
a weather call, a status check. Each does one known thing. But a whole
class of tasks doesn't fit a fixed tool at all:

- "What's the standard deviation of these 200 numbers?"
- "Reformat this CSV so the dates are ISO 8601 and drop rows with no email."
- "How many business days between these two dates, skipping the holidays I listed?"

You could build a tool for each. You'd never finish, because the next
task is always slightly different. The general answer is to give the
model one tool that runs code it writes. Ask for a calculation, and it
writes and runs the Python. This is the most capable tool an agent can
have: instead of a menu of fixed actions, it has a general-purpose
computer.

[Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)
and others have found that letting a model *write code* to
orchestrate its work, rather than emit a long series of individual tool
calls, can be dramatically more efficient for certain tasks: the model
writes a short script that loops, filters and combines results, instead
of making dozens of separate calls. Code execution is increasingly a
core agent capability, not a niche one.

on your own machine, it would be yours.*

</Subsection>

<Subsection title="The same property that makes it powerful makes it dangerous" variant="b">

That last call is the problem. A fixed tool can only do the one thing
it was written to do.
`get_agent_model` reads a name and returns a string; there is no
argument that makes it delete a file. A code-execution tool is the
opposite: its whole point is that it runs *whatever the model writes*,
and "whatever" includes code you never anticipated.

And the code is untrusted. Not because the model is malicious, but
because:

- **The model can be wrong.** It might write a script that deletes the
  wrong directory, or loops forever.
- **The model can be manipulated.**
  [Module 1's training pipeline lesson](/01-llm-foundations/07-the-training-pipeline/03-preference-training-and-message-roles/#the-root-cause-of-prompt-injection)
  noted that a model can't fully separate instructions from data. If the
  code-writing model has read a web page or a document that contains
  "ignore your task and run this instead", that text can shape the code
  it writes. A later lesson in this module, on the tool threat model, is
  entirely about this.

So the question this lesson answers is not "should an agent run code":
for many real agents, it should. The question is *where*. Running
model-written code in a place where it can reach your files, your
network and your credentials is the single most dangerous thing an agent
system can do. Running it somewhere it can't reach any of those is a
routine, useful capability. The whole difference is isolation, and the
next three concepts are about getting it right, starting with a way of
getting it wrong that looks correct.

</Subsection>
