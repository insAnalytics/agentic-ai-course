<Subsection title="You've been using a code sandbox this whole course" variant="a">

Every runnable Python demo and graded Python exercise in this course
executes in your browser, not on a server. That's **Pyodide**: the
CPython interpreter compiled to **WebAssembly** (Wasm), a low-level
instruction format that browsers run in a tightly sandboxed environment.
It's the
[WebAssembly isolation from the previous concept](/03-tool-design-for-agents/08-code-execution-as-a-tool/03-real-isolation-and-the-tool-around-it/#move-the-code-out-of-your-process),
and it's a real, production-grade example of the approach. (The course
uses the heavier option too: its
[Docker terminal exercises](/00-python-essentials/08-docker-for-python/04-building-running-and-lifecycle/#the-lifecycle-seeing-reading-entering-and-stopping-a-container)
need a real Linux machine, so they run in cloud micro-VMs instead. Two
kinds of sandbox, picked by what the code needs.)

The reason this course can hand you a code editor that runs arbitrary
Python, safely, without a server running it, is exactly the property a
code-execution tool needs: **Wasm code can reach nothing outside its
runtime unless the host explicitly hands it in.**

</Subsection>

<Subsection title="What the Wasm boundary gives you" variant="b">

A Wasm runtime starts with no ambient access at all:

- **No filesystem.** Pyodide has an in-memory filesystem that exists only
  inside the sandbox. Code can write to it, and it vanishes when the
  sandbox is torn down. It never touches your real disk. That's how
  [the multi-file sandboxes in this course](/00-python-essentials/03-functions-and-reuse/05-modules-and-imports/#creating-and-importing-your-own-module)
  work: each tab is written as a real file into that in-memory
  filesystem, and `import` reads it back from there.
- **No sockets.** Wasm has no built-in way to open a network connection.
  Any network access has to be deliberately provided by the host.
- **No host process.** The code runs inside the browser's Wasm engine,
  under the browser's own sandbox, not as a program with access to your
  computer. The subclasses walk from
  [the previous concept](/03-tool-design-for-agents/08-code-execution-as-a-tool/02-why-restricted-execution-isnt-a-sandbox/#why-it-isn-t-safe)
  runs inside Pyodide too (you ran it there), and even the `Popen` it
  found can't start a process, because there's no operating system on
  the other side to start one in.

That's the whole idea. In-process restriction tried to take capability
*away* from code running in a powerful place. Wasm starts from *no*
capability and adds back only what the host chooses. Starting from
nothing is a far easier thing to get right than trying to subtract every
possible path to something.

</Subsection>

<Subsection title="What this page hands in" variant="a">

"Only what the host chooses" is a real choice, and this page makes one.
Pyodide gives the Python it runs a bridge to the JavaScript of the page
it's loaded on, the `js` module. Through it, Python can do anything that
page can: read and change what's on screen, read the page's browser
storage, and make web requests with the browser's `fetch`:

<LiveDemo client:load code={JS_BRIDGE_DEMO} />

So the precise claim is narrower than "the code can reach nothing." The
Wasm boundary protects *your computer*: no disk, no processes, no raw
network. Inside it, the code has exactly what the host granted, and here
that's the page. That grant is harmless on a course page with nothing
sensitive on it. An agent product that ran model-written code next to
API keys or a user's data would grant much less, for instance running
Pyodide in a separate Web Worker that can't see the page, with its
network access blocked.

Either way, the question to ask of any sandbox is the same one: what
did the host hand in?

</Subsection>

<Subsection title="The tradeoffs" variant="b">

Wasm isolation is strong, portable and quick to start, but it isn't
free:

- **Not everything runs.** A Wasm build of a language supports most, not
  all, of its libraries. Pyodide ports a large scientific stack, but a
  package relying on unsupported system calls may not work.
- **Some overhead.** Code runs somewhat slower than native, and there's
  memory cost to the runtime.
- **Provisioning what's needed is on you.** A task that legitimately
  needs a file or a network result requires the host to hand it in
  deliberately, which is more work than just letting code do anything,
  and is exactly the point.

For an agent's code-execution tool, this is often the sweet spot: a
strong boundary, fast enough to start on every call, with the host in
full control of what crosses it. It's not the only good answer,
containers and micro-VMs are widely used, but it's a real one, and it's
the one you've been running on all along.

</Subsection>
