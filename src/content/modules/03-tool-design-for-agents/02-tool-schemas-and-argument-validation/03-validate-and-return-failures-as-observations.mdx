<LiveDemo client:load code={`from pydantic import BaseModel, field_validator

`field_validator` — a custom semantic check beyond what a type alone can
express, on top of the `BaseModel` fundamentals from
[Module 0's Pydantic lesson](/00-python-essentials/05-typed-data-models/04-pydantic-fundamentals/)
— catches what the schema's type alone couldn't; the existence check
catches the other gap. Both return a plain string,
[the exact same failure-as-observation pattern from Module 2](/02-the-agent-loop/06-termination-failure-and-control/05-tool-errors-as-observations/#the-fix-catch-it-and-let-the-model-see-it)
— never a crash, always something the model can actually see and react
to.

A real validation error is also longer than a hand-written message would
be. Pydantic appends a `[type=value_error, ...]` detail and a trailing
"For further information visit..." docs link, so the live output above
carries more than the message text itself (`date 2020-01-01 is in the
past`, exactly what the `raise ValueError(...)` call wrote). That extra
detail helps a developer reading a log. For a model it's noise, and the
next sections trim it.

</Subsection>

<Subsection title="Two kinds of check, and where each belongs" variant="b">

[The previous concept](/03-tool-design-for-agents/02-tool-schemas-and-argument-validation/02-the-gap-constrained-decoding-doesnt-close/#four-more-ways-a-valid-call-can-still-be-wrong)
listed four ways a well-typed call can still be wrong. They split into
two groups, and each group has its own home:

- **Checks that depend only on the arguments** belong in the Pydantic
  model: a number out of range, a date in the past, two fields that
  contradict each other. The arguments alone are enough to decide.
- **Checks that depend on the world's current state** belong in the tool
  body: does this agent exist, is it retired right now. The answer can
  change between two identical calls, so it can't be part of the
  arguments' definition.

`field_validator` looks at one field at a time, so it can't compare two.
For a rule that involves several fields, Pydantic has `model_validator`.
With `mode="after"`, it runs once every field has passed its own
validation, and it receives the finished model as `self`, so it can read
all the fields together. Like a `field_validator`, it raises `ValueError`
to reject the input. If everything is fine it returns `self`:

<LiveDemo client:load code={`from datetime import date

code runs. The state checks come next, in the complete tool.

</Subsection>

<Subsection title="Trim the error before the model sees it" variant="a">

The full `ValidationError` text, above, includes the input dict, a type
code and a docs URL. Every character of that goes to the model as input.
`e.errors()` gives the same information as a list of dicts, one per
problem, so you can keep only what the model needs: which field, and
what's wrong with it. Each dict's `"loc"` holds the field's location (an
empty tuple for a cross-field `model_validator` error), and `"msg"` holds
the message:

<LiveDemo client:load code={`from datetime import date

`short_error` turns each problem into `field: message` (or just the
message, when there's no field), joined with `"; "`. It keeps what the
model needs to fix its call and drops the rest.

</Subsection>

<Subsection title="Wired into the loop" variant="a">

In a real run, the model often asks for several tool calls in one
response, and some may fail validation while others succeed. The loop
has to handle that without special cases:
[the same collect-every-call loop from Module 2](/02-the-agent-loop/05-react-and-reasoning-in-the-loop/01-the-react-pattern/#the-fix-gather-every-tool-call-act-on-all-of-them-reply-once)
runs every call and sends every result back in one user message, errors
included. (`pause_agent` and `REGISTRY` from the previous demo are
already defined here, along with the fake client. The `RecordingClient`
keeps a copy of every `messages` list it was sent, so the demo can show
exactly what went back to the model.)
