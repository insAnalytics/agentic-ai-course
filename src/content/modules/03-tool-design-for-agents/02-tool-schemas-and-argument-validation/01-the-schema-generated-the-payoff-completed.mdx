<Subsection title="The standard, from here forward" variant="a">

Every tool in this module gets its shape defined the same way:
[a Pydantic `BaseModel`, converted via `.model_json_schema()`](/01-llm-foundations/10-structured-output-and-tool-calling/03-from-a-pydantic-model-to-a-schema/#generating-the-schema-directly-from-a-model-you-already-know).

<LiveDemo client:load code={`from pydantic import BaseModel

class GetAgentConfigArgs(BaseModel):
    agent_name: str

schema = GetAgentConfigArgs.model_json_schema()
print(schema)`} />

Nothing new mechanically — this concept exists to make explicit that
[Lesson 1's parameter-design discipline](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/02-parameter-design/)
and this schema mechanism are two halves of the same job: good field
names and types feed directly into a schema the model's calls are
actually constrained against.

</Subsection>

<Subsection title="Richer arguments: lists and nested models" variant="b">

Real tools often take more than flat strings and numbers. Two shapes come
up constantly: a **list** of values, and a group of related fields that
belong together. For the list, use the `list[str]` type hint from
[Module 0's collections lesson](/00-python-essentials/02-collections/01-lists/).
For the group, define a second `BaseModel` and use it as a field's type.
That's a **nested model**: Pydantic validates the inner fields too, and
the schema describes them.

<LiveDemo client:load code={`import json
from pydantic import BaseModel, Field

class Owner(BaseModel):
    team: str = Field(description="Team responsible for the agent.")
    contact_email: str = Field(description="Where alerts about this agent are sent.")

class RegisterAgentArgs(BaseModel):
    agent_name: str = Field(description="Unique name for the new agent.")
    model: str = Field(description="Model the agent runs on, e.g. 'claude-sonnet'.")
    tags: list[str] = Field(description="Short labels for filtering, e.g. ['support', 'eu'].")
    owner: Owner = Field(description="Who owns this agent.")

print(json.dumps(RegisterAgentArgs.model_json_schema(), indent=2))`} />

Two things to find in the output:

- `tags` has `"type": "array"` with `"items": {"type": "string"}`: a list,
  and every item must be a string.
- `Owner` is described once under `"$defs"`, and the `owner` field points
  to it with a `"$ref"` to `#/$defs/Owner` (wrapped here in an `"allOf"`
  list, which just means "must match this"). The model sees `team` and
  `contact_email`, their descriptions, and that both are required.

This is the structured alternative to
[the JSON-in-a-string parameter the previous lesson warned against](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/02-parameter-design/#don-t-hide-json-inside-a-string-parameter):
the grouping is still there, but now the schema can see inside it and
check every part.

</Subsection>

<Subsection title="The full tool definition, built from code" variant="a">

[The previous lesson](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/01-names-and-descriptions-as-prompts/#what-the-model-actually-receives)
assembled a tool definition by hand: name, description and input schema.
Doing that by hand for every tool invites mistakes, so here it is as a
helper that takes any function plus its args model:

<LiveDemo client:load code={`import json
from pydantic import BaseModel, Field

class GetAgentConfigArgs(BaseModel):
    agent_name: str = Field(description="Exact registered name of the agent.")

def get_agent_config(agent_name: str) -> dict:
    """Look up one registered agent by its exact name.

    Returns that agent's configuration as a dict.
    """
    ...

def to_tool_definition(func, args_model) -> dict:
    return {
        "name": func.__name__,
        "description": func.__doc__,
        "input_schema": args_model.model_json_schema(),
    }

print(json.dumps(to_tool_definition(get_agent_config, GetAgentConfigArgs), indent=2))`} />

The code is now the single source of truth. Rename the function or
change the docstring or a field, and the next call to
`to_tool_definition` reflects it, with no separate JSON to keep in sync.
Two rough edges remain, though, and both are visible above. The
description still carries the docstring's line breaks and indentation
(the `\n` characters and the spaces after them). And a function with *no* docstring would quietly produce
`"description": null`, a tool the model has no description for. The
exercise below fixes both.

</Subsection>
