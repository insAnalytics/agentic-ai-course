<Subsection title="Valid shape, nonsensical content" variant="a">

[With strict mode on, constrained decoding](/01-llm-foundations/10-structured-output-and-tool-calling/02-constrained-decoding/#a-hard-guarantee-not-a-soft-nudge)
guarantees a call matches its schema — the right field names, the right
types; without it, arguments are usually but not always well-formed.
Even the guarantee says nothing about whether those values actually
make sense:

<LiveDemo client:load code={`from pydantic import BaseModel

class ScheduleMaintenanceArgs(BaseModel):
    agent_name: str
    date: str   # ISO 8601

call = ScheduleMaintenanceArgs(agent_name="research_agent", date="2020-01-01")
print(call)   # perfectly schema-valid -- and a date years in the past`} />

Nothing about this fails — `date` is a correctly-typed string,
`agent_name` is a correctly-typed string. The schema has no concept of
"in the past," or of `"research_agent"` actually existing in the real
registry. Both are real, meaningful problems the schema structurally
cannot catch, because they're facts about the world, not facts about
shape.

</Subsection>

<Subsection title="Four more ways a valid call can still be wrong" variant="b">

A past date is one example of a wider pattern. Here are four tool calls,
each typed exactly right, each accepted by Pydantic, and each wrong in a
different way:

<LiveDemo client:load code={`from datetime import date
from pydantic import BaseModel

REGISTRY = {
    "research_agent": {"model": "claude-sonnet", "status": "active"},
    "legacy_agent": {"model": "claude-haiku", "status": "retired"},
}

class SetMaxResultsArgs(BaseModel):
    agent_name: str
    max_results: int

class UpdateAgentModelArgs(BaseModel):
    agent_name: str
    model: str

class PauseAgentArgs(BaseModel):
    agent_name: str
    start_date: date
    end_date: date

calls = [
    ("out-of-range number", SetMaxResultsArgs(agent_name="research_agent", max_results=-5)),
    ("agent that doesn't exist", UpdateAgentModelArgs(agent_name="research_agnet", model="claude-opus")),
    ("start date after end date", PauseAgentArgs(agent_name="research_agent", start_date="2026-10-10", end_date="2026-10-01")),
    ("invalid for current state", UpdateAgentModelArgs(agent_name="legacy_agent", model="claude-opus")),
]
for label, call in calls:
    print(f"accepted ({label}): {call}")
print("legacy_agent's status:", REGISTRY["legacy_agent"]["status"])`} />

Every call got through. Each one breaks a different kind of rule:

- **Out of range.** `max_results=-5` is an `int`, but a negative count of
  results means nothing. The type allows it; the meaning doesn't.
- **A reference to something that doesn't exist.** `"research_agnet"` is
  a perfectly good string. It just isn't the name of any agent.
- **Fields that contradict each other.** Each date is valid on its own.
  Only together are they wrong: the pause would end before it starts. A
  check on one field at a time can never see this.
- **Invalid for the current state.** `legacy_agent` exists, and
  `"claude-opus"` is a real model. But the agent is retired, so updating
  it makes no sense *right now*. Nothing in the arguments alone can tell
  you that. It depends on what's in the registry at the moment of the
  call.

</Subsection>

<Subsection title="Why models produce calls like these" variant="a">

None of these calls is random noise. They're *plausible*, and that's the
problem. A model produces arguments the same way it produces any text,
[predicting likely tokens rather than checking facts](/01-llm-foundations/04-how-llms-generate-text/03-the-model-predicts-it-doesnt-know/#the-same-mechanism-whether-the-answer-is-grounded-or-not).
`"research_agnet"` looks like an agent name. A date range, a result
count and a model name all look like what those fields usually hold. An
ID the model half-remembers, or invents because it fits the pattern,
looks exactly as confident as a real one. At best (with strict mode on),
constrained decoding makes sure the *shape* is right. Nothing in the generation process checks that the
*values* are true.

So the fix can't live in the schema or the model. It has to live in your
code, which does know today's date, what's in the registry, and which
rules connect the fields. That's the next concept.

</Subsection>
