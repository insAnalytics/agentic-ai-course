def run_tool(call, tools: dict) -> dict:
    """Run one call, turning an unknown tool or a raised exception into an error observation."""
    if call.name not in tools:
        return {"type": "tool_result", "tool_use_id": call.id,
                "content": f"Error: there is no tool called {call.name}", "is_error": True}
    try:
        output = tools[call.name](**call.input)
    except Exception as e:
        return {"type": "tool_result", "tool_use_id": call.id, "content": f"Error: {e}", "is_error": True}
    return {"type": "tool_result", "tool_use_id": call.id, "content": output}

def answer_call(call, tools: dict, gated: set, decisions: dict) -> dict:
    if call.name in gated and decisions.get(call.id) is False:
        # the human said no: the model gets an error observation, and the tool never runs
        return {"type": "tool_result", "tool_use_id": call.id,
                "content": f"Error: a human declined {call.name}({call.input}). Don't retry it; tell the user.",
                "is_error": True}
    return run_tool(call, tools)

def run_agent(llm, messages: list, tools: dict, gated: set, decisions: dict, max_steps: int = 10) -> dict:
    for _ in range(max_steps):
        if messages[-1]["role"] != "assistant":
            response = llm.create(messages=messages)
            messages.append({"role": "assistant", "content": response.content})
        calls = [b for b in messages[-1]["content"] if b.type == "tool_use"]
        if not calls:
            return {"status": "done", "answer": "".join(b.text for b in messages[-1]["content"] if b.type == "text")}
        waiting = [c for c in calls if c.name in gated and c.id not in decisions]
        if waiting:
            # pause BEFORE answering: nothing runs, and no tool_result is sent, until a human decides
            return {"status": "paused", "waiting": [(c.id, c.name, c.input) for c in waiting]}
        messages.append({"role": "user", "content": [answer_call(c, tools, gated, decisions) for c in calls]})
    return {"status": "stopped", "answer": f"stopped after {max_steps} steps"}

<Subsection title="Not all tools carry the same risk" variant="a">

[Narrow tools](/03-tool-design-for-agents/11-designing-for-least-privilege/01-narrow-tools-shrink-the-blast-radius/)
shrink what each tool can do. This concept shrinks *where the dangerous
tools are exposed*. The key observation: reading and writing carry very
different risk. A read tool that's tricked leaks information, which is
bad; a write tool that's tricked changes or destroys it, which is often
worse and can't always be undone.

Yet tools are frequently built to do both, an `update_agent` that reads
the current config and writes a new one, a file tool that can read or
overwrite. When one tool both reads and writes, every place the read is
used also exposes the write. Splitting them lets each carry only the power
it needs.

</Subsection>

<Subsection title="The split" variant="b">

<LiveDemo client:load code={SPLIT_DEMO} />

The read tools can be handed out freely: the worst an injection does
through them is read a model name, which isn't sensitive here. The write
tools are a separate, smaller set, and they're the ones to guard. An agent
whose *job* is read-only, answering questions about the registry, can be
given only the read tools and none of the write ones, and then no
injection can change anything at all, because the capability isn't
present. This is
[narrow tools](/03-tool-design-for-agents/11-designing-for-least-privilege/01-narrow-tools-shrink-the-blast-radius/)
again, applied to the read/write line: the most useful cut you can make in
most agents.

</Subsection>

<Subsection title="Gating the writes that remain" variant="a">

Some agents genuinely need to write. For the destructive or outbound ones
among those, the next protection is an **approval gate**: before the
action runs, a human is asked to confirm it. The agent proposes; a person
disposes.

The obvious way to build one doesn't work. You might answer a gated call
with a `tool_result` saying "awaiting approval", let the loop carry on,
and run the real action later. But every `tool_use` gets exactly one
`tool_result`, sent in the very next message, so there's nowhere for the
real result to go once the model has already been told "awaiting". The
model would also carry on believing the action is still pending.

So the gate pauses the loop *before* answering. When the model asks for a
gated tool and no human has decided yet, `run_agent` returns what's
waiting and sends nothing. The `messages` list, ending with the model's
unanswered request, is the saved state, the same idea as
[Module 2's checkpointing](/02-the-agent-loop/07-agent-state-and-the-scratchpad/03-checkpoint-and-resume/).
Once a human decides, calling `run_agent` again with the same `messages`
picks up exactly where it stopped:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={GATE_DEMO} />

On the first run the deletion doesn't happen, and the last message is
still the model's unanswered request. After a human approves that call by
its id, the second run answers it with the real result and the model
finishes. If the human declines, `answer_call` sends an
[error observation](/02-the-agent-loop/06-termination-failure-and-control/05-tool-errors-as-observations/)
instead, so the model learns the action was refused and can tell the
user.

Two design points make the gate real rather than decorative:

- **The gate is in your code, not the prompt.** "Ask before deleting" in a
  system prompt is a request the model can be talked out of. A loop that
  won't run a gated call without a recorded decision is a limit that holds
  no matter what the model was persuaded to do. This is the
  [structural-versus-mitigation line](/03-tool-design-for-agents/10-the-tool-threat-model/02-why-the-model-cant-be-the-security-boundary/)
  once more.
- **Approval is per call, not per tool.** Approving one `delete_agent`
  call must not stand in for the next one. The human is confirming *this
  deletion of this agent*, so decisions are keyed by the call's id, and an
  injection can't get one innocuous deletion approved and reuse that
  approval for a different one.

Gates cost something too: they put a human back in the loop, which is
slower and doesn't scale to thousands of actions. So you gate the actions
whose cost of being wrong is high, deletion, sending money, emailing
outsiders, and let the cheap, reversible ones run freely. Deciding which
is which is the design judgment
[last lesson's blast-radius thinking](/03-tool-design-for-agents/10-the-tool-threat-model/04-thinking-in-terms-of-the-blast-radius/)
is meant to inform.

</Subsection>
