export const NARROW_DEMO = String.raw`import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE agents (name TEXT, model TEXT, owner TEXT, monthly_cost INTEGER)")
db.executemany("INSERT INTO agents VALUES (?, ?, ?, ?)", [
    ("research_agent", "claude-opus", "alice", 4200),
    ("support_agent", "claude-haiku", "bob", 900),
])

# the same capability, as narrow purpose-built tools
def get_agent_model(agent_name: str) -> str:
    row = db.execute("SELECT model FROM agents WHERE name = ?", (agent_name,)).fetchone()
    return row[0] if row else f"Error: no agent named '{agent_name}'."

def list_agent_names() -> str:
    return ", ".join(name for (name,) in db.execute("SELECT name FROM agents"))

# the normal requests still work
print("normal:", get_agent_model("research_agent"))
print("names: ", list_agent_names())

# an injection can only choose the argument, and no argument reaches the other columns
for attempt in ["SELECT * FROM agents", "x' OR '1'='1"]:
    print(f"injected {attempt!r} ->", get_agent_model(attempt))`;

<Subsection title="The same choice, now for a different reason" variant="a">

[The narrow-versus-broad choice](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/03-granularity-narrow-vs-broad-tools/)
was weighed as a usability question: a narrow tool like
`get_agent_model(name)` is easier for a model to call correctly than a
broad one like `run_query(sql)`.
[The last lesson](/03-tool-design-for-agents/10-the-tool-threat-model/04-thinking-in-terms-of-the-blast-radius/)
added the second reason, and it's the one this lesson builds on. A broad
tool is a bigger **blast radius**: more that a compromised agent can do
through it.

This is the first and often most effective least-privilege technique,
because it works at the point where capability enters the agent. A tool
the agent doesn't have is a thing no injected instruction can make it do.

</Subsection>

<Subsection title="The pain: one broad tool, asked the wrong way" variant="b">

Here's a registry that holds more than just models: it also has each
agent's owner and monthly cost, which shouldn't leave the system. It's a
real SQLite table, the same built-in database from
[the parameterized-query demo](/03-tool-design-for-agents/10-the-tool-threat-model/02-why-the-model-cant-be-the-security-boundary/#sql-injection-has-a-fix-prompt-injection-doesn-t-yet).
The agent has one broad tool, `run_query`:

<LiveDemo client:load code={BROAD_DEMO} />

The tool was added so the agent could look up a model. It can do that. It
can also be asked for the entire table, costs and owners included, and the
tool has no reason to refuse: returning whatever the query asks for is its
whole job. An injected `SELECT *` turns the model-lookup tool into a data
dump. The blast radius of `run_query` is "anything in the database".

</Subsection>

<Subsection title="The fix: purpose-built tools" variant="a">

Replace the one broad tool with a few narrow ones, each returning exactly
what a real task needs and nothing more:

<LiveDemo client:load code={NARROW_DEMO} />

`get_agent_model` returns one field of one agent. `list_agent_names`
returns names. Neither can return a cost or an owner, because neither was
written to, and there is no `run_query` any more. The most an injected
instruction can do is pick the argument, and the argument travels through
a `?` placeholder, so even SQL-shaped text is only ever an agent name that
doesn't exist. The sensitive columns
aren't guarded by a rule the model has to follow: they're simply not
reachable through any tool the agent has. That's the difference between a
mitigation and a structural limit,
[the distinction from the last lesson](/03-tool-design-for-agents/10-the-tool-threat-model/02-why-the-model-cant-be-the-security-boundary/).

The cost is real and worth naming: narrow tools are less flexible. A
question nobody anticipated ("which owner has the highest total cost?")
now has no single tool that answers it, where `run_query` could. That's
the trade at the center of least privilege. You give up open-ended
flexibility to gain a blast radius you can actually reason about, and for
an agent exposed to untrusted content, that's almost always the right
trade. An agent exposed only to trusted input can afford broader tools,
exactly as
[last lesson's "match the radius to the trust"](/03-tool-design-for-agents/10-the-tool-threat-model/04-thinking-in-terms-of-the-blast-radius/#match-the-radius-to-the-trust)
put it.

</Subsection>
