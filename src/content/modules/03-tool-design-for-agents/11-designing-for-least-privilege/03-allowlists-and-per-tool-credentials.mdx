export const ALLOWLIST_DEMO = String.raw`# an outbound email tool, with and without an allowlist on the recipient

ALLOWED_RECIPIENTS = {"team@ourcompany.example", "oncall@ourcompany.example"}
SENT = []

def send_email_unrestricted(to: str, body: str) -> str:
    SENT.append((to, body))
    return f"sent to {to}"

def send_email(to: str, body: str) -> str:
    if to not in ALLOWED_RECIPIENTS:
        return f"Error: {to} is not an approved recipient. Allowed: {', '.join(sorted(ALLOWED_RECIPIENTS))}."
    SENT.append((to, body))
    return f"sent to {to}"

# an injected instruction wants the agent to email data to an outside address
print("unrestricted:", send_email_unrestricted("attacker@evil.example", "Q3 figures: ..."))
print("allowlisted: ", send_email("attacker@evil.example", "Q3 figures: ..."))
print("legit use:   ", send_email("oncall@ourcompany.example", "research_agent is down"))
print("actually sent:", SENT)
`;

# whoever owns the database sets it up, with full access
admin = sqlite3.connect("registry.db")
admin.execute("CREATE TABLE IF NOT EXISTS agents (name TEXT PRIMARY KEY, model TEXT)")
admin.execute("INSERT OR REPLACE INTO agents VALUES ('research_agent', 'claude-opus')")
admin.commit()

# the lookup tool is handed a READ-ONLY connection: its credential, scoped to its job
lookup_credential = sqlite3.connect("file:registry.db?mode=ro", uri=True)

def get_agent_model(agent_name: str) -> str:
    row = lookup_credential.execute("SELECT model FROM agents WHERE name = ?", (agent_name,)).fetchone()
    return row[0] if row else f"Error: no agent named '{agent_name}'."

print("lookup works:", get_agent_model("research_agent"))

# suppose something goes wrong and a write is attempted through this tool's credential
try:
    lookup_credential.execute("DELETE FROM agents")
except sqlite3.OperationalError as e:
    print("refused by the database, not the tool:", e)

print("rows still there:", admin.execute("SELECT COUNT(*) FROM agents").fetchone()[0])`;

export const SEND_REFERENCE = String.raw`def make_send_email(allowed_recipients: set, outbox: list):
    def send_email(to: str, body: str) -> str:
        if to not in allowed_recipients:
            allowed = ", ".join(sorted(allowed_recipients))
            return f"Error: {to} is not an approved recipient. Allowed recipients: {allowed}."
        outbox.append({"to": to, "body": body})
        return f"sent to {to}"
    return send_email
`;

<Subsection title="Limiting a tool that does get called" variant="a">

[Narrow tools](/03-tool-design-for-agents/11-designing-for-least-privilege/01-narrow-tools-shrink-the-blast-radius/)
limit what tools exist, and
[gates](/03-tool-design-for-agents/11-designing-for-least-privilege/02-separate-reads-from-writes-and-gate-the-writes/)
limit when a tool runs. This concept limits what a tool can reach *when it
does run*, so that even a tool the agent is meant to have, called with the
agent's own permission, can't be turned all the way to the worst case.

</Subsection>

<Subsection title="Allowlists: bound what a tool can act on" variant="b">

An **allowlist** is a fixed set of things a tool is permitted to act on,
checked inside the tool. You met one already:
[Lesson 9's fetch tool](/03-tool-design-for-agents/09-web-interaction/04-everything-from-the-web-is-untrusted-input/#why-the-model-can-t-simply-ignore-it)
that would only fetch URLs the agent had actually been given. The same
idea bounds any tool with an external reach, an email tool's recipients, a
database tool's tables, a file tool's directories:

<LiveDemo client:load code={ALLOWLIST_DEMO} />

The unrestricted tool emailed the confidential figures to an outside
address, because that's what it was asked to do. The allowlisted tool
refused: `attacker@evil.example` isn't on the list, so no injected
instruction can send there, while genuine sends to the team still work.
This cuts the
[external-communication leg of the trifecta](/03-tool-design-for-agents/10-the-tool-threat-model/03-the-dangerous-combination/)
down from "anywhere" to "these approved destinations", which for many
agents is enough to break the leg entirely. Note the refusal is a useful
error that names the allowed recipients,
[as Lesson 3 advised](/03-tool-design-for-agents/03-shaping-what-tools-return/03-structured-results-and-useful-error-messages/),
so a model that had a legitimate reason can correct itself.

</Subsection>

<Subsection title="Per-tool credentials: each tool holds only its own access" variant="a">

The deepest version of least privilege is about the *credentials* the
tools run with. An agent's tools need access to real systems, a database,
an email service, a payment API, and that access comes from credentials:
API tokens, database roles, service accounts. The temptation is to give
the whole agent one powerful credential that can do everything. The safer
design gives each tool only the credential it needs, scoped to exactly its
job:

<LiveDemo client:load code={CREDENTIAL_DEMO} />

*A read-only SQLite connection stands in for a real scoped credential,
such as a read-only database role or an API token limited to one
resource. In production the refusal would come from a database server or
an API, not from a library in the same process, but the idea is the
same.*

The lookup tool holds a connection that can only *read* the registry. The
tool's code never checks for writes at all: when one is attempted, the
database itself refuses, one layer below the tool. And the tool was never
handed any other credential, for billing or anything else, so nothing
that goes wrong in it can reach those systems.

This is **the principle of least privilege**, the idea underneath this
whole lesson, stated in its original form: every component should have the
minimum access it needs to do its job, and no more. It matters because
it's the last line that holds when the others don't. If a narrow tool
turns out to do more than you realized, or a gate is missing on some
action, a tightly scoped credential still caps what any single tool can
actually reach. Scoping credentials is enforced by the systems the
credentials belong to, the database, the API, the operating system, not by
the agent or the model, which is exactly why it holds even when everything
above it has been talked around.

Setting up scoped credentials, service accounts, narrow database roles and
rotating tokens, is operational work that belongs to deployment and
production security, later in the course. What matters at the design stage
is the principle: decide what each tool must reach before you build it,
give it exactly that, and never hand the agent one credential that can do
everything.

</Subsection>
