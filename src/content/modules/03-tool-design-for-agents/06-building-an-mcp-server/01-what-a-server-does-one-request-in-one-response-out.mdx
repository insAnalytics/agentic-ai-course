<Subsection title="A server is a function" variant="a">

[Lesson 5](/03-tool-design-for-agents/05-the-model-context-protocol/00-intro/)
described MCP from the client's side of the wire. This lesson builds the
other side: a registry server that any MCP host can connect to. Before
using the official SDK, which hides most of the work, it's worth writing
one by hand, because the core turns out to be small.

MCP is
[stateless](/03-tool-design-for-agents/05-the-model-context-protocol/03-stateless-by-design/#you-ve-met-this-idea-three-times-already):
every request carries everything needed to answer it, and the server
remembers nothing between requests. So a server's whole job fits in one
function: take one JSON-RPC request, return one JSON-RPC response.
Everything else, stdin or HTTP, is just how the request arrives and the
response leaves.

That function does three things, in order:

1. **Check the request's `_meta`,** exactly as
   [Lesson 5's exercise](/03-tool-design-for-agents/05-the-model-context-protocol/03-stateless-by-design/#every-request-carries-its-own-meta)
   did: required fields present, protocol version supported.
2. **Route by `method`** to the code that handles it. An unknown method
   gets `-32601`.
3. **Build the answer** into a response with the request's `id` and a
   `result` carrying `resultType`.

</Subsection>

<Subsection title="The tool table" variant="b">

The server keeps its tools in a table, the same idea as
[Module 2's `TOOL_REGISTRY`](/02-the-agent-loop/04-writing-the-loop-by-hand/03-handling-multiple-tools/#the-fix-a-dict-mapping-names-to-actual-callables),
with one addition: each tool is stored with the Pydantic model
describing its arguments. That model does two jobs. It produces the
tool's schema for `tools/list`,
[the same way Lesson 2 generated schemas](/03-tool-design-for-agents/02-tool-schemas-and-argument-validation/01-the-schema-generated-the-payoff-completed/#the-full-tool-definition-built-from-code),
and in the next concept it validates the arguments a `tools/call`
arrives with.

Here's the whole server, handling `server/discover` and `tools/list` so
far:

```python
from pydantic import BaseModel, Field

SUPPORTED_VERSIONS = ["2026-07-28"]
REQUIRED_META = ["io.modelcontextprotocol/protocolVersion", "io.modelcontextprotocol/clientCapabilities"]

REGISTRY = {"research_agent": "claude-sonnet", "support_agent": "claude-haiku"}

class GetAgentModelArgs(BaseModel):
    agent_name: str = Field(description="Exact registered name of the agent.")

def get_agent_model(agent_name: str) -> str:
    """Return the model one registered agent runs on, looked up by its exact name."""
    return REGISTRY[agent_name]

# the server's tool table: each tool's function and its arguments model
TOOLS = {"get_agent_model": (get_agent_model, GetAgentModelArgs)}

def error_response(request_id, code: int, message: str, data=None) -> dict:
    error = {"code": code, "message": message}
    if data is not None:
        error["data"] = data
    return {"jsonrpc": "2.0", "id": request_id, "error": error}

def result_response(request_id, result: dict) -> dict:
    return {"jsonrpc": "2.0", "id": request_id, "result": {"resultType": "complete", **result}}

def handle_discover(params: dict) -> dict:
    return {
        "supportedVersions": SUPPORTED_VERSIONS,
        "capabilities": {"tools": {}},
        "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "registry-server", "version": "1.0.0"}},
        "instructions": "Read-only access to the agent registry.",
    }

def handle_tools_list(params: dict) -> dict:
    tools = []
    for name, (function, args_model) in TOOLS.items():
        tools.append({
            "name": name,
            "description": function.__doc__,
            "inputSchema": args_model.model_json_schema(),
        })
    return {"tools": tools}

METHOD_HANDLERS = {"server/discover": handle_discover, "tools/list": handle_tools_list}

def handle_request(request: dict) -> dict:
    request_id = request.get("id")
    meta = request.get("params", {}).get("_meta", {})
    for field in REQUIRED_META:
        if field not in meta:
            return error_response(request_id, -32602, f"Invalid params: missing _meta field {field}")
    requested = meta["io.modelcontextprotocol/protocolVersion"]
    if requested not in SUPPORTED_VERSIONS:
        return error_response(request_id, -32022, "Unsupported protocol version",
                              {"supported": SUPPORTED_VERSIONS, "requested": requested})
    handler = METHOD_HANDLERS.get(request["method"])
    if handler is None:
        return error_response(request_id, -32601, f"Method not found: {request['method']}")
```

this demo can call `handle_request` directly:

A few details worth noticing:

- **`METHOD_HANDLERS` is a dispatch dict,** the same pattern as the tool
  registry, one level up: it maps a method name to the function that
  answers it. Adding `resources/list` later means adding one entry.
- **The tool's description is its docstring,** read with
  `function.__doc__`, the attribute
  [Lesson 1's exercises graded](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/01-names-and-descriptions-as-prompts/#what-the-model-actually-receives).
  Everything that lesson said about writing descriptions as prompts
  applies here: this string is what the model reads when it decides
  whether to call the tool.
- **The two helpers keep the response shapes in one place.** Every error
  has the same shape and every result gets `resultType`, so no handler
  can forget either.

</Subsection>

<Subsection title="Where the transport fits" variant="a">

`handle_request` knows nothing about how the request arrived. A
transport is a thin loop around it. For stdio,
[following the transport rules from Lesson 5](/03-tool-design-for-agents/05-the-model-context-protocol/05-transports-how-the-messages-travel/#stdio-a-local-server-as-a-subprocess),
the loop reads one line, answers, and writes one line:

```python
import json
import sys

for line in sys.stdin:
    response = handle_request(json.loads(line))
    # this print() is the protocol itself: one response, one line, on stdout
    print(json.dumps(response), flush=True)
```

*Illustrative. It isn't run in this sandbox, which has no stdin to
read.*

This is the one place a stdio server *should* write to stdout, because
the response is the protocol. Any other output belongs on stderr. For
Streamable HTTP, the same function sits behind a single POST endpoint,
[the kind of route Module 0's FastAPI lessons built](/00-python-essentials/09-building-apis-with-fastapi/04-request-bodies-and-uploads/#a-basemodel-parameter-is-the-request-body).
The core doesn't change, and that separation is exactly what the SDK in
the rest of this lesson relies on.

This sketch handles requests only. A notification has no `id`,
[so it never gets a response](/03-tool-design-for-agents/05-the-model-context-protocol/02-json-rpc-as-the-message-format/#the-four-shapes);
a full server would check for that before answering.

</Subsection>
