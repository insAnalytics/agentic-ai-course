<Subsection title="What an agent needs from the web" variant="a">

A model's knowledge stops at
[its training cutoff](/01-llm-foundations/04-how-llms-generate-text/05-knowledge-cutoff/),
and it has never seen your company's internal pages at all. For anything
current, or anything it was never trained on, an agent has to go and read
it. Almost every web-capable agent does that with the same pair of tools:

- **Search** takes a query and returns a short list of candidates: a
  title, a URL and a snippet for each.
- **Fetch** takes one URL and returns that page's content.

They're separate on purpose. Search results are small and cheap: a few
lines per result, enough for the model to judge which page is worth
reading. Fetching a page is expensive: a full page is thousands of
tokens. Splitting the two lets the model look at many candidates cheaply
and then spend tokens only on the one or two pages that actually answer
the question. It's
[Lesson 3's result-size discipline](/03-tool-design-for-agents/03-shaping-what-tools-return/01-why-a-huge-tool-result-hurts/)
built into the shape of the tools.

The demos in this lesson use a small, canned slice of "the web", since
the course's sandbox can't make network requests:

<Subsection title="Search, then fetch" variant="b">

*A real search tool calls a search API, and real fetching makes an HTTP
request, as in
[Lesson 4](/03-tool-design-for-agents/04-tools-that-call-the-outside-world/00-intro/).*

The search result is
[structured JSON](/03-tool-design-for-agents/03-shaping-what-tools-return/03-structured-results-and-useful-error-messages/),
with a URL the model can pass straight to fetch, and a `total` so it
knows whether it's seeing everything. Sometimes the snippet alone answers
the question, and no fetch is needed at all.

The fetch result is the problem. Of its roughly 1,000 characters, the
actual answer is about 150. The rest is styling, scripts, a navigation
bar, a cookie banner and a footer, all of which the model would pay for
and have to read around. Getting the useful part out of a page is
[the next concept](/03-tool-design-for-agents/09-web-interaction/02-getting-the-useful-part-out-of-a-page/).

</Subsection>

<Subsection title="Designing the two tools" variant="a">

Everything from
[Lesson 1](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/00-intro/)
applies. A few choices matter especially for web tools:

- **Say what each tool is for, and when not to use it.** "Search the web
  for pages about a topic. Use fetch, not search, when you already have
  the URL." Models otherwise tend to re-search for pages they've already
  found.
- **Bound the results.** A search tool should return a handful of
  results, not fifty. More results means more tokens, and more
  near-duplicates for the model to choose between.
- **Make "nothing found" useful.** An empty list gives the model nothing
  to do next. "No results for X; try fewer or more general keywords" does.
- **Report fetch failures clearly.** A page can be missing, blocked or
  slow. Each should come back as a tool error the model can react to, with
  [the timeouts and retries from Lesson 4](/03-tool-design-for-agents/04-tools-that-call-the-outside-world/00-intro/)
  behind it.

</Subsection>

<Subsection title="You don't always have to build them" variant="b">

Some model providers offer search and fetch as **server tools**: tools
that run on the provider's own infrastructure rather than yours.
Anthropic's API has both. You include `web_search` or `web_fetch` in the
request's tool list, the API performs the search or fetch itself during
the request, and the results appear in the conversation. Your code never
runs the tool or returns a `tool_result` for it.

That saves real work, and the provider handles fetching, text
extraction, rate limits and sometimes citations. You'd still build your
own tools when you need a particular search provider, access to internal
pages the provider can't reach, or control over exactly what's fetched
and how. Either way, the rest of this lesson applies, because both kinds
bring web content into the model's context.

</Subsection>
