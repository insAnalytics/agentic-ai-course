<Subsection title="Every server you connect adds to every request" variant="a">

Connecting a server is one line of configuration, and a useful server
might offer ten, twenty or fifty tools. So it's easy for an agent to end
up with far more tools than any single task needs. That has two costs,
and both grow with every server added.

**Tokens, on every request.**
[The previous concept](/03-tool-design-for-agents/07-connecting-an-agent-to-mcp-servers/02-routing-the-models-calls-inside-the-loop/#the-routed-loop)
sent the whole catalog with every `create(...)` call. Tool definitions
are ordinary input, so this is
[Lesson 3's cost problem](/03-tool-design-for-agents/03-shaping-what-tools-return/01-why-a-huge-tool-result-hurts/#a-tool-result-is-just-more-input-tokens)
again, from the other direction: not one oversized result, but a large
block of definitions resent on every step.

<LiveDemo client:load code={COST_DEMO} />

*Characters ÷ 4 is
[a rough token estimate](/03-tool-design-for-agents/03-shaping-what-tools-return/01-why-a-huge-tool-result-hurts/#a-tool-result-is-just-more-input-tokens).*

These toy definitions are short, about 90 tokens each. Real ones are
much longer, with detailed descriptions, many parameters and nested
schemas. Anthropic's documentation gives a real example: a typical setup
of five servers, such as GitHub, Slack, Sentry, Grafana and Splunk, uses
around 55,000 tokens of tool definitions before the model has done any
work at all.
[Prompt caching](/01-llm-foundations/06-context-windows-and-kv-cache/04-prompt-structure-and-cache-hits/#the-cache-benefit-extends-across-separate-requests-not-just-within-one)
softens the price, since the definitions are the same stable prefix on
every request, but they still take up the context window every time,
and caching does nothing for the second problem.

**Worse choices.** The more tools a model sees, the more likely it is to
pick the wrong one. Anthropic's documentation puts the threshold
plainly: Claude's ability to pick the right tool degrades once it has
more than about 30 to 50 tools available. Anthropic's engineering team
reports that the most common failures are choosing the wrong tool and
passing incorrect parameters, especially when tools have similar names.
The demo's catalog has five `get_status` tools; a real multi-server
setup has many near-duplicates like that.

</Subsection>

<Subsection title="Fix 1: connect only what the agent needs" variant="b">

The simplest fix happens before any code: an agent that manages the
registry doesn't need the calendar server. Each agent gets its own list
of servers, chosen for its job, rather than every agent connecting to
everything the organization has.

</Subsection>

<Subsection title="Fix 2: offer only the tools the task needs" variant="a">

Even a relevant server usually offers more tools than one agent uses. An
**allowlist** names, per server, exactly which tools this agent may see,
and the catalog builder skips everything else. This lesson's stand-in
servers are loaded before the demo runs:

<LiveDemo client:load setupCode={MCP_STANDINS} code={ALLOWLIST_DEMO} />

Two tools instead of four. The registry's `get_status` and the
monitoring server's `alerts.list` still exist on their servers; this
agent just isn't offered them. Two details matter here:

- **The allowlist uses the servers' original tool names,**
  `get_agent_model` rather than `registry__get_agent_model`, because
  it's written against what each server actually offers.
- **A tool the model isn't offered can't be called.** The route for it
  never exists, so
  [the routing step](/03-tool-design-for-agents/07-connecting-an-agent-to-mcp-servers/02-routing-the-models-calls-inside-the-loop/#three-things-that-can-go-wrong)
  answers any attempt as an unknown tool, without contacting a server.
  That makes the allowlist more than a performance fix: it's the first
  step toward limiting what an agent is able to do, covered properly in
  a later lesson in this module on designing for least privilege.

</Subsection>

<Subsection title="Fix 3: different tools for different stages" variant="b">

An agent that plans, then acts, then checks its work rarely needs the
same tools in every stage.
[Module 2's phase-aware system prompts](/02-the-agent-loop/03-the-system-prompt-as-agent-design/04-phase-aware-prompting/#the-stronger-approach-the-code-tracks-phase-as-real-state)
changed the instructions per stage; the same idea applies to the tool
list. Building a catalog per stage, a read-only set while researching, a
write set only when it's time to act, keeps each stage's list short.

</Subsection>

<Subsection title="Fix 4: make similar tools easy to tell apart" variant="a">

When two tools really are both needed and look alike, the fix is
[Lesson 1's](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/01-names-and-descriptions-as-prompts/#what-a-description-should-say):
descriptions that say when to use each one, and when *not* to. The
server prefix from
[the first concept](/03-tool-design-for-agents/07-connecting-an-agent-to-mcp-servers/01-discovering-tools-from-several-servers/#the-fix-prefix-clean-up-and-keep-a-route-back)
helps too: `registry__get_status` and `monitoring__get_status` are
already clearer than two tools both called `get_status`.

</Subsection>

<Subsection title="Beyond static lists" variant="b">

All four fixes decide the tool list *before* the task starts. For agents
that genuinely need access to hundreds of tools, there's a different
approach: offer the model a small search tool, and load the definitions
it asks for only when it needs them. Anthropic's API has this built in,
and it's one of several techniques for managing what goes into the
context window at all, which is Module 4's subject. For most agents, a
well-chosen allowlist is enough.

</Subsection>
