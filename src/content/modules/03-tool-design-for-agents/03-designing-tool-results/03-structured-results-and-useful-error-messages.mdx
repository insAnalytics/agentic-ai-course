<Subsection title="Two more ways a result can be the wrong shape" variant="a">

[Concept 2](/03-tool-design-for-agents/03-designing-tool-results/02-truncation-and-pagination/#the-fix-for-a-result-that-could-be-huge-cap-it-and-say-so)
dealt with a result being too *big*. This concept covers two quieter
problems: a result that's the right size but awkward for the model to
actually *use*, and an error message that technically reports a failure
but gives the model nothing to act on.

</Subsection>

<Subsection title="Prose results make the model re-extract what you already had" variant="b">

<LiveDemo client:load code={`def get_agent_config_prose(agent_name: str, registry: dict) -> str:
    info = registry[agent_name]
    return (
        f"The agent called {agent_name} is currently configured to run on "
        f"{info['model']}, and it was originally set up on {info['created']}. "
        f"Its current status is {info['status']}."
    )

registry = {
    "research_agent": {"model": "claude-sonnet", "created": "2026-03-14", "status": "active"},
}
print(get_agent_config_prose("research_agent", registry))`} />

The tool *had* clean, separate fields — `model`, `created`, `status` —
and then deliberately blended them into a sentence. If the model's next
step needs just the `model` value (to pass into another tool call, say),
it now has to pull it back out of the prose itself. Usually that works;
but it's an unnecessary, avoidable extraction step, and one more place
for a subtle misreading to creep in.

</Subsection>

<Subsection title="The fix: return structured data, as JSON text" variant="a">

A `tool_result`'s content is text —
[the same message format from Module 2's hand-written loop](/02-the-agent-loop/04-writing-the-loop-by-hand/02-from-round-trip-to-loop/#the-actual-loop-written-and-running-for-real)
— so "structured" here means structured *text*: JSON, produced with
[`json.dumps`, from Module 0](/00-python-essentials/06-files-errors-and-validation/02-working-with-json/#json-loads-json-dumps-the-string-versions).

<LiveDemo client:load code={`import json

def get_agent_config(agent_name: str, registry: dict) -> str:
    info = registry[agent_name]
    return json.dumps({"agent_name": agent_name, **info})

registry = {
    "research_agent": {"model": "claude-sonnet", "created": "2026-03-14", "status": "active"},
}
print(get_agent_config("research_agent", registry))`} />

Every field is labeled and separated — the model reads
`"model": "claude-sonnet"` directly, with no sentence to parse around it.
`{"agent_name": agent_name, **info}` uses
[the `**` unpacking operator from Module 0](/00-python-essentials/03-functions-and-reuse/02-args-and-kwargs/#why-this-matters-for-agent-code-forwarding-calls),
here inside a dict literal, to merge `info`'s keys into the new dict
alongside `agent_name`.

**When prose is actually fine:** a result the model will mostly just
*relay* to a user — a short summary, a confirmation message — doesn't
need JSON. Structure earns its place when the model needs to *act on*
specific fields, not just read them out.

</Subsection>

<Subsection title="Useful error messages: say what failed, and what to do next" variant="b">

[Lesson 2](/03-tool-design-for-agents/02-tool-schemas-and-argument-validation/03-validate-and-return-failures-as-observations/#closing-the-gap-a-validator-plus-the-failure-as-observation-pattern)
established *that* failures should come back as observations. This is
about the *quality* of that observation. Compare two ways of reporting the
same failure:

<LiveDemo client:load code={`import json

def get_agent_config_bad_error(agent_name: str, registry: dict) -> str:
    if agent_name not in registry:
        return "Error: failed"
    return json.dumps({"agent_name": agent_name, **registry[agent_name]})

def get_agent_config_good_error(agent_name: str, registry: dict) -> str:
    if agent_name not in registry:
        available = list(registry.keys())[:5]
        return (
            f"Error: no agent named '{agent_name}'. "
            f"Available agents include: {', '.join(available)}. "
            f"Agent names are case-sensitive."
        )
    return json.dumps({"agent_name": agent_name, **registry[agent_name]})

registry = {
    "research_agent": {"model": "claude-sonnet", "created": "2026-03-14", "status": "active"},
    "support_agent": {"model": "claude-haiku", "created": "2026-05-02", "status": "active"},
}

print(get_agent_config_bad_error("Research_Agent", registry))
print(get_agent_config_good_error("Research_Agent", registry))`} />

`"Error: failed"` tells the model *that* something went wrong and nothing
else — its most likely next move is to retry the exact same call, which
[Module 2's repeated-action detection](/02-the-agent-loop/06-termination-failure-and-control/03-repeated-action-detection/#a-sharper-signal-than-too-many-steps)
would then have to catch. The better message names what failed, shows
real valid options, and points at the likely cause (casing) — giving the
model an obvious, correct next call to make. `[:5]` caps the list of
names,
[the same result-size discipline from Concept 2](/03-tool-design-for-agents/03-designing-tool-results/02-truncation-and-pagination/#the-fix-for-a-result-that-could-be-huge-cap-it-and-say-so),
applied to an error message: a helpful error for a 5,000-agent registry
shouldn't itself become a 50,000-token result.

</Subsection>
