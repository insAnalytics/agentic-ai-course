<Subsection title="The schema constrains shape — not whether the shape makes sense" variant="a">

[Constrained decoding, from Module 1](/01-llm-foundations/10-structured-output-and-tool-calling/02-constrained-decoding/#a-hard-guarantee-not-a-soft-nudge),
guarantees a tool call's arguments match the declared types — but
*choosing* clear, well-typed, unambiguous parameters in the first place
is still an authored design decision the schema itself can't make for
you.

```python
from pydantic import BaseModel

class BadArgs(BaseModel):
    d: str
    flag: str

class GoodArgs(BaseModel):
    date: str   # ISO 8601, e.g. "2026-09-23"
    include_archived: bool
```

`BadArgs` technically has a schema, generated the same way
[Module 1's `AgentConfig` example did](/01-llm-foundations/10-structured-output-and-tool-calling/03-from-a-pydantic-model-to-a-schema/#generating-the-schema-directly-from-a-model-you-already-know)
— but `d` gives the model no signal about expected format, and
`flag: str` invites something like `"yes"` or `"true"` instead of an
actual boolean, a genuinely ambiguous choice the schema itself never
rules out. `GoodArgs` uses a real `bool` (letting constrained decoding
do its actual job) and a name plus comment clarifying the expected date
format — the same information a well-written docstring carries, now
living directly on the parameter.

</Subsection>

<Subsection title="A comment never reaches the model — a Field description does" variant="b">

There's a catch in `GoodArgs`: the `# ISO 8601` comment is invisible to
the model. Comments aren't part of the schema, and the schema is all the
model gets. To put that information where the model will actually see
it, use
[`Field(description=...)`, the same tool Module 0 used to fill in FastAPI's automatic docs](/00-python-essentials/09-building-apis-with-fastapi/06-automatic-docs/#what-ends-up-in-the-docs-and-where-it-comes-from):

<LiveDemo client:load code={`import json
from pydantic import BaseModel, Field

class ScheduleMaintenanceArgs(BaseModel):
    agent_name: str = Field(description="Exact registered name of the agent, e.g. 'research_agent'.")
    date: str = Field(description="Day to run maintenance, ISO 8601 format: YYYY-MM-DD.")

print(json.dumps(ScheduleMaintenanceArgs.model_json_schema()["properties"], indent=2))`} />

Each description lands inside that parameter's entry in the schema,
right next to its type. That's the per-parameter version of the
description checklist from the previous concept: what the value means,
plus any format or unit it has to follow.

</Subsection>

<Subsection title="Allowed values: Literal instead of a free-form string" variant="a">

Some parameters only have a few valid values. An agent's status might be
`"active"`, `"paused"` or `"retired"` and nothing else. Typing it as
`str` lets the model send `"disabled"`, `"Paused"` or `"on hold"`, all
valid strings. `Literal` from Python's `typing` module says exactly which
values are allowed: `Literal["active", "paused", "retired"]` means "one of
these three strings, spelled exactly like this":

<LiveDemo client:load code={`from typing import Literal
from pydantic import BaseModel, Field, ValidationError

class SetAgentStatusArgs(BaseModel):
    agent_name: str = Field(description="Exact registered name of the agent.")
    status: Literal["active", "paused", "retired"] = Field(description="The agent's new status.")

print(SetAgentStatusArgs.model_json_schema()["properties"]["status"])

try:
    SetAgentStatusArgs(agent_name="research_agent", status="disabled")
except ValidationError as e:
    print(e)`} />

The schema turns the `Literal` into an `"enum"`: a list of the only
allowed values. So the model sees the options up front, and constrained
decoding can enforce them while generating. Pydantic also rejects
anything else when it validates, as the
[`ValidationError` from Module 0](/00-python-essentials/05-typed-data-models/04-pydantic-fundamentals/#validation-actually-happens-now)
shows.

</Subsection>

<Subsection title="Required vs. optional, and names that carry units" variant="b">

A parameter with a default value is **optional**: the model can leave it
out and the default is used. A parameter without one is **required**.
The schema records the difference in its `"required"` list, so the model
knows exactly what it must provide:

<LiveDemo client:load code={`from pydantic import BaseModel, Field

class RunHealthCheckArgs(BaseModel):
    agent_name: str = Field(description="Exact registered name of the agent.")
    timeout_seconds: int = Field(default=30, description="Give up after this many seconds.")
    verbose: bool = Field(default=False, description="Include per-check details in the result.")
    notes: str | None = Field(default=None, description="Optional free-text note to attach to the check.")

schema = RunHealthCheckArgs.model_json_schema()
print("required:", schema["required"])
for name, prop in schema["properties"].items():
    print(f"{name}: default={prop.get('default', '(none -- required)')}")

print(RunHealthCheckArgs(agent_name="research_agent"))`} />

Only `agent_name` is required. Everything else has a sensible default, so
the model can call the tool with just a name. Two details:

- `str | None` reads as "a string, or `None`". Use it when "not given" is
  a real, meaningful state, as with `notes` here.
- `timeout_seconds`, not `timeout`. A bare `timeout=30` could mean
  seconds or milliseconds, and the model has to guess. When a number has
  a unit, put the unit in the name, where the model can't miss it.

</Subsection>

<Subsection title="Don't hide JSON inside a string parameter" variant="a">

A tempting shortcut is one catch-all parameter that takes a JSON string:

<LiveDemo client:load code={`from pydantic import BaseModel, Field

class SearchAgentsBadArgs(BaseModel):
    filters: str = Field(description='JSON object of filters, e.g. {"model": "claude-haiku", "status": "paused"}')

print(SearchAgentsBadArgs.model_json_schema()["properties"]["filters"]["type"])
print(SearchAgentsBadArgs(filters='{"model": "claude-haiku", "stauts": paused}'))`} />

To the schema, `filters` is just a string, so any string passes. The one
above has a misspelled key (`stauts`) and isn't even valid JSON
(`paused` has no quotes), and it's accepted anyway. The model also has to
produce JSON *inside* a JSON string, with every inner quote escaped,
which is harder to get right than plain arguments. Give each filter its
own typed parameter instead (`model: str`, `status: Literal[...]`), so
the schema can check each one. When parameters naturally group together,
the next lesson shows how to use a nested model instead of a string.

</Subsection>
