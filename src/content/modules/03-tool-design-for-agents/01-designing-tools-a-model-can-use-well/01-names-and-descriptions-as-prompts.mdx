A tool's name and description aren't documentation for a future developer
reading the code —
[they're the exact text the model sees when deciding whether and how to call a tool](/01-llm-foundations/10-structured-output-and-tool-calling/04-tool-calling/#the-model-doesn-t-call-anything-it-produces-structured-data).
Writing a vague name or description isn't a stylistic shortcut; it's the
same category of mistake as
[a vague prompt from Module 2](/02-the-agent-loop/02-prompting-fundamentals/01-specificity-and-clear-instructions/#the-pain-a-vague-instruction-leaves-too-much-to-guess),
just now shaping a tool-selection decision instead of a written response.

<Subsection title="What the model actually receives" variant="a">

When you give a model a tool, what it receives is a small bundle of text:
the tool's **name**, its **description**, and a **JSON schema** for its
arguments. Here's that bundle built from ordinary Python: the name comes
from
[the function's `__name__`](/00-python-essentials/03-functions-and-reuse/02-args-and-kwargs/#why-this-matters-for-agent-code-forwarding-calls),
the description from
[its docstring](/00-python-essentials/03-functions-and-reuse/01-function-fundamentals/#docstrings)
(`__doc__`), and the schema from
[a Pydantic model's `.model_json_schema()`](/01-llm-foundations/10-structured-output-and-tool-calling/03-from-a-pydantic-model-to-a-schema/#generating-the-schema-directly-from-a-model-you-already-know):

<LiveDemo client:load code={`import json
from pydantic import BaseModel

class GetUserProfileArgs(BaseModel):
    user_id: str

def get_user_profile(user_id: str) -> dict:
    """Retrieve a user's profile (name, email, account status) by their
    unique user ID. Use this when you need account details for a specific,
    already-identified user -- not for searching by name."""
    ...

tool_definition = {
    "name": get_user_profile.__name__,
    "description": get_user_profile.__doc__,
    "input_schema": GetUserProfileArgs.model_json_schema(),
}
print(json.dumps(tool_definition, indent=2))`} />

(`indent=2` only makes `json.dumps` print the JSON across several
indented lines so it's easier to read.) This printout *is* the model's
input. The model never sees the function's body, only this text. If the
description is vague, there's nothing else for the model to go on. The
`\n` characters and the spaces after them are the docstring's line breaks
and indentation, carried along as-is; the next lesson builds a helper
that tidies them up.

</Subsection>

<Subsection title="The pain: a name and description that don't actually distinguish intent" variant="b">

```python
def get_data(id: str) -> dict:
    """Gets data."""
    ...
```

Nothing here tells the model *what kind* of data, *what* `id` actually
identifies, or when this tool is even the right one among several
similarly-vague options. A model choosing between this and a
similarly-underspecified second tool has no real basis to pick
correctly — not because it reasoned poorly, but because the tool never
gave it enough to reason *with*.

</Subsection>

<Subsection title="The fix: specific enough to actually disambiguate" variant="a">

```python
def get_user_profile(user_id: str) -> dict:
    """
    Retrieve a user's profile (name, email, account status) by their
    unique user ID. Use this when you need account details for a
    specific, already-identified user — not for searching by name.
    """
    ...
```

The description now does real work: it states exactly what's returned,
what `user_id` means, and — importantly — an explicit boundary
("not for searching by name") ruling out a plausible misuse before it
happens. This is
[the same always/never constraint pattern from Module 2's system-prompt design](/02-the-agent-loop/03-the-system-prompt-as-agent-design/02-role-persona-and-behavioral-constraints/#role-and-explicit-behavioral-constraints),
applied at the individual-tool level rather than the whole agent's
behavior.

</Subsection>

<Subsection title="Two tools that overlap" variant="b">

The real test comes when a model has several tools to choose from.
Here's the menu a model would see for two user tools with vague
descriptions, next to a request it has to handle:

<LiveDemo client:load code={`def get_user_profile(user_id: str) -> dict:
    """Gets user info."""
    ...

def search_users(name: str) -> list:
    """Finds users."""
    ...

def show_tool_menu(tools: list) -> None:
    for tool in tools:
        print(f"- {tool.__name__}: {tool.__doc__}")

print("Request: What's Dana Reyes's email address?")
show_tool_menu([get_user_profile, search_users])`} />

Both descriptions fit the request. "Gets user info" sounds like it
returns an email. "Finds users" sounds like it looks someone up. The
model has a name, not an ID, so the right move is `search_users` first
and then `get_user_profile`, but nothing in the menu says so. A
plausible wrong move is to call `get_user_profile` with
`user_id="Dana Reyes"`. Now the same two tools, with descriptions that
split the job between them:

<LiveDemo client:load code={`def get_user_profile(user_id: str) -> dict:
    """Returns one user's profile (name, email, account status) as a dict.
    Use when you already have the user's ID. Not for finding a user by name -- use search_users for that."""
    ...

def search_users(name: str) -> list:
    """Returns a list of {user_id, name} matches for a full or partial name.
    Use when you only know a name. Not for reading profile details -- pass a user_id to get_user_profile."""
    ...

def show_tool_menu(tools: list) -> None:
    for tool in tools:
        print(f"- {tool.__name__}: {tool.__doc__}")

print("Request: What's Dana Reyes's email address?")
show_tool_menu([get_user_profile, search_users])`} />

Each description now says what the tool returns and when to use it, and
its "not for" line names the other tool. The two descriptions no longer
compete for the same request: they describe two steps of one job,
`search_users` to get the ID, then `get_user_profile` to read the email.

</Subsection>

<Subsection title="What a description should say" variant="a">

A checklist for every tool description:

- **What it does**, in plain words: "Retrieve a user's profile", not
  "Gets data".
- **When to use it**: the situation it's meant for ("use when you
  already have the user's ID").
- **When not to use it**: the plausible misuse, ideally naming the tool
  to use instead ("not for finding a user by name — use `search_users`").
- **What it returns**: the shape and fields ("a dict with name, email,
  account status"), so the model knows what it will get back before it
  calls.
- **Units and formats**: anything the model has to get exactly right,
  like "seconds", "ISO 8601 date (YYYY-MM-DD)" or "case-sensitive".

</Subsection>
