<Subsection title="A real usability tradeoff, not a purely technical one" variant="a">

```python
def get_user_profile(user_id: str) -> dict:
    """Retrieve one user's profile by their user ID."""
    ...

def run_sql(query: str) -> list:
    """Run an arbitrary SQL query against the database."""
    ...
```

`get_user_profile` is **narrow**: it does exactly one thing, and the
model has very little room to call it wrong — a `user_id` is either
right or it isn't. `run_sql` is **broad**: genuinely more flexible (it
can answer questions no narrow tool anticipated), but that flexibility
means the model has to correctly construct an entire query itself,
leaving far more room for a subtly wrong — or badly-scoped — call than a
narrow tool ever could.

</Subsection>

<Subsection title="The real tradeoff, stated plainly" variant="b">

Narrow tools are easier for a model to use *correctly*, at the cost of
covering only what was anticipated in advance. Broad tools cover far
more ground, at the cost of asking the model to get something more
complex right on every single call. This concept is scoped strictly to
that usability question — the same tradeoff has a real *security*
dimension too (what a broad tool like `run_sql` could do if misused),
covered properly in a later lesson on designing for least privilege.

</Subsection>

<Subsection title="The middle ground: bounded, parameterized tools" variant="a">

The choice isn't only between the two extremes. Take the question "which
Haiku agents are paused?" `get_agent_config(agent_name)` can't answer it
unless the model already knows every agent's name. `run_sql(query)` can,
but only if the model writes a correct query. In between sits a tool
that takes a few typed parameters and does one bounded job:

<LiveDemo client:load code={`REGISTRY = {
    "research_agent": {"model": "claude-sonnet", "status": "active"},
    "support_agent": {"model": "claude-haiku", "status": "paused"},
    "billing_agent": {"model": "claude-haiku", "status": "active"},
    "triage_agent": {"model": "claude-haiku", "status": "paused"},
}

def search_agents(model: str, status: str) -> list:
    """Find registered agents by model and status.

    Returns a list of matching agent names (possibly empty).
    Use when you need every agent matching a model and a status.
    Not for looking up one agent's full configuration -- use get_agent_config for that.
    """
    return [name for name, info in REGISTRY.items() if info["model"] == model and info["status"] == status]

print(search_agents("claude-haiku", "paused"))`} />

`search_agents` answers a whole family of questions ("which Sonnet agents
are active?", "which Haiku agents are retired?") with two simple
arguments. It can't do anything outside that family, and that's the
point: the model only has to pick a model and a status, not write a
query. In a real tool, `status` would be a `Literal` of the allowed
values, exactly as in
[the parameter-design concept](/03-tool-design-for-agents/01-designing-tools-a-model-can-use-well/02-parameter-design/#allowed-values-literal-instead-of-a-free-form-string).

</Subsection>

<Subsection title="Composite tools: one call for a common sequence" variant="b">

Granularity also decides how many loop steps a task takes. Copying an
agent with narrow tools takes two calls: read the source agent's
configuration, then create the new one. A **composite** tool,
`clone_agent`, does both in one call. Below, the same loop runs each
version. The fake client is scripted to take each design's shortest
correct path, and a small subclass counts how many messages the loop
actually sends:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`REGISTRY = {"research_agent": {"model": "claude-sonnet", "status": "active"}}

def get_agent_config(agent_name: str) -> str:
    return str(REGISTRY[agent_name])

def create_agent(agent_name: str, model: str, status: str) -> str:
    REGISTRY[agent_name] = {"model": model, "status": status}
    return f"created {agent_name}"

def clone_agent(source_name: str, new_name: str) -> str:
    REGISTRY[new_name] = dict(REGISTRY[source_name])
    return f"cloned {source_name} to {new_name}"

TOOLS = {"get_agent_config": get_agent_config, "create_agent": create_agent, "clone_agent": clone_agent}

class CountingClient(FakeLLMClient):
    def __init__(self, scripted_responses: list):
        super().__init__(scripted_responses)
        self.messages_sent = 0

    def create(self, messages: list) -> FakeResponse:
        self.messages_sent += len(messages)
        return super().create(messages)

def run_agent(client, user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]
    while True:
        response = client.create(messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        tool_calls = [block for block in response.content if block.type == "tool_use"]
        if not tool_calls:
            return "".join(block.text for block in response.content if block.type == "text")
        results = [{"type": "tool_result", "tool_use_id": call.id, "content": TOOLS[call.name](**call.input)} for call in tool_calls]
        messages.append({"role": "user", "content": results})

narrow = CountingClient(scripted_responses=[
    [ToolUseBlock(name="get_agent_config", input={"agent_name": "research_agent"})],
    [ToolUseBlock(name="create_agent", input={"agent_name": "research_agent_v2", "model": "claude-sonnet", "status": "active"})],
    [TextBlock(text="Created research_agent_v2 as a copy of research_agent.")],
])
composite = CountingClient(scripted_responses=[
    [ToolUseBlock(name="clone_agent", input={"source_name": "research_agent", "new_name": "research_agent_v3"})],
    [TextBlock(text="Created research_agent_v3 as a copy of research_agent.")],
])

for label, client in [("two narrow tools", narrow), ("one composite tool", composite)]:
    run_agent(client, "Make a copy of research_agent.")
    print(f"{label}: {client.call_count} model calls, {client.messages_sent} messages sent in total")
print(REGISTRY)`} />

Every extra tool call is another model call, and every model call resends
the whole conversation so far. So the composite version saves more than
one step: it sends 4 messages in total instead of 9, which means fewer
input tokens and less latency. It also removes a chance for error, since
the model never has to copy `"claude-sonnet"` from one result into the
next call by hand. Composite tools make sense for sequences that are
common and always done the same way. (`dict(REGISTRY[source_name])`
makes a *copy* of the source's config dict, so later changes to the
clone don't also change the original.)

</Subsection>

<Subsection title="The cost of going too narrow" variant="a">

Narrow tools aren't free either. Every tool you add is one more name,
description and schema in the model's input, and one more option to
choose between on every call. A model with forty tiny, overlapping tools
has a harder selection problem than one with eight well-bounded ones, no
matter how good each description is. How many tools is too many, and
what to do about it, is covered in a later lesson in this module. For
now: prefer a few tools that each cover a clear, bounded job over
either one do-everything tool or dozens of single-purpose ones.

</Subsection>
