    """Compare each planned change with the state read back afterwards. current maps each agent to its
    record as read now; an agent missing from it is treated as changed by someone else."""
    result = {"applied": [], "not_applied": [], "overwritten": []}
    for change in plan:
        now = current.get(change["agent"], {}).get(change["field"])
        if now == change["after"]:
            result["applied"].append(change["agent"])
        elif now == change["before"]:
            result["not_applied"].append(change["agent"])
        else:

    return {key: sorted(agents) for key, agents in result.items()}

<Subsection title="A reply isn't proof" variant="a">

When a write tool replies "ok", it's tempting to count the action as done.
The reply says what the service claims, and several ordinary things can make
that claim differ from what actually happened:

- **The write is accepted but applied later.** Many stores acknowledge a
  write before every copy of the data reflects it. Amazon DynamoDB's
  [documentation on read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html)
  says its default reads may not reflect a recently completed write, and that
  repeating the read after a short time should return the latest data.
- **The reply is lost, not the write.** A timeout says no reply arrived, not
  that nothing happened, the point
  [Module 3 made](/03-tool-design-for-agents/04-tools-that-call-the-outside-world/02-which-failures-to-retry-and-how/#retrying-a-write-can-do-it-twice)
  about retrying writes.
- **The tool fails silently.** It reports success and did something else, or
  nothing: the silent failures
  [Lesson 3 checked results for](/06-reliability/03-checks-in-the-loop/02-checking-a-tool-result/).

The fix is the one
[Module 2's goal-state check](/02-the-agent-loop/06-termination-failure-and-control/04-goal-state-termination-checks/)
used to decide when a task was done: look at the real state. Here it's
applied to each action that matters: after the write, read the record back
and compare it with what the write was meant to produce. Anthropic gives the
same advice for a model driving a screen. Its
[computer-use documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
warns that Claude "sometimes assumes outcomes of its actions without
explicitly checking their results", and suggests prompting it to confirm
each step worked before moving on to the next.

</Subsection>

<Subsection title={'An "ok" that hasn\'t happened yet'} variant="b">

<LiveDemo client:load code={DELAYED_DEMO} />

*(An in-memory stand-in that applies writes one step late.)*

An agent that reported success on the reply alone would have been right
here only by luck of timing. A read straight after the write shows the old
value, so the read-back needs to allow for delay: read again a few times, a
short wait apart, and give up after a limit, which is
[Module 2's retry with backoff](/02-the-agent-loop/06-termination-failure-and-control/06-timeouts-retry-and-graceful-give-up/)
applied to reads. Where the store offers it, a strongly consistent read,
such as DynamoDB's `ConsistentRead` option, removes the wait, at a higher cost
per read.

</Subsection>

<Subsection title="A failure that has already happened" variant="a">

The opposite case is just as common:

<LiveDemo client:load setupCode={DELAYED_DEMO} code={TIMEOUT_DEMO} />

*(`Registry` from the demo above is already loaded here.)*

The call raised an error, and the change was made anyway. An agent that
trusted the error would retry, and for a write without an idempotency key,
that's the double write Module 3 warned about. Reading back first shows
there's nothing to retry. So a read-back is useful on both sides: it catches
a success that isn't one, and a failure that isn't one either.

</Subsection>

<Subsection title="Comparing what was planned with what's there" variant="b">

With a plan from the previous concept's dry run, the read-back has something
precise to compare with: for each change, the value before and the value
it should now hold. Each record read back is in one of three states:

- **Applied:** it holds the planned value.
- **Not applied:** it still holds the old value. Wait and read again, or
  retry if the write is safe to repeat.
- **Changed by someone else:** it holds neither. Something else wrote to
  it, and the agent shouldn't overwrite that without checking, as with the
  stale plan in the previous concept.

</Subsection>
