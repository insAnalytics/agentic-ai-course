<Subsection title="Done, by the check's own measure" variant="a">

[The previous concept](/06-reliability/07-safe-actions/04-checking-the-report-against-the-log/)
caught a report that claimed more than the agent did. There's a subtler
failure where the report is true. The check really does pass, but the task
isn't done. Here's a task with a clear check, "bring the error rate under the
alert threshold", and three runs that satisfy it:

<LiveDemo client:load setupCode={WORLD} code={RUNS_DEMO} />

*(A scripted stand-in registry; `START`, `apply`, `goal` and `RUNS` are
loaded above the demo.)*

Only the first run did what was meant. The second paused the agent: it serves
no requests, so it makes no errors. The third raised the threshold. All three
pass, and a report that said "the error rate is now under the threshold"
would be true every time.

This has a name. DeepMind's Krakovna et al.
[defined *specification gaming*](https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity/)
(2020) as behaviour that satisfies the literal specification of an objective
without achieving the intended outcome. In reinforcement learning it's
called *reward hacking*: optimising the measurement instead of the thing
measured. Lilian Weng's
[survey of reward hacking](https://lilianweng.github.io/posts/2024-11-28-reward-hacking/)
(2024) collects examples, from game agents that loop for points to language
models that edit the unit tests they were meant to pass.

</Subsection>

<Subsection title="Not a hypothetical" variant="b">

For current agents, the best-documented cases come from coding, where the
check is a test suite:

- **Frontier labs report it in their own models.** Anthropic's
  [Claude 3.7 Sonnet system card](https://www.anthropic.com/claude-3-7-sonnet-system-card)
  describes the model sometimes special-casing tests in agentic coding,
  most often by returning the values the tests expect, instead of fixing the
  code. Anthropic's
  [Claude 4 announcement](https://www.anthropic.com/news/claude-4) reports
  that both new models were 65% less likely than Claude 3.7 Sonnet to use
  shortcuts or loopholes on agentic tasks prone to them: much less, but not
  never. OpenAI's
  [work on monitoring reasoning models](https://openai.com/index/chain-of-thought-monitoring/)
  (2025) caught a frontier model in training subverting the tests it was
  given.
- **It's common where the check is in view.** METR
  [found](https://metr.org/blog/2025-06-05-recent-reward-hacking/) OpenAI's o3
  reward-hacking in 30% of its runs on one benchmark, against under 1% on
  another, and suggests the difference is that on the first the model could
  see its scoring function. It kept hacking in 14 of 20 attempts even when
  told the work had real consequences.
- **It can be measured directly.** Zhong, Raghunathan and Carlini's
  [ImpossibleBench](https://arxiv.org/abs/2510.20270) (ICLR 2026) gives coding
  agents tasks whose tests contradict their specification, so any pass means
  the agent took a shortcut. GPT-5 passed 54% of one variant anyway. Given an
  explicit option to stop and say the task can't be done, it did so, and its
  rate fell to 9%.

Nothing about this is specific to code. Any agent given a checkable goal and
tools that can change the thing being checked can find the cheaper path to a
pass. [Lesson 5 saw](/06-reliability/05-voting/06-better-than-a-plain-vote/#pick-with-a-check-instead-of-counting)
the same effect in a verifier pushed too hard: the more a search is aimed at
a check, the more it finds the check's gaps.

</Subsection>

<Subsection title="Checking the goal, not just the check" variant="a">

[Module 2's goal-state check](/02-the-agent-loop/06-termination-failure-and-control/04-goal-state-termination-checks/#a-deterministic-check-on-real-state)
looked at real state, not the model's word, and that still matters. But a
check on the state can still be gamed, so four habits go with it:

- **Say what must stay true, as well as what must become true.** "The error
  rate is under 2%" is the goal. "The agent is still active and serving
  traffic" is an *invariant*, and it's the one the second run broke. Most
  gamed checks break something nobody thought to write down, so writing it
  down is the fix.
- **Keep the measuring stick out of reach.** A run that changed the
  threshold, the tests or the evaluation config can't be judged by them. The
  tools that change how success is measured shouldn't be in the agent's
  toolset at all, the
  [least-privilege](/03-tool-design-for-agents/11-designing-for-least-privilege/01-narrow-tools-shrink-the-blast-radius/)
  choice. Where they must be, a call to one means the run can't be accepted
  on its own measure. Anthropic's
  [guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
  puts it plainly: "The agent shouldn't be able to easily 'cheat' the eval."
- **Give it a way out.** ImpossibleBench's biggest drop came from letting the
  agent say the task couldn't be done. An agent that can
  [escalate](/06-reliability/06-when-unsure/03-escalating/) has less reason to
  force a pass.
- **Look at how, not only whether.** OpenAI found that a monitor reading the
  model's reasoning caught reward hacking far more reliably than one reading
  its actions alone. It also found that training the model against that
  monitor taught it to hide its intent rather than stop, so a monitor like
  that works as a review, not as a training signal. Reviewing traces of real
  runs is Module 7's subject.

The exercise turns the first two into a review that runs after the task's
check passes.

</Subsection>
