export const REFERENCE = String.raw`def run_saga(steps: list[tuple]) -> dict:
    """Run (name, action, compensate) steps in order. If an action raises, run the compensations of
    the steps that completed, newest first; a compensation that raises is recorded, and the rest still run."""
    completed = []
    for name, action, compensate in steps:
        try:
            action()
        except Exception:
            compensated, compensation_failed = [], []
            for done_name, done_compensate in reversed(completed):
                try:
                    done_compensate()
                    compensated.append(done_name)
                except Exception:
                    compensation_failed.append(done_name)
            return {"completed": [n for n, _ in completed], "failed": name,
                    "compensated": compensated, "compensation_failed": compensation_failed}
        completed.append((name, compensate))
    return {"completed": [n for n, _ in completed], "failed": None, "compensated": [], "compensation_failed": []}

<Subsection title="Half a change can be worse than none" variant="a">

Many real actions take more than one step. Moving `research_agent` onto
`claude-opus` means first moving it to the priority tier, the only tier that
allows that model, and then changing the model. If the second step fails,
the first has already happened:

The agent is now on the priority tier, which its owner's budget holder has
to approve and pay for, and still on the old model. Nothing crashed, and
the registry is in a state nobody asked for. Reading back, from the previous
concept, would show this; something still has to put it right.

</Subsection>

<Subsection title="Sagas: every step comes with its undo" variant="b">

This problem is decades older than agents. Garcia-Molina and Salem's paper
[*Sagas*](https://dl.acm.org/doi/10.1145/38713.38742) (SIGMOD 1987)
described long-running operations written as a sequence of smaller steps,
where the system guarantees that either every step completes, or
*compensating* steps run to amend the partial execution. Each step is paired
with a compensation that undoes its effect: here, moving the agent back to
the standard tier. When a step fails, the compensations of the steps that
completed run in reverse order, newest first, since later steps may depend
on earlier ones.

The idea is now a standard pattern for work that spans several services.
Microsoft's [Saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)
describes it, and AWS's
[Well-Architected guidance](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)
recommends it to "roll back previous operations in case a later operation
of the same transaction fails". Four details from it matter for agents:

- **A compensation undoes the effect, not the history.** The registry's
  change log will show the tier going up and back down. That's correct: the
  compensation restores what the business cares about, not the exact
  earlier state.
- **Some steps can only be corrected, not undone.** A sent email can't be
  unsent; its compensation is a follow-up that corrects it. Steps like that
  are best placed last, after everything that can still fail. Microsoft's
  saga guidance calls such a step the *pivot*, the point of no return, and
  puts only steps that can be retried until they succeed after it. They're
  also exactly where
  [Lesson 2's risk](/06-reliability/02-reliability-tradeoffs/04-spend-reliability-where-the-risk-is/)
  and the approval gate belong.
- **A compensation is itself a write, and can fail.** It needs the same care
  as any other: an
  [idempotency key](/03-tool-design-for-agents/04-tools-that-call-the-outside-world/02-which-failures-to-retry-and-how/#retrying-a-write-can-do-it-twice)
  so it can be retried safely, a read-back to confirm it worked, and, if it
  still fails, an escalation to a person with the state it's left behind, as
  [the previous lesson](/06-reliability/06-when-unsure/03-escalating/)
  described. Microsoft's
  [Compensating Transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)
  gives the same advice: make each step "an idempotent command", and expect
  that "sometimes manual intervention is the only way to recover".
- **A step that failed may still have taken effect.** The textbook saga
  compensates only the steps that completed, which assumes a step that
  raised an error changed nothing. With a remote service, that isn't
  guaranteed:
  [the previous concept's timeout](/06-reliability/07-safe-actions/02-reading-the-result-back/#a-failure-that-has-already-happened)
  was a failure whose write had landed. When a step's outcome is unknown,
  read back what it would have changed before deciding. Otherwise, run its
  compensation too, written so it's safe to run even if the step never
  happened, for example "set the tier to standard", not "lower the tier by
  one".

</Subsection>

<Subsection title="When the agent itself crashes" variant="a">

A saga run in memory has one more weakness: the list of which steps
completed lives in the process. If the process dies between steps, or partway
through compensating, that list is gone, and nothing knows what's left to
undo.

Durable execution is the standard answer. Workflow engines such as
[Temporal](https://docs.temporal.io/evaluate/understanding-temporal) record
every step of a workflow in a durable event history; if the process running
it crashes, another process rebuilds the workflow's state from that history
and resumes where it stopped. Running an agent's multi-step actions this way
makes a saga survive a crash. The infrastructure for that belongs to
Module 10; the design idea, that progress has to be written down somewhere
that outlives the process, is the part to take from here.

</Subsection>
