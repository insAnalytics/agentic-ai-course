    properties = {"untrusted" in touched, "private" in touched,

<Subsection title="From what was read to what's allowed" variant="a">

The guard from
[the previous concept](/06-reliability/09-restricting-after-reading/01-tracking-what-the-session-has-read/)
knows what the session has touched. This concept uses it: before each tool
call, at the point
[Lesson 3 called the check on the call](/06-reliability/03-checks-in-the-loop/01-where-a-check-can-sit/#four-points-four-different-views),
decide whether the session may still make it. There are three answers:

- **Allow** the call.
- **Approve:** a person confirms it first, through the approval gate
  [Module 3 built](/03-tool-design-for-agents/11-designing-for-least-privilege/02-separate-reads-from-writes-and-gate-the-writes/).
  This lesson doesn't change that gate; it decides when the session needs it.
- **Deny** the call outright.

</Subsection>

<Subsection title="The Rule of Two, and where it isn't enough" variant="b">

Meta's Rule of Two, applied literally, only steps in when a call would give
the session all three properties at once: untrusted input, private data, and
a way to change state or send data out. (Meta then asks for a person's
approval; the demo simply denies.) Here's what that lets through:

<LiveDemo client:load code={RULE_OF_TWO_DEMO} />

The second call is blocked, as it should be. The first isn't, and Simon
Willison, whose lethal trifecta the Rule of Two builds on,
[pointed out the problem](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/):
untrusted input combined with the ability to change state can do harm even
without any private data. An email that says "move research_agent to
claude-opus" needs nothing private to cause damage; it only needs the agent to
be allowed to act on what it read.

So the rule this lesson uses is stricter than two-of-three:

| The session has read untrusted content, and the tool... | Decision |
|---|---|
| only reads, and nothing it's given leaves the system | allow |
| changes state inside the system | approve |
| sends data out, and the session hasn't touched private data | approve |
| sends data out, and the session has touched private data | deny |
| isn't declared at all | deny |

In a session that hasn't read anything untrusted, this guard allows every
declared tool; any gate Module 3 already put on writes still applies on top.

"Only reads" is narrower than it sounds. A read is safe here only if nothing
the model puts in its arguments reaches anyone outside. Fetching a URL, running
a web search or calling a third-party API sends the arguments out, so an
injected instruction can hide private data in them. Those tools are labelled
`external` as well as `untrusted`, as the previous concept did with
`fetch_url`, and the table then treats them as sending data out. The final
answer is an outgoing channel too. If the interface renders a markdown image,
the user's browser requests its URL as soon as the answer is shown, and a
link sends its URL out with one click;
[Module 5 showed a real attack that worked this way](/05-rag-systems/13-permissions/04-defences-by-design/#the-answer-is-a-way-out-too).
So an answer from a session that has read untrusted text shouldn't be rendered
with live links or images to arbitrary addresses.

Denying the last combination, rather than asking a person, is a design
choice worth explaining. Approving an outgoing message after the session has
read both untrusted text and private data means checking every byte of it for
something that shouldn't leave, which is a job people do badly.
[CaMeL's](https://arxiv.org/abs/2503.18813) authors warn that frequent
prompts leave users "desensitized to security prompts", so that they "may
inadvertently approve malicious actions". The safer answer is to refuse, and
do the sending from a fresh session that hasn't read the untrusted content.
Some systems choose approval instead, as Meta's Rule of Two does for this
case; what matters is that the choice is made on purpose.

</Subsection>

<Subsection title="What the decision must never read" variant="a">

The model writes a tool call's arguments, and a model that has read a planted
instruction may write whatever the instruction said: `"approved": True`,
`"role": "admin"`. So the decision is made from two things only: the tool's
declared labels and what the session has touched. The arguments aren't
consulted at all, and neither is anything a tool returned. The exercise's
tests try both.

This is the in-code enforcement that Module 3's
[blast-radius](/03-tool-design-for-agents/10-the-tool-threat-model/04-thinking-in-terms-of-the-blast-radius/)
thinking calls for: however the model is steered, the set of things it can
do from this point on is fixed by code it can't write to.

</Subsection>
