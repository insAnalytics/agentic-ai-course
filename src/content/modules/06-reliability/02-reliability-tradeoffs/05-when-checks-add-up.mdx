<Subsection title="A run has to get past every check" variant="a">

[The previous concept](/06-reliability/02-reliability-tradeoffs/04-spend-reliability-where-the-risk-is/)
chose checks one step at a time. A run doesn't experience them one at a
time. A fine run only gets through if *every* check lets it through, so
false blocks compound the way
[Lesson 1's errors did](/06-reliability/01-per-step-reliability/01-small-errors-compound/):

<LiveDemo client:load code={STACK_DEMO} />

*(Arithmetic, assuming the checks' false blocks are independent.)*

A 2% false-block rate sounds harmless for one check. Five of them stop nearly
one fine run in ten, and a 1% check on every step of a twenty-step task stops
almost one in five. Working backwards gives the useful rule: set the
false-block limit for the whole run first, and divide it among the checks.
Keeping a twenty-step run under 5% leaves each step's check about 0.25%.
That's far stricter than any check looks like it needs on its own, and it's
a strong argument for checking the risky steps and not every step.

</Subsection>

<Subsection title="Most blocks can be false alarms" variant="b">

A check is described by two rates:
[what it catches, and what it wrongly blocks](/06-reliability/02-reliability-tradeoffs/01-four-things-every-technique-trades/#a-refusal-can-be-a-reliability-failure).
What a person reviewing its blocks experiences depends on a third number:
how often the thing it guards actually goes wrong.

<LiveDemo client:load code={BASE_RATE_DEMO} />

*(Arithmetic with a made-up check.)*

The same check, with the same two rates, goes from mostly right to mostly
wrong as mistakes get rarer. Where one step in a hundred is wrong, two of
every three blocks are false alarms. This is the base-rate effect, and it
turns up in measured checks too.
[Lesson 6's judges](/06-reliability/06-when-unsure/02-signals-the-agent-isnt-sure/#measuring-a-signal-on-your-own-cases)
caught 21 of 23 mistakes by reviewing verdicts under 0.9, but those 21 were
among 66 verdicts reviewed: about a third of the reviews found something.

So a check's report should include the share of its blocks that were
right, alongside the two rates. It's the number that decides whether people
trust the check, and it falls as the agent gets better. A check that was
worth its false alarms when the agent was wrong often can become mostly noise
once it rarely is.

</Subsection>

<Subsection title="Checks that fail together" variant="a">

Stacking checks is meant to work the other way for mistakes. If two checks
each miss 10% of problems, a mistake gets past both only 1% of the time. But
that multiplication assumes the checks miss *different* mistakes. The
questions that fool one model tend to fool another:

<LiveDemo client:load dataFiles={BOTH_DATA} setupCode={LOAD_RUNS} code={TOGETHER_DEMO} />

*(Real committed runs. `load_run` is Lesson 1's.)*

On this module's runs, the 2B and the 4B were both wrong on the same question
more than twice as often as independent mistakes would be. Six of the eight
questions the 4B ever misses are ones the 2B misses too. It's
[Lesson 1's clustering](/06-reliability/01-per-step-reliability/02-the-same-question-run-twice/#failures-cluster-on-particular-questions)
seen across models: some questions are hard for everything.

The research finds the same at scale. Kim et al.'s
[*Correlated Errors in Large Language Models*](https://arxiv.org/abs/2506.07962)
(ICML 2025) compared more than 350 models. On one leaderboard, when two
models were both wrong, they gave the same wrong answer 60% of the time.
Larger, more accurate models shared more of their errors, even across
providers. Goel et al.,
[*Great Models Think Alike and this Undermines AI Oversight*](https://arxiv.org/abs/2502.04313)
(ICML 2025), found model mistakes becoming more similar as models get more
capable. That's
[Module 2's shared blind spots](/02-the-agent-loop/09-reflection-and-self-critique/03-the-limits-shared-blind-spots/)
at the level of a whole system.

Two practical rules follow. Layers that work differently fail differently: a
check in code and a model judge share fewer blind spots than two model
judges from the same family. And a stack's miss rate can't be worked out
from its layers' miss rates; it has to be measured with the layers running
together, which is what
[Lesson 10](/06-reliability/10-layered-checks/03-what-each-layer-earns/)
does.

</Subsection>
