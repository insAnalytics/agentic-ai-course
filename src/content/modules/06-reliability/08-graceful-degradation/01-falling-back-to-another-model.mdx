<Subsection title="When retrying isn't enough" variant="a">

[Module 2](/02-the-agent-loop/06-termination-failure-and-control/06-timeouts-retry-and-graceful-give-up/)
taught the loop to retry a failing call with backoff and then give up with
a defined result, and
[Module 3](/03-tool-design-for-agents/04-tools-that-call-the-outside-world/02-which-failures-to-retry-and-how/)
taught which failures are worth retrying at all. Both assume the problem is
brief. Sometimes it isn't: a provider has an outage, or a model's rate limit
is exhausted for the hour.

Giving up cleanly is better than crashing, but the user still gets nothing.
If another model could have answered, the agent gave up too early.

<Subsection title="A fallback chain" variant="b">

A **fallback** is a second choice: when the primary model can't answer,
try the next one on a list, in priority order. It might be the same model
from another provider, a different model from the same provider, or a smaller
model that's always available. LLM gateways build this in. The open-source
gateway LiteLLM, for example,
[configures fallbacks](https://docs.litellm.ai/docs/proxy/reliability) as
a priority-ordered list of models per primary, and keeps separate lists for
particular kinds of error, such as a prompt too long for the model's context
window, since the right backup depends on what went wrong.

That last point is the one to design around. Whether falling back can help
depends on the error:

- **The provider is down or rate-limited:** another provider, or another
  model, may well be up. Fall back.
- **The prompt is too long for this model:** a model with a larger context
  window may take it. Fall back, to a model that can.
- **The request itself is wrong,** such as a malformed tool schema or an
  invalid parameter: every model would refuse it. Falling back only hides a
  bug and wastes calls. Raise it.

Sort errors by what they mean, not by their HTTP status alone. On the major
APIs a prompt that's too long also comes back as a 400 "invalid request",
the same status as a malformed schema, so it's the error's type or message
that tells them apart. And "every model would refuse it" is an assumption to
check. A parameter or schema feature one model supports may be rejected by
another, so a request can be wrong for one model and fine for the next.
Treat those as their own kind of error: fall back only to models known to
accept the request.

This is the same split as Module 3's retry rules, one level up: retry what
might succeed on a second try, fall back on what might succeed somewhere else,
and fix what would fail everywhere.

</Subsection>

<Subsection title="A fallback is a different model" variant="a">

Falling back keeps the agent answering, but not in the same way. A backup
model may be weaker, format its output differently, or follow instructions
less closely. Two habits follow:

- **Its answers pass the same checks.** The result checks from
  [Lesson 3](/06-reliability/03-checks-in-the-loop/02-checking-a-tool-result/)
  and the support checks from
  [Lesson 4](/06-reliability/04-verifying-claims/01-checking-each-claim/)
  apply to a backup's answer exactly as to the primary's. If anything, a
  weaker model's answers are the ones that most need them.
- **The record says which model answered.** When answers go wrong later,
  whether they came from the backup is the first thing to find out, and it's
  impossible to find out if nothing recorded it. Recording and tracing runs is
  Module 7's subject; recording which model answered is the minimum.

</Subsection>

<Subsection title="Falling back in the middle of a run" variant="b">

A fallback before the first model call is simple: send the same request
somewhere else. Partway through an agent's loop, it's harder, because the
conversation so far was written in the primary provider's format, and not all
of it carries over:

- **Some parts belong to one provider.** Anthropic's API returns signed
  thinking blocks, and its
  [documentation](https://platform.claude.com/docs/en/build-with-claude/thinking-tool-workflows)
  requires the assistant turn to be sent back exactly as received: rebuilding
  it, or filtering blocks out, is a 400 error. Another provider can't use
  those blocks at all, so falling back mid-run means translating the
  conversation, and the primary's reasoning is left behind.
- **A request valid for one model can be invalid for the next.** On Claude
  Opus 4.7 and later, setting `temperature` to a non-default value
  [returns a 400](https://platform.claude.com/docs/en/about-claude/model-deprecations),
  where older models accepted it. The same request, retried on the backup,
  fails for a reason the primary never had.
- **Prompts don't transfer perfectly.**
  [Lesson 1](/06-reliability/01-per-step-reliability/04-reliable-across-wordings/)
  showed one model's answers changing with the wording. A prompt tuned for
  one model is a different wording to the next.

So fallbacks work best at a turn boundary, with each model's prompt and
parameters kept in its own configuration, and with the backup's answers put
through the same checks.

</Subsection>

<Subsection title="A fallback that's never used" variant="a">

There's a less obvious risk in any backup path: it only runs when something
has already gone wrong. Jacob Gabrielson's
[*Avoiding fallback in distributed systems*](https://aws.amazon.com/builders-library/avoiding-fallback-in-distributed-systems/),
in the AWS Builders' Library, argues that fallback code is rarely exercised,
so it's rarely tested, and can make an outage worse when it finally runs.
Amazon almost never uses fallback, it says. Where a backup path is needed,
it runs it all the time alongside the main one, turning fallback into
failover.

For a fallback model, that means not waiting for an outage to find out
whether the backup still works: whether its model ID is still served, its
prompt still fits, and its answers still pass the checks. A small share of
real traffic sent to the backup all the time, or a regular test against it,
keeps it a path that's known to work, not one that's only assumed to.

</Subsection>
