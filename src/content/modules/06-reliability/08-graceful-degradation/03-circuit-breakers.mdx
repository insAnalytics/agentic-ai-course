    """Raised instead of calling a dependency the breaker has stopped calling."""


class CircuitBreaker:
    """Stop calling a failing dependency for a while. clock() returns the current time in seconds."""

    def __init__(self, threshold: int, reset_after: float, clock, trips_on: tuple = (Exception,)):
        self.threshold, self.reset_after, self.clock, self.trips_on = threshold, reset_after, clock, trips_on
        self.failures = 0
        self.opened_at = None

    @property
    def state(self) -> str:
        if self.opened_at is None:
            return "closed"
        return "half_open" if self.clock() - self.opened_at >= self.reset_after else "open"

    def call(self, fn):
        if self.state == "open":
            raise CircuitOpen(f"not calling: {self.failures} failures, retrying after {self.reset_after} s")
        try:
            result = fn()
        except self.trips_on:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = self.clock()
            raise
        self.failures = 0
        self.opened_at = None
        return result

<Subsection title="Every caller waits for the same timeout" variant="a">

When a dependency goes down, every request that needs it waits for its
timeout before failing. One slow failure is annoying; many of them at once,
each holding a request open, is how one broken service drags down
everything that calls it:

*(Simple arithmetic, not a measurement.)*

Retrying makes this worse, not better: each request's retries add more
waiting and more load on a service that's already struggling.

</Subsection>

<Subsection title="The circuit breaker" variant="b">

Martin Fowler's
[description of the pattern](https://martinfowler.com/bliki/CircuitBreaker.html),
which Michael Nygard popularised in his book *Release It!*, is short. Wrap
the call to the dependency in a breaker that counts failures. Once they
reach a threshold, the breaker *trips*: further calls fail at once, without
the dependency being called at all. After a set time, the breaker lets one
real call through as a trial; if it succeeds, the breaker resets, and if it
fails, the wait starts again.

That gives three states:

- **Closed:** calls pass through, and failures are counted. A success resets
  the count.
- **Open:** calls fail immediately, without reaching the dependency.
- **Half-open:** the wait is over, and the next call is a trial.

The version in the exercise is the simplest form. It lets any call through
while half-open, which is fine when calls arrive one at a time. With many at
once, a real breaker lets a set number of trial calls through and keeps
failing the rest fast until they come back. Production libraries such as
[Resilience4j](https://resilience4j.readme.io/docs/circuitbreaker) also
usually trip on the *rate* of failures over a recent window, not a count in
a row, and can count slow calls as failures too.

Two details from Fowler's description matter for agents:

- **Not every error should trip it.** A malformed request says nothing about
  whether the dependency is healthy. Only errors that do, timeouts, refused
  connections, server errors, should count. In the code here that's
  `trips_on=(ConnectionError, TimeoutError)`: Python's `TimeoutError`
  isn't a kind of `ConnectionError`, so it has to be listed too. It's the same distinction as
  the fallback rules in
  [the first concept](/06-reliability/08-graceful-degradation/01-falling-back-to-another-model/).
- **The caller still has to decide what to do.** An open breaker is a fast
  "no", not an answer. That's where the rest of this lesson comes in: fall
  back to another model if there is one, or give a partial answer that says
  what's missing.

For an agent, each model provider and each tool's backing service can have
its own breaker. When the health service's breaker is open, the agent
doesn't need to wait five seconds to learn the health figures are
unavailable; it knows at once, and can write the partial answer straight
away.

A breaker's state is also worth logging and watching: a breaker that keeps
tripping is an early warning about the dependency behind it, which is
Module 10's territory.

</Subsection>
