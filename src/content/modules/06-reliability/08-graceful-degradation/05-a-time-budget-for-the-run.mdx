HUNG = {"provider-a/large", "provider-b/large"}  # today, the first two never answer
now = [0.0]


def call(model: str, timeout: float) -> str:
    """A stand-in model call on a fake clock: a hung provider uses up the whole timeout, then fails."""
    if model in HUNG:
        now[0] += timeout
        raise TimeoutError(f"{model} didn't answer in {timeout:.0f} s")
    now[0] += 1.0
    return f"answer from {model}"


def call_with_deadline(models: list[str], timeout: float, deadline: float, min_useful: float = 2.0) -> dict:
    """Try each model in turn, but never past the run's deadline: each call gets at most the time that's left."""
    for model in models:
        remaining = deadline - now[0]
        if remaining < min_useful:
            return {"answer": None, "why": f"{remaining:.0f} s left, too little for another call", "at": now[0]}
        try:
            return {"answer": call(model, min(timeout, remaining)), "at": now[0]}
        except TimeoutError:
            continue
    return {"answer": None, "why": "every model timed out", "at": now[0]}

for timeout in (30, 10):
    now[0] = 0.0
    result = call_with_deadline(MODELS, timeout, deadline=45)
    print(f"45 s budget, {timeout} s per call: {result}")

<Subsection title="Slow is a failure too" variant="a">

The earlier concepts dealt with calls that fail. A call that succeeds after
twenty seconds can be just as bad for a user waiting on an agent, and slow
calls are more common than failed ones. Dean and Barroso's
[*The Tail at Scale*](https://research.google/pubs/the-tail-at-scale/)
(Communications of the ACM, 2013) showed why this matters more as work fans
out. If each of a hundred servers answers in 10 ms but takes a second one
time in a hundred, then 63% of requests that need all hundred take over a
second.

An agent's calls come one after another instead of all at once, but the
arithmetic is the same as
[Lesson 1's](/06-reliability/01-per-step-reliability/01-small-errors-compound/):
the more calls a run makes, the more likely it meets the slow one.

<LiveDemo client:load code={TAIL_DEMO} />

*(A simulated latency distribution, not a measurement of any provider.)*

A 1% chance of a slow call is invisible in a single call's median. At twenty
calls per run, it catches nearly one run in five, and the p99 of a whole run
is dominated by it. That's why a latency target for an agent has to be set
for the run and checked at the tail, not taken from one call's median.

</Subsection>

<Subsection title="Retries and fallbacks multiply time" variant="b">

Everything in this lesson so far spends time. A retry waits out a timeout
before trying again, and a fallback chain does it once per model.
Marc Brooker's
[*Timeouts, retries, and backoff with jitter*](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)
(AWS Builders' Library) calls retries "selfish": each one spends the
system's capacity on one request. Stacked across layers they multiply, so
three retries at each of five layers can send 243 times the load to the
bottom one. Time multiplies the same way.

The fix is a **deadline**: a time budget for the whole run, with each call
getting only what's left of it.

<LiveDemo client:load code={DEADLINE_DEMO} />

*(Scripted providers on a fake clock.)*

With 30-second timeouts, the budget runs out before the chain reaches the
provider that works. The deadline stops the run cleanly instead of letting it
wait for minutes, and what's left is
[a partial answer](/06-reliability/08-graceful-degradation/02-partial-answers/)
that says what's missing. With 10-second timeouts, the same budget reaches
the working provider. The per-call timeout should come from the run's budget
and the length of the chain, not the other way round. And a circuit breaker
from [the previous concept](/06-reliability/08-graceful-degradation/03-circuit-breakers/)
would have skipped the hung providers entirely after their first failures.

</Subsection>

<Subsection title="Hedged requests" variant="a">

A deadline limits the damage from a slow call. A **hedged request** avoids
much of it. Send the call, and if it hasn't answered by the time most calls
have, send a second copy and use whichever answers first. Dean and Barroso
report the result in Google's BigTable: hedging after 10 ms cut the
99.9th-percentile latency for a 1,000-key read from 1,800 ms to 74 ms,
while sending only 2% more requests. Waiting until the 95th percentile before
hedging keeps the extra load to about 5%.

<LiveDemo client:load setupCode={HELPERS} code={HEDGE_DEMO} />

*(The same simulated distribution. `call_seconds` and `percentile` from the
first demo are already loaded here.)*

The slow tail almost disappears, for about 5% more calls. For an agent,
the rule from
[Lesson 3](/06-reliability/03-checks-in-the-loop/04-parallel-checks-and-tripwires/#what-parallel-costs-speculative-work)
decides where hedging is allowed. A model call or a read has no side effects,
so a duplicate costs tokens and nothing else. A write can't be hedged,
because both copies might land, unless it carries an
[idempotency key](/03-tool-design-for-agents/04-tools-that-call-the-outside-world/02-which-failures-to-retry-and-how/#retrying-a-write-can-do-it-twice).
Hedging also adds load to a service that may be slow because it's already
overloaded, which is when a circuit breaker should be stopping calls instead.

</Subsection>
