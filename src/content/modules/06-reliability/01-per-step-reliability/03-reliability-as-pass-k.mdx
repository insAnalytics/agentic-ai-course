export const REFERENCE = String.raw`from math import comb


def pass_hat_k(results: dict[str, list[bool]], k: int) -> float:
    """pass^k over a set of tasks: for each task, the chance that k of its runs, picked without
    replacement, all succeeded; then the average over tasks."""
    if k < 1:
        raise ValueError("k must be at least 1")
    if not results:
        raise ValueError("no tasks")
    estimates = []
    for task, runs in results.items():
        if len(runs) < k:
            raise ValueError(f"{task} has {len(runs)} runs, fewer than k={k}")
        estimates.append(comb(sum(runs), k) / comb(len(runs), k))
    return sum(estimates) / len(estimates)

<Subsection title="Two ways to count repeated runs" variant="a">

Run the same task several times and you can ask two different questions
of the results:

- **Did it succeed at least once?** That's **pass@k**: the chance that at
  least one of *k* runs succeeds. It's the standard measure for code
  generation, where unit tests can check each attempt and you keep the one
  that passes. It measures what an agent *can* do.
- **Did it succeed every time?** That's **pass^k** (read "pass hat k"):
  the chance that all *k* runs succeed. It measures what an agent *will*
  do, run after run.

An agent serving users doesn't get to keep its best attempt. Each user
gets one run, so the share of users served correctly is the plain success
rate, pass^1. pass^k asks a different question: can this task be *promised*?
A task with pass^8 near 1 goes right every time it comes up, for every user
who asks it and every time a scheduled workflow repeats it. A task with the
same average success rate but a low pass^k is the one that fails someone
eventually, and you can't say who. When an agent has to be dependable,
not just right on average, pass^k is the measure.

The metric comes from
[τ-bench](https://arxiv.org/abs/2406.12045) (Yao et al., 2024), a benchmark
where an agent helps a simulated customer through an airline or retail
task, calling real tools and following a written policy. Success is
checked in code: the database at the end of the conversation either
matches the correct outcome or it doesn't. The paper's best agent at the
time succeeded on about 61% of retail tasks in a single run, and its pass^8
fell below 25%: most tasks it could solve, it couldn't solve eight times in
a row. Notably, the agent ran at temperature 0. The variation came from the
simulated customer, sampled at temperature 1, phrasing the same request
differently each time, and from the
[nondeterminism that remains even at temperature 0](/01-llm-foundations/05-decoding-strategies-and-generation-controls/06-stop-sequences-and-nondeterminism/).

At *k* = 1 the two measures are the same thing: the success rate. They
split apart as *k* grows. pass@k rises toward 1 for any task the agent
ever gets right, and pass^k falls toward 0 for any task it ever gets wrong.

</Subsection>

<Subsection title="Estimating pass^k from runs you already have" variant="b">

Suppose a task was run 8 times and succeeded 6. What's its pass^3?

One direct way to estimate it: consider every way of picking 3 of those 8
runs, and count how many of those picks are all successes.

<LiveDemo client:load code={PICKS_DEMO} />

You don't need to list the picks. There are C(8, 3) ways to pick 3 runs of
8, and C(6, 3) of them use only the 6 successes. So for a task with *c*
successes in *n* runs, the estimate is C(*c*, *k*) / C(*n*, *k*). That's the
estimator τ-bench uses, and pass@k has a matching one:

<LiveDemo client:load code={FORMULA_DEMO} />

Why not just take the success rate, 6/8, to the power *k*? Because that
treats 0.75 as the task's true success rate, when it's only an estimate
from 8 runs, and the error doesn't cancel out. Picking without replacement
counts only what was actually observed: at *k* = 8 there's exactly one
pick, all 8 runs, and it included two failures, so the estimate is 0. The
power formula still says 10%, which the runs you have don't support.

Two practical consequences:

- **You can't estimate pass^k with fewer than *k* runs.** There's no way to
  pick 8 runs out of 5. To report pass^8, run each task at least 8 times,
  and more runs give a steadier estimate.
- **`math.comb(c, k)` is 0 when *c* < *k*,** which is exactly right: with 3
  successes, no pick of 4 runs can be all successes.

</Subsection>

<Subsection title="Average per task, never the average to the power k" variant="a">

A benchmark has many tasks. pass^k for the whole set is the average of each
task's pass^k. The tempting shortcut is to take the overall success rate
and raise it to the power *k*, which is what "one in three succeeds, so
three in a row happens about 4% of the time" does. That shortcut is right
for a single task. For a set of tasks it's wrong, and it can be wrong in
either direction.

Here are two made-up agents with the same overall success rate, 70%, on ten
tasks run ten times each:

<LiveDemo client:load code={TWO_AGENTS_DEMO} />

*(Both agents are made up to show the two extremes.)*

At *k* = 1 the agents look identical. At *k* = 5 they're nothing alike:

- **The all-or-nothing agent is perfectly consistent.** Its pass^5 stays at
  70%, because the tasks it solves, it solves every time. Raising the mean
  to the fifth power says 17%, far too pessimistic.
- **The agent that gets every task 7 times in 10 is a coin flip everywhere.**
  Its pass^5 is 8%, and the shortcut's 17% is twice too optimistic.

The shortcut assumes every task has the same success rate, which is the
same assumption behind
[the easy/hard split in the compounding concept](/06-reliability/01-per-step-reliability/01-small-errors-compound/#where-the-model-breaks),
and real task sets don't satisfy it: τ-bench's per-task success rates, and
the clustering you saw in [the previous concept](/06-reliability/01-per-step-reliability/02-the-same-question-run-twice/#failures-cluster-on-particular-questions),
both show tasks differing widely. Estimate per task, then average.

Here's the same comparison on the real runs from the previous concept, 84
questions and 20 runs each:

*(Real runs from both models, loaded with the lesson's shared setup.)*

Both models look like the all-or-nothing agent more than the coin-flip one,
because most of their questions never fail: the shortcut underestimates
pass^k for both, and by a factor of more than two for the 2B at *k* = 20.
Its measured pass^20 means that about three questions in five were answered
correctly all twenty times. These are two small models on 84 questions;
the point that carries over is the method, not the numbers.

</Subsection>

<Subsection title="Reading a pass^k curve" variant="b">

Plot pass^k against *k* and the shape tells you something the success rate
can't:

- **pass^1 is the success rate.** Every curve starts there.
- **The curve never rises.** Each extra run is one more chance for a
  failure to appear.
- **A flat curve means consistency.** The tasks the agent solves, it keeps
  solving; improving it means solving new tasks.
- **A steep curve means coin flips.** Many tasks succeed sometimes and fail
  sometimes; improving it means making the agent consistent on tasks it
  can already do.
- **The curve levels off at the share of tasks the agent never fails.**
  For large *k*, only those tasks are left.

This is why the module measures reliability as pass^k. Two changes to an
agent can raise the success rate by the same amount, and only pass^k shows
whether either made it more dependable. Measuring it across a whole suite,
and tracking it as the agent changes, is Module 7's job; in this module
it's the yardstick for each technique.

</Subsection>
