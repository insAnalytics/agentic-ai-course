def run_cascade(small: list[dict], large: list[dict], questions: dict, k: int, min_agreement: int) -> dict:
    """Vote on the small model's samples in groups of k; when fewer than min_agreement agree, use one sample
    from the large model instead. Report accuracy, how often it escalated, and the tokens each model used."""
    large_samples = {record["id"]: record["samples"] for record in large}
    decisions = escalated = correct = small_tokens = large_tokens = 0
    for record in small:
        question, samples = questions[record["id"]], record["samples"]
        for group_number, start in enumerate(range(0, len(samples) - k + 1, k)):
            group = samples[start:start + k]
            vote = majority_answer([s["text"] for s in group], question["type"])
            decisions += 1
            small_tokens += sum(s["tokens"] for s in group)
            if vote["votes"] >= min_agreement:
                correct += is_correct(question, f"ANSWER: {vote['answer']}")
            else:
                escalated += 1
                fallback = large_samples[record["id"]][group_number]
                large_tokens += fallback["tokens"]
                correct += fallback["correct"]
    if not decisions:
        return {"decisions": 0, "accuracy": None, "escalated": None, "small_tokens": None, "large_tokens": None}
    return {"decisions": decisions, "accuracy": correct / decisions, "escalated": escalated / decisions,
            "small_tokens": small_tokens / decisions, "large_tokens": large_tokens / decisions}

<Subsection title="Two places to send a doubtful case" variant="a">

When a signal from
[the previous concept](/06-reliability/06-when-unsure/02-signals-the-agent-isnt-sure/)
fires, the agent has two ways to get a better answer:

- **A stronger model:** send the case to a more capable model, at a higher
  price or with more latency.
- **A person:** hand the case to someone who can answer it, at the cost of
  their time and the user's wait.

The same signals can drive either, and a system can use both: a stronger
model first, a person when even that isn't sure.

It's worth being precise about how this differs from the approval gate in
[Module 3](/03-tool-design-for-agents/11-designing-for-least-privilege/02-separate-reads-from-writes-and-gate-the-writes/).
That gate triggers on *what the action is*: a write, an irreversible or
external step, needs a person's approval however sure the agent is. The
escalation here triggers on *how sure the agent is*, whatever the action.
They answer different questions and combine naturally: a risky action by an
unsure agent is the clearest case for a person.

</Subsection>

<Subsection title="Cascades" variant="b">

Sending every request to the strongest model is simple and expensive.
A cascade tries the cheapest model first, and moves up only when the answer
looks doubtful. Chen, Zaharia and Zou's
[FrugalGPT](https://arxiv.org/abs/2305.05176) (TMLR 2024) is the best-known
study. They found the prices of language model APIs differed by up to two
orders of magnitude, and built a cascade that could match GPT-4's performance
with up to 98% lower cost, or beat it by up to 4% at the same cost.

How their cascade decides matters. It doesn't ask the model how sure it is.
Each answer is scored by a separate, small model, DistilBERT trained as a
regressor on examples of queries and answers labelled right or wrong, and the
cascade accepts the answer when the score clears a threshold. That scorer is
a learned check, trained and validated on labelled data, which is exactly
what [Lesson 4 said a checker needs](/06-reliability/04-verifying-claims/02-checking-the-checker/).

The cascade below uses a signal that needs no training: agreement among
votes, from
[Lesson 5](/06-reliability/05-voting/03-agreement-as-a-confidence-signal/).
Qwen3.5-2B votes on five samples; if too few agree, the question goes to
Qwen3.5-4B instead. The exercise builds it and runs it on the committed data.

</Subsection>

<Subsection title="Escalating to a person" variant="a">

The same thresholds decide what goes to a person, and the escalation rate
becomes something new: the load on people. In the run above, escalating on
any disagreement would send more than a fifth of decisions to someone. For a
system handling thousands of requests, that may be more than anyone can
review, and a person asked to check too many cases stops checking any of them
carefully. Anthropic reports that Claude Code's users approve 93% of its
permission prompts, and calls the result
[approval fatigue](https://www.anthropic.com/engineering/claude-code-auto-mode):
people stop paying close attention to what they're approving.

So escalating to a person is most useful at the far end of the signal: the
rare cases where the agent is least sure, or where
[Lesson 2's risk](/06-reliability/02-reliability-tradeoffs/04-spend-reliability-where-the-risk-is/)
is highest. And the person needs what the agent had: the question, the
competing answers or the failed check, and the sources. An escalation that
says only "please review" moves the work without moving the evidence. How
that hand-off is shown to people is Module 9's subject.

</Subsection>
