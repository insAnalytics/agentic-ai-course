from datetime import datetime, timedelta, timezone

REQUIRED = ("agent_name", "error_rate", "p95_ms", "checked_at")
MAX_AGE = timedelta(minutes=15)


def check_health_result(output: str, now: datetime) -> str | None:
    """None if a get_health result is usable; otherwise a short reason, for an is_error observation."""
    try:
        record = json.loads(output)
    except json.JSONDecodeError:
        return "get_health returned text that isn't valid JSON, possibly cut off"
    if not isinstance(record, dict) or not record:
        return "get_health returned no health record"
    if missing := [field for field in REQUIRED if field not in record]:
        return f"get_health's record is missing {missing}"
    if empty := [field for field in REQUIRED if record[field] is None]:
        return f"get_health returned no usable value for {empty}"
    if not 0 <= record["error_rate"] <= 1:
        return f"error_rate {record['error_rate']} is outside 0 to 1"
    if record["p95_ms"] < 0:
        return f"p95_ms {record['p95_ms']} is negative"
    age = now - datetime.fromisoformat(record["checked_at"])
    if age > MAX_AGE:
        return f"the health check is stale: taken {age} ago, more than {MAX_AGE} allowed"
    return None

<Subsection title="A success that isn't" variant="a">

[Module 2](/02-the-agent-loop/06-termination-failure-and-control/05-tool-errors-as-observations/)
taught the loop to catch a tool that fails loudly, with an exception or an
error status, and pass it to the model as an error observation. The harder
case is a tool that reports success and returns nothing usable: an empty
record, a field replaced by a placeholder, a reading from hours ago, JSON
cut off halfway. Nothing crashes, and the model is handed something that
looks like an answer.

Two studies show why this case matters:

- **Most tool failures are silent.** Sun et al.,
  [*Tools Fail: Detecting Silent Errors in Faulty Tools*](https://arxiv.org/abs/2406.19228)
  (EMNLP 2024), point out that a malformed call usually produces an error
  message, but a well-formed call with the wrong content, or a tool that is
  simply wrong, produces a wrong result with no signal at all, and the
  mistake carries into the steps that follow. They tested whether models
  notice such results without an explicit error, and framed the problem as
  models trusting their tools too much.
- **Whether a failure is signalled decides what the model says.** A
  preprint from September 2026 by Sethi et al.,
  [*Fabrication After Tool Failure*](https://arxiv.org/abs/2609.14758), not
  yet peer-reviewed, forced a tool call and then returned a payload that
  couldn't answer the question. When the tool reported an error, the model's
  answer was never dishonest in their main condition. When it reported
  success with an empty, cut-off, stale, corrupted or redacted value, the
  model sometimes stated a value it didn't have, or gave a made-up reason
  for not answering: up to 45.3% of the time for redacted values. The main
  experiments used one model and stub tools, so the rates themselves won't
  carry over.

The authors suggest the fix this concept builds: turn a failure the tool
didn't signal into one it did, at the tool boundary, before the model reads
it. They predict this would work, from their results, but didn't test it
directly. A result check in code is exactly that step.

</Subsection>

<Subsection title="What a result check looks for" variant="b">

A result check doesn't judge whether the answer is right. It checks whether
the result is usable at all, which is a much easier question, and one code
can answer. The usual kinds, several of which match the failure types in
Sethi et al.'s study:

- **Empty:** `{}`, `null`, an empty list, when the tool promises a record.
- **Missing a field** the next step needs.
- **A placeholder** where a value should be: `"[REDACTED]"`, `"N/A"`, `null`.
- **Cut off:** text that no longer parses, because something upstream
  truncated it without saying so.
- **Out of range:** a rate above 1, a negative count, a date in the future.
- **Stale:** a reading older than the task can use.

When one fails, the check returns a reason, and the loop from the previous
concept sends it back as an `is_error` observation. The reason should say
what failed and what to do instead, as
[Module 3's error messages did](/03-tool-design-for-agents/03-shaping-what-tools-return/03-structured-results-and-useful-error-messages/#useful-error-messages-say-what-failed-and-what-to-do-next).

<Subsection title="A result check can block good results too" variant="a">

Like every check, this one has a false-block rate, and two mistakes cause
most of it:

- **"Nothing found" isn't always a failure.** A search for incidents in the
  last hour that finds none has answered the question. If the tool returns
  `{"incidents": []}` for that and `null` when the search itself failed, a
  check can tell them apart. If it returns an empty list for both, no check
  can, which is a reason to design tools that way from the start, as
  [Module 3 argued](/03-tool-design-for-agents/03-shaping-what-tools-return/03-structured-results-and-useful-error-messages/#the-fix-return-structured-data-as-json-text).
- **Zero isn't missing.** An error rate of `0.0` is the best possible
  reading, and a check written as `if not value` treats it as absent. Test
  for `None` explicitly.

The exercise below includes both kinds of test: bad results the check has
to catch, and good ones it must let through.

</Subsection>
