def answer_key(question: dict, answer: str | None):
    """As in the previous concept: the value for a number, the normalized text otherwise."""
    if answer is None:
        return None
    return as_number(answer) if question["type"] == "number" else normalize(answer) or None


def vote_winner(question: dict, samples: list[dict]):
    """The winning answer's key, and whether it's correct; ties go to the answer seen first."""
    keys = [answer_key(question, s["answer"]) for s in samples]
    counts = Counter(key for key in keys if key is not None)
    if not counts:
        return None, False
    winner = counts.most_common(1)[0][0]
    return winner, next(s["correct"] for s, key in zip(samples, keys) if key == winner)

def decide_by_vote(propose, lead: int = 2, cap: int = 7) -> dict:
    """Ask propose() for proposed tool calls one at a time, until one call leads every other by lead votes,
    or cap proposals have been asked for. Returns the winning call, how many proposals it took, and
    whether the vote was decided."""
    counts, first = {}, {}
    used = 0
    decided = False
    while used < cap and not decided:
        proposal = propose()
        used += 1
        if proposal is None:
            continue
        key = json.dumps({"name": proposal["name"], "input": proposal["input"]}, sort_keys=True)
        counts[key] = counts.get(key, 0) + 1
        first.setdefault(key, proposal)
        ranked = sorted(counts.values(), reverse=True) + [0]
        decided = ranked[0] - ranked[1] >= lead
    if not counts:
        return {"call": None, "proposals": used, "decided": False}
    best = max(counts.values())
    winner = next(key for key in first if counts[key] == best)
    return {"call": first[winner], "proposals": used, "decided": decided}

<Subsection title="Four ways to improve on the vote" variant="a">

A plain vote, as the earlier concepts built it, has two weaknesses. It
spends the same number of samples on every question, even when the first two
already agree. And it
[locks in a favourite wrong answer](/06-reliability/05-voting/02-when-voting-helps-and-hurts/#why-the-most-common-answer-wins):
when a model's most common reply to a question is wrong, more samples only
make that reply win more reliably.

This concept measures three refinements on the same runs, and adds a fourth
that matters most for agents:

- **Stop when the samples agree,** and spend the full vote only on the
  questions that are contested.
- **Vary the prompt, not just the sample,** so a mistake tied to one
  wording doesn't win every vote.
- **Pick with a check instead of counting,** when something can tell a good
  answer from a bad one.
- **Vote on the decision, not the answer:** sample the agent's next tool
  call several times before running it once.

</Subsection>

<Subsection title="Stop when the samples agree" variant="b">

Most questions don't need five samples. If the first two agree, three more
rarely change the result. Aggarwal et al.'s
[Adaptive-Consistency](https://arxiv.org/abs/2305.11860) (EMNLP 2023) turned
that into a stopping rule: keep sampling only while the vote is still in
doubt. Across 17 reasoning and coding datasets and three models, it cut the number of samples by up to 7.9 times, for an average accuracy drop of under 0.1%. Here's a simpler rule on this module's runs: stop
as soon as one answer leads every other by two votes, with five samples as
the most any question gets.

<LiveDemo client:load dataFiles={BOTH_DATA} setupCode={VOTE_SETUP} code={EARLY_STOP_DEMO} />

*(Real committed runs, each question's samples shuffled 200 times.
`answer_key` and `vote_winner` from the second concept are already loaded
here.)*

For almost the same accuracy, the vote used under half the samples. The
saving isn't spread evenly. Questions the model always gets right stop after
two samples. The contested ones, where a vote actually does something, still
get all five. That's
[Lesson 2's rule](/06-reliability/02-reliability-tradeoffs/04-spend-reliability-where-the-risk-is/)
applied inside a single technique: spend where the doubt is. The price is
latency. Samples drawn one at a time can't all run in parallel, so an
agent that needs the answer quickly might draw two at once, and add more
only when they disagree.

</Subsection>

<Subsection title="Vary the prompt, not just the sample" variant="a">

A favourite wrong answer comes from somewhere. Often it's how the question
was put:
[Lesson 1 found](/06-reliability/01-per-step-reliability/04-reliable-across-wordings/)
questions whose accuracy swung by 50 points or more with the wording. If
every sample sees the same wording, every sample shares that wording's pull.
Anthropic's
[guide to building agents](https://www.anthropic.com/engineering/building-effective-agents)
gives this as a use of voting: "reviewing a piece of code for
vulnerabilities, where several different prompts review and flag the code if
they find a problem." Li et al.'s
[DiVeRSe](https://aclanthology.org/2023.acl-long.291/) (ACL 2023) sampled
answers from several different prompts instead of one, and combined that
with a verifier. With both, GSM8K accuracy rose from 74.4% to 83.2%.
This module's runs asked every question in four wordings, so the idea can be tested directly: a vote of four samples of the
original wording, against one sample from each of the four.

<LiveDemo client:load dataFiles={WORDINGS_DATA} setupCode={VOTE_SETUP} code={MIXED_DEMO} />

*(Real committed runs of Qwen3.5-2B, 200 random draws per question.)*

Over all 84 questions, the average barely moves. The question-level rows
show why: two effects cancel.

- **On e68 and e21, it breaks the lock-in.** These are the second
  concept's questions, where one wording pulled the 2B towards the same
  wrong value. Other wordings don't share that pull, so the wrong answer
  stops winning every vote.
- **On e83, it hurts.** Here the original wording was the good one, and
  the other wordings were right less than half the time. Mixing brings in
  their mistakes.

So varying the prompt helps when mistakes are tied to one prompt, and costs
when some prompts are simply worse. It's worth measuring each wording before
mixing them in, just as Lesson 1 measured them before blaming the model.
Mixing models instead of wordings has the same logic, with a limit that
[Module 2](/02-the-agent-loop/09-reflection-and-self-critique/03-the-limits-shared-blind-spots/) met as
shared blind spots. Kim et al.'s
[*Correlated Errors in Large Language Models*](https://arxiv.org/abs/2506.07962)
(ICML 2025) compared more than 350 models and found that, on one leaderboard,
when two models both got a question wrong they gave the same wrong answer 60%
of the time. Larger, more accurate models shared more of their errors, even
across providers. A vote across models is less independent than it looks.

</Subsection>

<Subsection title="Pick with a check instead of counting" variant="b">

Counting treats every sample as equally likely to be right. If something
can tell a right answer from a wrong one, it can do better: sample several
answers, and keep the one the check passes. That's how Anthropic reports its
highest coding-benchmark scores. For its
[Claude 4 results](https://www.anthropic.com/news/claude-4), it sampled
several attempts in parallel, discarded patches that broke the repository's
visible regression tests, and had a scoring model choose among the rest.
The research behind the idea goes back further. Cobbe et al.
[trained such a verifier](https://arxiv.org/abs/2110.14168) for grade-school
maths (2021). A 6B model choosing among its samples with the verifier slightly outperformed a fine-tuned 175B model, a gain the authors put at about what a thirtyfold larger model would give. Lightman et al.'s
[*Let's Verify Step by Step*](https://arxiv.org/abs/2305.20050) (2023)
improved on it by checking each step of the reasoning, not only the final
answer. Snell et al., from
[the fourth concept](/06-reliability/05-voting/04-voting-thinking-or-a-stronger-model/),
found that searching against such a verifier was one of the most effective
ways to spend extra computation at test time.

An agent often has a check already, and it doesn't have to be a trained
model. Tests that pass, a schema the output matches, a figure found in a tool
result: the checks from
[Lesson 3](/06-reliability/03-checks-in-the-loop/01-where-a-check-can-sit/) and
[Lesson 4](/06-reliability/04-verifying-claims/01-checking-each-claim/) can all choose between
samples. Here's the simplest one, applied to a vote of five: vote only among
the samples whose answer appears in the question's sources.

<LiveDemo client:load dataFiles={BOTH_DATA} setupCode={VOTE_SETUP} code={VERIFIER_DEMO} />

*(Real committed runs, 200 random draws of five samples per question.)*

On average the check made things slightly worse, and the question-level rows
show both sides of it:

- **Where it's right, it wins.** On e41, the 4B said "unknown" in 7 of its
  20 replies. "unknown" appears in no source, so the check drops those
  samples, and the vote goes to `claude-haiku`, which the source states.
- **Where it false-flags, it loses badly.** The answers to e83 (1.5 days)
  and e69 (13 minutes) are worked out from the sources, not written in them.
  So the check rejects every right sample. When a draw includes a wrong
  answer that does appear in the text, such as e83's 31 (a figure from the
  same sentence), the vote goes to it. It's
  [Lesson 4's derived-number false flag](/06-reliability/04-verifying-claims/04-figures-traced-to-tool-results/),
  with a bigger effect: a false flag no longer just flags an answer, it
  swaps it for a worse one.

A check that chooses between samples is only as good as its false-flag
rate, and it has to be measured
[the way Lesson 4 measured its judges](/06-reliability/04-verifying-claims/02-checking-the-checker/)
before it gets that job. There's a second risk. The harder a search pushes
against a check, the more it finds the answers that fool it.
Cobbe et al. saw this
too: accuracy rose as the verifier chose among more samples per problem, up to
400, and then fell. Past that point, they concluded, the search was finding
adversarial solutions that fool the verifier. An agent pushed hard against a
check can do the same thing,
[in the next lesson's terms](/06-reliability/07-safe-actions/05-gaming-the-check/):
satisfy the check instead of the task.

</Subsection>

<Subsection title="Vote on the decision, not the answer" variant="a">

Everything so far voted on answers. An agent's riskier outputs are its
actions, and an action can't be sampled five times: five `set_model` calls
are five changes. The decision can be, though. Before a tool call runs, the
agent can ask the model for its next step several times, compare the
proposed calls, and run the winner once.

<LiveDemo client:load code={DECISION_DEMO} />

*(Scripted proposals, standing for five samples of the model's next step.)*

Two things carry over from answers. What counts as the same call has to be
decided first, and the same arguments in a different order are the same call.
And a split vote is itself a signal. If the proposals disagree about which
model to move the agent to, the agent shouldn't pick one. It should look
the value up or ask, as
[Lesson 6](/06-reliability/06-when-unsure/01-asking-before-acting/)
describes.

Voting on every step can go a long way. Meyerson et al.'s
[MAKER](https://arxiv.org/abs/2511.09030), a 2025 preprint from Cognizant's AI
lab, split a 20-disk Towers of
Hanoi, 1,048,575 moves, into one model call per move. It chose each move with
*first-to-ahead-by-k* voting, the stop-at-a-lead rule from earlier in this
concept, and threw out any sample that wasn't in the expected format before
it could vote. The authors'
[published code](https://github.com/cognizant-ai-lab/neuro-san-benchmarking)
shows both. With a small model, gpt-4.1-mini, the authors report finishing all million
moves without an error, against the arithmetic of
[Lesson 1's compounding](/06-reliability/01-per-step-reliability/01-small-errors-compound/).
The caveat is the task. Every Hanoi move is fully specified and can be checked
on its own, so voting corrects random slips, not a mistake every sample shares. The exercise builds this vote, with the early stop from earlier
in this concept.
