<Subsection title="Everything built from a restricted document" variant="a">

Filtering chunks protects the chunks. But this module has built a lot of other
things out of them: Lesson 9's contexts, Lesson 4's vectors, Lesson 12's graph
edges and community summaries. Each is new text or data derived from the
documents, and each carries some of what its sources said. Here's how much of
it comes from documents an all-staff reader may not see. First, two helpers,
defined once here and already loaded for every demo and exercise from here to
the end of this lesson:

```python
CHUNK_ACCESS = {f"{c['doc_id']}:{c['chunk']}": set(c["access"])
                for d in load_documents() for c in structured_chunks(d, 200)}

def readable(chunk_id: str, groups) -> bool:
    """Whether a reader with these groups may read the chunk with this id."""
    return bool(set(groups) & CHUNK_ACCESS[chunk_id])
```

<Subsection title="Rules for each kind of derived data" variant="b">

The principle is that **derived data inherits the permissions of what it was
derived from.** How that works depends on what it was derived from:

- **Derived from one chunk:** a context, a vector, a header. It gets the chunk's
  access, and it's filtered with the chunk. `PermittedRetriever` already does
  this, because each reader's pipeline is built from permitted chunks, with
  their contexts and vectors. Vectors deserve the same care as text:
  [Morris and colleagues (EMNLP 2023)](https://arxiv.org/abs/2310.06816)
  recovered 92% of 32-token inputs *exactly* from their embeddings, and
  concluded embeddings should be protected like the text they came from.
- **Derived from several chunks, each enough on its own:** a graph edge. If
  one source a reader may read states the fact, the reader may know it. So an
  edge is visible when at least one of its sources is readable, and it shows
  only those sources.
- **Derived from several chunks together:** a summary. It can repeat anything
  from any of its sources, so a reader may see it only if they may read
  *every* source. The alternative is to write a separate summary for each
  permission level, which multiplies the summaries' cost by the number of
  levels.
- **Caches of any of these.** A cached answer or a cached prompt prefix built
  for one reader must never be served to another with different permissions,
  which is why Lesson 1 noted that pasting a corpus means a separate cached
  prefix per set of permissions. Key every cache by the permission set as well
  as the question.

</Subsection>

<Subsection title="Deleting a document reaches everything built from it" variant="a">

Derived data follows its sources out of the index, too. When a document is
deleted, everything built from it has to go or be rebuilt, or the index
keeps serving what the source system no longer holds. The rules above say
which. Here's what deleting D11, the INC-2093 report, would touch
in the structures this module has built:

<LiveDemo client:load dataFiles={RAG_GRAPH_DATA} setupCode={SETUP} code={DELETION_DEMO} />

- **Derived from its chunks alone:** the 4 chunks, their 4 contexts, and a
  vector for each chunk in each index that embedded it. These are deleted
  with the chunks. Vectors are filed by a hash of their text, so the text
  finds them.
- **Graph edges:** the rule that decided who may see an edge decides what
  happens to it. 8 edges rest on D11 alone and are deleted. 3 are also
  stated elsewhere: they stay, citing only their other sources. Deleting
  edge by edge like this gives exactly the graph a rebuild without D11
  would.
- **Summaries:** two were written partly from D11, and nothing in a
  summary's text records which sentence came from which chunk. So each is
  written again from what's left, or dropped. The communities themselves
  can change, so summaries are regenerated from the rebuilt graph's
  communities: INC-2093 existed only in D11's edges, so its community is
  gone, and what's left of it, SEC-014, `support_agent` and `triage_agent`,
  is a new community with no summary at all.
- **Caches:** any answer or prompt prefix cached from D11's chunks. A cache
  keyed by question and permission set, as above, can't be searched by
  source, so either record which chunks each entry used, or clear the cache
  when a document is deleted.

Doing this reliably, at scale, as documents change every day, and honouring
a person's right to have their data deleted, belongs to Module 10
(Production). The rule it rests on is this lesson's: whatever holds part of
a document is removed or rebuilt with it.

</Subsection>

<Subsection title="When permissions change at the source" variant="b">

Every chunk's `access` field is a copy, taken from the document when it was
indexed. The permissions themselves live in the source system: the wiki,
the document store, the directory that says who's in which group. When they
change there, a page made private or a document's audience narrowed, the
copy is wrong until the index catches up, and so is everything derived from
it. A user removed from a group is the same problem wherever their groups
were looked up once and kept, for example at login.

Between the change and the next sync, retrieval enforces the old
permissions. The gap is as long as the sync interval, and longer if a sync
fails without anyone noticing. So a sturdier design checks twice:

1. **Filter by the index's copy before ranking,** as the first concept
   does. This keeps ranking fair, and needs nothing outside the index.
2. **Check each result against the source system's current permissions
   before it reaches the model.** This catches whatever changed since the last sync,
   at the cost of one check for each of a handful of results.

The second check doesn't replace the first, and it isn't the
[filtering afterwards that the first concept rejected](/05-rag-systems/13-permissions/01-permissions-at-retrieval-time/#filtering-afterwards-isn-t-enough).
Every ranking stage still sees only what the index says the reader may
read. The second layer removes only results whose permissions changed since
the sync, usually few, so results are seldom short; fetching a few extra
candidates covers it when they are.

The live check is often answered by a dedicated authorisation service.
Google described its own in
[Zanzibar](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)
(USENIX ATC 2019): permissions are stored as relationships, such as this
user is a member of this group, this group may view this folder, and this
folder holds this document, and a check follows them. This is
**relationship-based access control**. OpenFGA and SpiceDB are open-source
services built on the same design. [OpenFGA's guide to retrieval](https://openfga.dev/docs/modeling/agents/rag-authorization)
offers the two calls this design needs, as two alternative approaches:
listing the documents a reader may see, for a filter in the search, and
checking a batch of results before they reach the model. Using both, one
before ranking and one after, is the two-layer check above.
Keeping indexes in step with their sources is, again, Module 10's
subject.

</Subsection>
