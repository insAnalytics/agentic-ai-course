<Subsection title="Filtering the text doesn't work" variant="a">

The obvious defence is to look for planted instructions: search new text for
phrases like "note for AI assistants" and block it. It's the deny-list
from [Lesson 11's SQL guardrails](/05-rag-systems/11-agentic-rag/04-when-the-answer-is-in-a-table/#guardrails-allow-don-t-ban)
again, with the same weakness: it catches the phrasings someone thought of,
and a planted page can be written a thousand other ways. A false fact with no
instruction in it at all, "the limit was removed in v2.6", has nothing to
detect.

Classifiers trained to spot injected instructions, such as Meta's
[Prompt Guard](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M) and
Microsoft's [Prompt Shields](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection),
learn from many examples rather than a fixed list.
But they're probabilistic filters, and attackers adapt to them. In
[The Attacker Moves Second](https://www.usenix.org/conference/usenixsecurity26/presentation/nasr)
(USENIX Security 2026), Nasr,
Carlini and colleagues optimised attacks against four such detectors, and got
past three of them, Prompt Guard among them, more than 90% of the time.
[EchoLeak](/05-rag-systems/13-permissions/04-defences-by-design/#the-answer-is-a-way-out-too),
below, got past Microsoft's own classifier in production by wording its
instructions as if they were meant for a person.
And a planted false fact contains no instruction for a classifier to find. A
detector can be one more tripwire, but not the defence the design rests on.

So the defences that hold are structural. They decide **who can put text in
front of the model**, **what the model is told about that text**, and **what
the model can do after reading it**, without depending on recognising a bad
page when it arrives.

</Subsection>

<Subsection title="Control what gets indexed" variant="b">

The planted page reached the model because anyone could write to a source the
index trusted as much as the API reference. The first defence is at ingestion,
before a document is ever chunked:

- **Know who wrote each document.** Record the author from whoever submitted
  it, the same way a reader's groups come from who they are, never from a field
  inside the document.
- **Trust writers per source.** The documentation pipeline may publish official
  documents directly. An edit to the open wiki isn't trusted that way, however
  useful the wiki is.
- **Quarantine the rest until reviewed.** An untrusted document waits outside
  the index until someone other than its author approves it. An untrusted edit
  to a page that's already indexed waits too, so the reviewed version stays
  searchable until the edit is approved.
- **Derive only from what's indexed.** Contexts, vectors, graph edges and
  summaries are built from what the gate has let in, never from what's
  waiting in quarantine. Otherwise a document nobody approved reaches the
  model through what was derived from it.

This moves the decision from the model, which can't be relied on, to people and
code, which can be held to a process. It's what
[OWASP recommends](https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/)
for retrieval systems: "Accept data only from trusted and verified sources."
It costs review time, which is why it's worth applying first to the sources
anyone can write to, not to every document.
This concept's exercise builds that gate.

</Subsection>

<Subsection title="Keep provenance visible, and watch what's new" variant="a">

Whatever is indexed should carry its source type and date to the model, as
[Lesson 10 arranged](/05-rag-systems/10-grounded-answers/01-assembling-the-request/#what-each-source-carries-and-what-the-model-is-told),
so an answer policy like "prefer the newer official source" has something to
act on. It's a softer defence, since it relies on the model, but it costs
nothing.

Changes to the index can also be watched. When a new page arrives, run the
labelled questions again and see what it displaces. The demo builds a keyword
index with the planted page added and runs every labelled question, so allow a
few seconds:

<Subsection title="Limit what the model can do after reading" variant="b">

Some untrusted text will always reach the model: the open wiki is useful,
customer emails need answering, and the web is full of pages worth reading. So
the last defence limits the damage when a planted instruction is followed.
[Module 3 called it the lethal trifecta](/03-tool-design-for-agents/10-the-tool-threat-model/03-the-dangerous-combination/#one-injected-instruction-needs-somewhere-to-send-the-data):
untrusted input, access to private data, and a way to act or send data out.
An agent with all three can be steered by a document into leaking or changing
things. Cutting one leg is the structural fix, as long as the leg is really
cut:

- **Keep retrieval tools read-only, and count every way out.** Lesson 11's
  SQL tool couldn't write, and the search tool only reads. But read-only
  isn't the same as having no way out. A tool that fetches an address the
  model wrote sends whatever the model put in that address. So does the
  answer itself, if the interface displays it, as the next subsection shows.
- **Put a person in front of actions.** An agent that reads the open wiki
  shouldn't also send messages or change the registry without someone
  confirming.
- **Keep permissions tied to the reader.** A planted instruction can't widen
  what the agent retrieves if the reader's groups are fixed in code, as in the
  first concept.

The trifecta is about leaks and actions. It does nothing against the
[previous concept's planted fact](/05-rag-systems/13-permissions/03-retrieved-text-is-untrusted-input/),
which needs no action at all: the model simply repeats it, faithfully and
with a citation. Only the gate and the provenance above address that.

</Subsection>

<Subsection title="The answer is a way out too" variant="a">

An answer goes to an interface, and most chat interfaces render Markdown. A
Markdown image is an instruction to the browser to fetch an address, and the
browser follows it the moment the answer is displayed. Whoever chose the
address receives everything in it.

Here's a page planted on the open wiki that uses this, one that got past
review. A security-team reader asks about SEC-014, which they're allowed to
read, and keyword search over what they may read brings back the planted
page along with the report. The page's author can't read the report, and
doesn't need to. As in
[the previous concept](/05-rag-systems/13-permissions/03-retrieved-text-is-untrusted-input/#what-reaches-the-model),
the reply is scripted: it shows what following the page looks like, not how
often a real model would:

<LiveDemo client:load dataFiles={RAG_GRAPH_DATA} setupCode={SETUP} code={EXFIL_DEMO} />

The retrieval was correct: every chunk in the request is one this reader may
read. The leak happens afterwards. The badge's address carries the answer's
first sentence, taken from a report only the security team may read, to a
host the page's author runs. It's fetched when the answer appears, with no
click and no tool call. The "full report" link needs a click, and its label
invites one.

This is how **EchoLeak** (CVE-2025-32711) worked, an attack on Microsoft 365
Copilot that
[Aim Security's researchers disclosed](https://web.archive.org/web/20250611174716/https://www.aim.security/lp/aim-labs-echoleak-blogpost)
in June 2025, after Microsoft had fixed it. Reddy and Gujral later wrote it
up as a [case study](https://arxiv.org/abs/2509.10540). The attacker
sent an ordinary-looking email. When the user later asked Copilot something
the email was relevant to, Copilot's retrieval brought it into the context,
and its instructions had Copilot put data from that context into the address
of a Markdown image, which the user's browser fetched automatically. It got
past three defences on the way. The instructions were worded as if addressed
to the email's human recipient, which got them past Microsoft's classifier
for injected prompts. They used reference-style Markdown, which the filter
that removed external links didn't recognise. And the image went through a
Microsoft Teams address that the interface's content security policy
allowed.

The defence is code that runs on every answer before it's displayed, and
doesn't judge what the answer says, only where its addresses go. Microsoft
lists "deterministic blocking of known data exfiltration methods" among
[its own defences](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks).
Here's a version for this corpus:

<LiveDemo client:load dataFiles={RAG_GRAPH_DATA} setupCode={SETUP} code={OUTPUT_FILTER_DEMO} />

The badge is gone, the outside link keeps only its text, and the runbook link
on the allowed host survives. The reference-style image shows why the last
step exists: the image pattern never matched it, and only the sweep over
every address caught it. The last three lines show why the host comes from
`urlsplit` rather than a text check. Both of the outside addresses contain
"docs.example.com", and neither goes there.

The same rules apply wherever the output is used:

- **Don't load remote images automatically.** Show images only from hosts
  you control, or not at all.
- **Allow links only to known hosts.** Anywhere else, show the text without
  the link.
- **Set a content security policy in the interface.** It tells the browser
  which hosts a page may load anything from, so a form the filter misses
  still isn't fetched. Keep off it any host that fetches or redirects on
  request, as the Teams address in EchoLeak did.
- **Treat addresses in tool arguments the same way.** A fetch tool's URL, or
  a query sent to an outside search engine, carries whatever the model
  writes into it.
  [Module 3's allowlists](/03-tool-design-for-agents/11-designing-for-least-privilege/03-allowlists-and-per-tool-credentials/#allowlists-bound-what-a-tool-can-act-on)
  bound those.

Like the ingestion gate, the filter is a rule in code: it doesn't need to
recognise the planted page to stop what it asked for.

</Subsection>
