<Subsection title="Citations a program can read" variant="a">

An answer built from retrieved sources is only as trustworthy as the link
between each statement and where it came from. A citation is that link, and
this lesson's instructions ask for it in a form code can read: after each
statement, the id of the source it came from, like `[S2]`. Because
`assemble_request` recorded which chunk each id stands for, every citation
can be traced to a document and a section.

Models don't do this perfectly. [Gao and colleagues built
ALCE](https://arxiv.org/abs/2305.14627), a benchmark that scores answers with
citations automatically, and found that even the best models they tested
lacked complete citation support in about half of their answers on one of
its datasets. So citations are worth asking for, and worth checking.

</Subsection>

<Subsection title="Checking what can be checked" variant="b">

Some things about citations are mechanical, and code can check them every
time. This is already loaded for every demo and exercise from here to the
end of this lesson:

```python
CITATION = re.compile(r"\[(S\d+)\]")

def check_citations(answer: str, sources: dict) -> dict:
    """What code can check about an answer's citations: which statements cite what, which ids
    weren't among the sources sent, and which statements cite nothing."""
    # a sentence ends at . ! or ?, unless a citation follows straight after
    statements = [s.strip() for s in re.split(r"(?<=[.!?])\s+(?!\[)", answer.strip()) if s.strip()]
    checked = [{"text": s, "cites": CITATION.findall(s)} for s in statements]
    cited = {source_id for s in checked for source_id in s["cites"]}
    return {
        "statements": checked,
        "unknown": sorted(cited - sources.keys()),
        "uncited": [s["text"] for s in checked if not s["cites"]],
        "cited": {i: (sources[i]["doc_id"], sources[i]["section"]) for i in sorted(cited & sources.keys())},
    }
```

It splits the answer into statements, collects each statement's citations,
and reports two kinds of problem: ids that weren't among the sources sent,
and statements that cite nothing. It also maps every valid id back to its
document and section, which is what an interface would show a reader, a
subject for Module 9. Here it is on a scripted answer to the rate-limit
question:

Here are three answers that go wrong in different ways:

The first two are caught. An id the model wasn't given is either invented or
garbled, and a statement with no citation is exactly the kind of statement
that might have come from the model's general knowledge rather than the
sources. What to do about them is a design choice: drop the statement, ask
the model again, or show the answer with a warning.

The third passes both checks and is still wrong. `S3` exists, and the
statement cites it, but S3 is the error-code table, and it never says 60.
The number is right; its source isn't. Checking that a cited source actually
*supports* a statement means reading both and comparing what they say, which
is a model call or a person, not a regular expression. That's Module 6's
subject, verification. This lesson's checks are the cheap first layer: they
make sure every citation points somewhere real, so that verification has
something to check.

</Subsection>

<Subsection title="Quotes that code can check" variant="b">

There's a layer between a regular expression and full verification that
still costs no model call. Ask the model to back each citation with a short
quote, copied word for word from the source it cites, by changing the
citation line of the instructions to something like:

```text
After each statement, cite the source it comes from by id, with a short quote copied word for word from that source, like [S2: "the exact words"].
```

Then code can check that each quote really is in the source it's attributed
to. Anthropic's guidance recommends both halves of this idea: for long
documents, [asking the model to quote the relevant parts
first](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices),
and, [to reduce
hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations),
making a response auditable "by having it cite quotes and sources for each
of its claims". The check itself is plain string matching, after
normalising what a model might reasonably change: curly quotes, line breaks
and runs of spaces, and the backticks Markdown puts around code. Here it is on the rate-limit question's sources, with the
wrong-source reply from above now carrying a quote, and some others:

<LiveDemo client:load dataFiles={RAG_EXPANSION_DATA} setupCode={SETUP} code={QUOTES_DEMO} />

*The replies are scripted to show what the check can and can't catch.*

- **The wrong source is now caught.** Here the model took the 60 from S1
  and labelled it S3. The words it quotes are S1's, and they aren't in S3.
- **An invented quote is caught.** S1 is the right source for a rate-limit
  statement, but it never says the limit resets every hour, so no quote can
  come from it.
- **Normalising matters.** The good reply's second quote leaves out the
  backticks around `REG-1009` that the source's Markdown has. Compared
  exactly, it would have been flagged.
- **A real quote that doesn't support the statement still passes.** S3 does
  say "The key made too many requests this minute", and it says nothing
  about 60. A quote proves the words are in the source, not that they
  support the statement, so that's still Module 6's job. A very short quote,
  like "60", proves even less, so a check can also insist on a minimum
  length.

The quote check runs alongside the id checks above, not instead of them: a
statement with no citation has no quote to check. And quotes cost output
tokens. The first reply is 47 tokens with its quotes and 21 without, more
than double.

</Subsection>

<Subsection title="Citations built into the API" variant="a">

Some providers build citations into the API itself. On
[Anthropic's Messages API](https://platform.claude.com/docs/en/build-with-claude/citations),
each source can be sent as a `document` content block with citations turned
on, instead of as a tagged source inside one text message. The reply
then comes back as several text blocks, and each block that draws on a
document carries a `citations` list. Each citation says which document it
points to, by its position among the documents sent, and gives `cited_text`,
the exact text cited, with where it sits: character positions for a
plain-text document, pages for a PDF, or block positions for a document
sent as a list of text blocks. Here's the shape, for this lesson's chunks:

```python
# Illustrative only: this needs the anthropic package and an API key, so it doesn't run on this page.
# instructions are this lesson's, minus the line asking for [S2] ids: the API does the citing now
documents = [{"type": "document",
              "source": {"type": "text", "media_type": "text/plain", "data": chunk["text"]},
              "title": chunk["section"],
              "context": f"{chunk['doc_id']}, dated {chunk['date']}, {chunk['source_type']}",
              "citations": {"enabled": True}}
             for chunk in results]
response = client.messages.create(
    model=MODEL, max_tokens=1024, system=instructions,
    messages=[{"role": "user", "content": [*documents, {"type": "text", "text": question}]}])

for block in response.content:
    if block.type == "text":
        for citation in block.citations or []:
            # a plain-text document is cited by character positions within it
            chunk = results[citation.document_index]
            print(f"{block.text!r} <- {chunk['doc_id']}: {citation.cited_text!r} "
                  f"(characters {citation.start_char_index} to {citation.end_char_index})")
```

The `title` and `context` go to the model but can't be cited, which makes
`context` the place for the date and type. A search tool can return
results in the same form: a `search_result` block, with a source, a title
and a list of text blocks, can go inside a tool result, so a tool like
[Lesson 11's search](/05-rag-systems/11-agentic-rag/01-from-pipeline-to-tool/#the-tool-designed-like-any-other)
could hand back citable results, and citations to them come back naming the
source and title each result was given. OpenAI's file search tool, which
searches files uploaded to OpenAI, similarly marks its answers with
`file_citation` annotations naming the file drawn on.

What this gains over the `[S1]` scheme:

- **The pointers are guaranteed.** Anthropic's documentation says citations
  are "guaranteed to contain valid pointers to the provided documents", and
  `cited_text` is extracted by the API rather than written by the model. An
  unknown id or an invented quote can't happen, so both checks above come
  built in.
- **Exact spans, without paying for them.** Each citation is tied to the
  part of the answer it supports and to an exact span of the source, and
  `cited_text` doesn't count towards output tokens. Anthropic also reports
  that, in its own evaluations, the feature cites the most relevant quotes
  significantly more often than prompting alone.

And what it costs:

- **It's one provider's format.** The request, the reply and the code that
  reads them are specific to that API. The `[S1]` scheme is plain text: it
  works with any model, and with this course's fake client.
- **Some features don't combine with it.** Citations and structured outputs
  can't be used together: the API returns an error if a request enables
  citations and asks for a JSON output format. The next concept suggests
  [an explicit `"answerable"` field in structured output](/05-rag-systems/10-grounded-answers/03-abstaining-when-retrieval-is-weak/#what-a-threshold-can-t-see);
  with citations on, that has to come some other way.
- **Support is still not checked.** A valid pointer to a real sentence can
  still be a sentence that doesn't support the claim. And text blocks with no
  citations are normal, since connecting words like " and " get their own
  blocks, so spotting a claim with no source takes more than finding blocks
  without citations.

</Subsection>
