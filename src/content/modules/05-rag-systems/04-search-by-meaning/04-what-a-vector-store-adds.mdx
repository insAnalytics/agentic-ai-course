def cluster(matrix: np.ndarray, count: int, rounds: int = 10, seed: int = 0) -> tuple[np.ndarray, np.ndarray]:
    """k-means by cosine: returns each cluster's centre and each row's cluster."""
    centres = matrix[np.random.default_rng(seed).choice(len(matrix), count, replace=False)]
    for _ in range(rounds):
        members = np.argmax(matrix @ centres.T, axis=1)
        for c in range(count):
            if (members == c).any():
                centre = matrix[members == c].mean(axis=0)
                centres[c] = centre / np.linalg.norm(centre)
    return centres, np.argmax(matrix @ centres.T, axis=1)

# indexing: group the chunks once, around 32 centres

<Subsection title="A matrix in memory isn't a database" variant="a">

The search so far is a numpy matrix and a list of chunks, rebuilt every
time the page runs. That's enough to learn how search by meaning works, and
it leaves out three things any real system needs:

- **Keeping the index.** Embedding a corpus is the expensive half. It
  should happen once, and the result should survive a restart.
- **Filtering.** A search usually has conditions: only documents this user
  may read, only this team's runbooks, only pages from this year.
- **Scale.** Scoring every vector is fine for 2,000 chunks and too slow for
  hundreds of millions, and holding them all in memory gets expensive.

A **vector store**, whether a library like FAISS or a database built around
the same ideas, provides these. Each is worth understanding before using
one, because each has a trap.

</Subsection>

<Subsection title="Keeping the index" variant="b">

Saving an index means saving what indexing produced: the vectors, and the
chunks with their metadata. It also means recording how the vectors were
made: the embedding model and its version, the query prefix, and the
chunker's settings. Vectors from two different models can't be compared, so
a question embedded by a new model can't search chunks embedded by the old
one, and when the two models make vectors of the same length,
[nothing reports the mistake](/05-rag-systems/04-search-by-meaning/02-queries-arent-documents/#vectors-from-different-models-don-t-mix).
Changing the model means embedding the whole corpus again, and the record
is what tells you it's needed.

<LiveDemo client:load dataFiles={RAG_BGE_DATA} setupCode={SETUP} code={PERSIST_DEMO} />

The reloaded index answers the same way without a single model call, and a
process that would embed its questions differently stops before searching.
What a real store adds beyond this is the hard part of persistence: adding,
changing and deleting chunks as documents change, without rebuilding
everything. Keeping an index in step with its documents is Module 10's
subject.

</Subsection>

<Subsection title="Filtering, and filtering in the wrong place" variant="a">

Here's the finance-only question from the labelled set, asked by someone in
the `all-staff` group, who may not read the finance page. The filter can go
in two places:

<LiveDemo client:load dataFiles={RAG_BGE_DATA} setupCode={SETUP} code={FILTER_DEMO} />

Filtering **after** taking the top five throws away the two finance chunks
and returns only three results. The reader gets less context, and never
learns there was room for more. With a stricter filter, the list can come
back empty even when plenty of permitted chunks exist. Filtering **before**
ranking lets only permitted chunks compete, so all five places go to text
this reader may see.

Vector stores offer filters for exactly this, but check where a store
applies them. With the approximate search described below, some stores find
a fixed number of nearest candidates first and filter those, which is
filtering after, with the same short or empty lists.
[pgvector](https://github.com/pgvector/pgvector#filtering), for example, filters
after scanning its approximate index: with its default settings, a filter that
matches 10% of rows leaves an HNSW search about 4 results, unless its
iterative scans are switched on. Stores differ, and
versions of the same store differ, so read the documentation and test it
with a strict filter. Two principles follow, and Lesson 13 builds on both:

- **The filter runs before the ranking picks its results,** not after.
- **The filter is code.** The finance chunks were never candidates, so no
  instruction to the model, and no mistake by it, can reveal them.

</Subsection>

<Subsection title="Why scoring everything stops scaling" variant="b">

Exact search scores every vector: 1,968 dot products of 384 numbers per
question, here. At ten million chunks that's nearly four billion
multiplications per question, for one user. **Approximate nearest-neighbour
(ANN)** search skips most of that work by accepting that it will sometimes
miss one of the true top results.

The simplest version groups the vectors in advance. At indexing time,
cluster the chunks around a set of centres. At query time, find the few
centres nearest the question, and score only the chunks in those clusters:

<LiveDemo client:load dataFiles={RAG_BGE_DATA} setupCode={SETUP} code={CLUSTER_DEMO} />

Searching 4 of the 32 clusters scores 9% of the chunks and still finds 88%
of the exact top five. Searching 8 scores 22% and finds 96%. The trade is
tunable, and it's the one every ANN method offers: how much work to do
against how much of the exact answer to find. Any of the missed results
that was a relevant chunk is recall lost.

</Subsection>

<Subsection title="HNSW: searching a graph" variant="a">

The most common approximate method is **HNSW** (hierarchical
navigable small world graphs,
[Malkov and Yashunin, 2016](https://arxiv.org/abs/1603.09320)), the default
index in [Weaviate](https://docs.weaviate.io/weaviate/concepts/vector-index) and the only dense
index in [Qdrant](https://qdrant.tech/documentation/concepts/indexing/). Instead of
clusters, it links each vector to a few of its nearest neighbours, forming
a graph, and builds several layers of these graphs over smaller and smaller
subsets of the vectors.

A search starts in the top layer, where only a few vectors live and each
link covers a long distance. It moves greedily to whichever neighbour is
closer to the question, and when it can't get closer, it drops a layer, to
a denser graph with shorter links, and continues. By the bottom layer it's
in the right neighbourhood, and it keeps a short list of the best
candidates it has seen. Starting from the top is what lets the search time
grow roughly with the logarithm of the number of vectors, rather than in
proportion to it.

Here's HNSW on this lesson's vectors, using FAISS:

```python
import faiss

queries = load_queries()["main"]
chunks = [c for d in load_documents() for c in structured_chunks(d, 200)]
matrix = vectors_for(chunks)
vectors = query_vectors()
query_matrix = np.stack([vectors[q["id"]] for q in queries])

# exact search: every vector scored, as in this lesson
exact = faiss.IndexFlatIP(384)
exact.add(matrix)
_, exact_top = exact.search(query_matrix, 5)

# HNSW: a layered graph, each vector linked to 32 neighbours
hnsw = faiss.IndexHNSWFlat(384, 32, faiss.METRIC_INNER_PRODUCT)
hnsw.add(matrix)
for breadth in [8, 16, 64]:
    # how many candidates the search keeps in play while it walks the graph
    hnsw.hnsw.efSearch = breadth
    _, approx_top = hnsw.search(query_matrix, 5)
    found = sum(len(set(e) & set(a)) for e, a in zip(exact_top, approx_top))
    print(f"efSearch {breadth:>2}: {found / exact_top.size:.0%} of the exact top 5 found")
```

```text
efSearch  8: 96% of the exact top 5 found
efSearch 16: 99% of the exact top 5 found
efSearch 64: 100% of the exact top 5 found
```

*Illustrative: FAISS can't run in this page's sandbox. This was run locally
with faiss-cpu 1.15.1 on the same vectors, and the output is real.*

Keeping 16 candidates in play finds 99% of the exact top five. `efSearch` is
the knob: a wider search is slower and finds more.

</Subsection>

<Subsection title="What each vector costs to store" variant="b">

Every chunk's vector is kept, and for fast search it's kept in memory. This
module's vectors ship as 16-bit floats: 384 numbers of 2 bytes each, 768
bytes a chunk. In memory, numpy works on a 32-bit copy, twice that, which
is why the index saved above took 3.0 MB. For 1,968 chunks that's nothing. For a
hundred million chunks, 768 bytes each is about 77 GB, before any index
structure.

Vectors can be stored more coarsely. Two common ways:

- **8 bits a number.** Scale each dimension so its largest value becomes
  127, round, and keep whole numbers from -127 to 127: half the size of 16
  bits. The 384 scales are stored once, for the whole index.
- **1 bit a number.** Keep only whether each number is positive, packed
  eight to a byte: 48 bytes a vector, a sixteenth of the size. Two such
  vectors are compared by counting the positions where their signs differ.

Here's each, measured against the exact search on the labelled questions.
The first row is the exact search itself, and the last two shrink the
vectors a different way, by keeping only their first numbers:

<LiveDemo client:load dataFiles={RAG_BGE_DATA} setupCode={SETUP} code={QUANTIZE_DEMO} />

Rounding to 8 bits changed nothing here: every question's top five holds
the same chunks as the exact search's, and the same 28 questions are
answered, at half the memory. One bit is much coarser. It finds half of the exact top
five and answers 23. Cutting the vectors does worse than rounding them at
the same size: the first 192 numbers take 384 bytes, like the 8-bit
version, and find only 69% of the exact top five, answering one question
fewer. The first 96 do about as well as 1 bit, at four times the size.

That last result depends on the model. Some models are trained so that the
first numbers of each vector carry the most, and any prefix works as a
smaller vector on its own. They're called **Matryoshka** embeddings, after
the nesting dolls
([Kusupati et al., 2022](https://arxiv.org/abs/2205.13147)). Models built
to be shortened often take it as a setting: OpenAI's text-embedding-3
models, for example, accept the number of dimensions to return. bge-small
wasn't trained this way, and its documentation offers only the full 384,
so cutting its vectors throws away information spread across all of them. Whether a model's vectors can be
shortened is part of its documentation, like its prefix.

</Subsection>

<Subsection title="Search small, then rescore" variant="a">

One bit loses too much to be the whole search, but it makes a good
shortlist. The common pattern has two stages: search the compressed
vectors for more candidates than you need, then score only those with the
full vectors, and keep the best. The compressed vectors stay in memory. The
full ones can stay on disk, since each question reads only its shortlist.

<LiveDemo client:load dataFiles={RAG_BGE_DATA} setupCode={SETUP} code={RESCORE_DEMO} />

A shortlist of 5 is plain 1-bit search, with the same 50% as before.
Shortlisting 50 and rescoring them finds 92% of the exact top five, and 100
finds 96%, while the search itself reads 48 bytes a chunk. The 29 answered
at 50 is one more than exact search, and it's luck. The extra question is
the bare "MON-2002", where exact search's top five are all unrelated pages.
The shortlist happened to leave some of them out, and a relevant chunk
moved up. It's no reason to expect a compressed search to beat an exact
one.

Vector stores offer this as a setting. Qdrant, for example, rescores the
shortlist from its compressed vectors with the original ones, and a factor
it calls
[oversampling](https://qdrant.tech/documentation/manage-data/quantization/)
sets how many more candidates the shortlist holds than the results asked
for.
Hugging Face's measurements of the same idea kept up to about 96% of
retrieval quality with 1-bit vectors and rescoring, on their benchmark
([Shakir, Aarsen and Lee, 2024](https://huggingface.co/blog/embedding-quantization)).
Like approximate search, compression trades some of the exact result for
memory and speed, and the trade is measured the same way: on your labelled
questions, before and after.

</Subsection>

<Subsection title="When a plain matrix is enough" variant="b">

For this corpus, none of that is needed. 1,968 chunks is under a million
multiplications per question, which numpy does almost instantly, and
the result is exact. That holds into the hundreds of thousands of chunks on
an ordinary machine, as long as the vectors fit in memory: a million vectors
of 384 numbers take about 1.5 GB as 32-bit floats, or 384 MB at 8 bits, and
scoring them all takes a fraction of a second.

So the order of decisions is: start with exact search and a matrix, measure
retrieval quality with it, and add approximate search or compressed vectors
when speed or memory at your real size demands it. Then measure again,
because the recall they trade away is recall your labelled questions can
see.

</Subsection>
