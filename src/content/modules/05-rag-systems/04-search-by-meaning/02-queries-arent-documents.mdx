<Subsection title="Two different kinds of text" variant="a">

A search compares two kinds of text that look nothing alike. A query is
short, usually a question, and often phrased the way a person talks: "Which
alerts wake someone up at night?". A chunk is a passage, usually
statements, phrased the way documentation is written: "Outside those hours,
only `RegistryUnreachable` pages."

Some embedding models treat both the same way: one model, one vector for
any text. They're called **symmetric**. Others are trained on pairs of
questions and the passages that answer them, so they learn to place a
question near its answer rather than near other questions. Many of these
**asymmetric** models mark which side a text is on, with a short prefix
before the query, sometimes before the document too. Which prefixes a model
expects, if any, is part of its documentation, and getting it wrong
quietly weakens retrieval. Hosted embedding services often take the side as
a setting instead: [Voyage](https://docs.voyageai.com/reference/embeddings-api)
takes an input type of "query" or "document", and [Cohere](https://docs.cohere.com/reference/embed)
"search_query" or "search_document". It's the same idea without writing the
prefix yourself; Voyage's documentation says it adds a prompt to the text for you.

bge-small, this module's model, is the asymmetric kind. Its documentation
gives one instruction, for queries only: "Represent this sentence for
searching relevant passages: ". Documents get no prefix. Every labelled
question was embedded both ways, and the prefix moves the vectors, though
not far:

<Subsection title="Measuring the instruction" variant="b">

bge-small's authors say they improved this version's retrieval without
the instruction, so it's optional. On our questions, the difference is a
measurement. Two helpers make that and every later comparison in this
lesson short. They're already loaded for every demo and exercise from here
to the end of this lesson:

```python
def meaning_search(chunks: list[dict], queries: list[dict], model: str = "bge-small-en-v1.5", kind: str = "instructed"):
    """search(question, k) by meaning over precomputed vectors. Works only for the labelled questions."""
    index = VectorIndex()
    index.add(chunks, vectors_for(chunks, model=model))
    vectors = query_vectors(model, kind)
    by_question = {q["query"]: vectors[q["id"]] for q in queries}
    return lambda question, k: index.search(by_question[question], k)

def answered_ids(search, queries: list[dict], k: int = 5) -> set:
    """The ids of questions with evidence whose top k results hold every part of the answer."""
    return {q["id"] for q in queries if q["evidence"] and answerable(search(q["query"], k), q)}
```

<Subsection title="Every model has a limit" variant="b">

The deciding difference turned out to be one the scores don't show. When
the vectors were made, every chunk was also counted with each model's own
tokenizer, and compared with the model's input limit:

| Model, chunking | Input limit | Largest chunk | Chunks over the limit |
|---|---|---|---|
| bge-small, structured 200 | 512 tokens | 350 | none of 1,968 |
| bge-small, structured 400 | 512 tokens | 594 | 9 of 1,378 |
| all-MiniLM-L6-v2, structured 200 | 256 word pieces | 350 | 42 of 1,968 |

*Measured offline, with each model's real tokenizer, when the vectors were
made.*

Two things follow:

- **The course's estimate undercounts.** A chunk estimated at 200 tokens
  can be 350 real ones: code, identifiers and punctuation break into more
  tokens than four characters each. Lesson 3 left room for that, and at 200
  it was enough for bge-small.
- **Truncation happened, silently.** With MiniLM, 42 chunks were embedded
  from their beginnings only, and nothing reported it at the time. The same
  would happen to 9 chunks at 400 tokens with bge-small. Checking every
  chunk against the real limit, with the model's own tokenizer, is part of
  building an index, not an extra.

So the module keeps bge-small with its instruction: not because it wins by
a wide margin here, but because it scored at least as well, and its longer
limit holds every chunk the module's chunker makes.

</Subsection>

<Subsection title="Choosing a model beyond this page" variant="a">

This page compared two small, free models, because they're the two whose
vectors ship with it. A real choice starts from many more, and there's a
standard place to find them.

**MTEB**, the Massive Text Embedding Benchmark
([Muennighoff et al., 2022](https://arxiv.org/abs/2210.07316)), scores
embedding models on public datasets across several kinds of task:
retrieval, and also classification, clustering, sentence similarity and
others. It launched with 8 task types, 58 datasets and 112 languages, and
its multilingual extension, MMTEB
([Enevoldsen et al., 2025](https://arxiv.org/abs/2502.13595)), has more than
500 tasks in over 250 languages. Its public leaderboard is the usual place
to find candidates. Three things limit what a rank there tells you:

- **The datasets aren't your documents.** They're public collections, such
  as web search questions, Wikipedia and scientific papers. An internal
  runbook full of its own error codes isn't among them, and
  [the bare "MON-2002"](/05-rag-systems/04-search-by-meaning/03-meaning-against-keywords-measured/#gained-lost-and-how-sure)
  in the next concept shows what that can mean.
- **Some models have seen them.** Many models are trained on the training
  portions of the same datasets the benchmark tests, which flatters their
  scores. The leaderboard now asks for each model's training data and
  reports how much of the benchmark it overlaps.
- **The average hides the column you need.** The headline rank averages
  every kind of task, so a model can rank high on the strength of
  classification or clustering. For search, read the retrieval column.
  MTEB's own authors found that no single model was best at every task.

So a leaderboard makes the shortlist, and your own labelled questions make
the decision, as they did on this page. The shortlist is also shaped by
things no benchmark ranks:

- **Hosted or open.** A hosted model is an API call for every chunk and
  every question: priced per token, your text goes to the provider, and the
  provider decides when the model is updated or retired. An open model,
  like both on this page, runs on your own hardware, with no price per call and
  no text leaving your systems, but you run it.
- **Languages.** bge-small is English-only, as the "en" in its name says.
  Documents or questions in other languages need a multilingual model, and
  a multilingual benchmark to shortlist it from.
- **Input limit.** The check in the previous subsection, done before the
  choice rather than after. Hosted models often accept several thousand
  tokens; OpenAI's text-embedding-3 models take about 8,000. A longer limit
  gives the chunker room. It doesn't make long chunks search better, as
  [the next concept measures](/05-rag-systems/04-search-by-meaning/03-meaning-against-keywords-measured/#settling-the-chunk-size).
- **Dimensions.** Every chunk's vector is stored, and every search
  multiplies through all of them. bge-small makes 384 numbers. OpenAI's
  text-embedding-3-small makes 1,536 by default and text-embedding-3-large
  3,072: four and eight times the memory and arithmetic per chunk.
  [This lesson's last concept](/05-rag-systems/04-search-by-meaning/04-what-a-vector-store-adds/#what-each-vector-costs-to-store)
  measures what smaller vectors cost.
- **What indexing costs.** Embedding the corpus is paid once per chunk, and
  paid again in full whenever the model changes, for the reason the next
  subsection shows.

</Subsection>

<Subsection title="Vectors from different models don't mix" variant="b">

A vector's numbers mean something only to the model that made it. Each
model learns its own coordinates during training, and nothing makes the
17th number of one model's vectors measure what the 17th measures in
another's. But both models here make 384 numbers, so nothing stops a
question embedded by one from searching chunks embedded by the other. Here
is every pairing, on the labelled questions. The last row pairs bge-small's
chunks with bge-small's own question vectors, their 384 numbers put in a
different order: what a model that had learned exactly the same things, but
numbered its coordinates differently, would produce.

<LiveDemo client:load dataFiles={RAG_MINILM_DATA} setupCode={SETUP} code={MIX_DEMO} />

*"top score" is the average score of each question's best result.*

Every row ran, with no error and no warning, and every question got its
five results. The two correct pairings answer 28 and 27. The mixed ones
answer 19 and 17: these two small models evidently share some structure,
so part of each ranking survives. Nothing guarantees that for any other
pair, and the last row shows the general case. It holds the same
information as the first row, and answers nothing.

The scores fall too, to about 0.22 for the mixed pairs and 0.08 for the
reordered one. That's a clue to someone comparing them with the old scores,
but a score has no fixed scale (MiniLM's correct pairing averages 0.562,
bge-small's 0.734), so no threshold flags a mixed index by itself. A mixed
index doesn't look broken. It looks like a somewhat worse search, or like
one that finds nothing relevant. Only a model with a different number of
dimensions fails loudly: the matrix product raises an error at the first
search, which is the better way to fail.

Two things follow:

- **Changing the model means embedding every chunk again.** The new model
  has to read every chunk itself; the old vectors can't stand in. Until every chunk has a
  new vector, a question embedded by the new model can't search the index.
- **The index must record what made its vectors:** the model, its version
  and the query prefix. A new version of a model has new weights, so it's a
  new model as far as its vectors are concerned, and
  [a prefix moves the query vectors](/05-rag-systems/04-search-by-meaning/02-queries-arent-documents/#two-different-kinds-of-text)
  too. This module's vector files each record the model that made them,
  and [keeping the index](/05-rag-systems/04-search-by-meaning/04-what-a-vector-store-adds/#keeping-the-index)
  in this lesson's last concept saves that record alongside the vectors.

On a system that's already serving questions, the swap is a migration:
build the new index alongside the old one, keep answering from the old one
until every chunk has its new vector, then switch both the index and the
query embedding together. Module 10 covers doing that on a live system.

</Subsection>
