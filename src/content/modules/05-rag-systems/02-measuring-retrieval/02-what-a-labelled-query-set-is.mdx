<Subsection title="Questions, with their answers written down first" variant="a">

A labelled query set is a list of questions, each paired with where its
answer is in the corpus. It's the retrieval equivalent of a test suite:
fixed inputs, known correct outputs, and a runner that reports what
passed. This module's set has 57 questions:

<LiveDemo client:load dataFiles={RAG_EVAL_DATA} setupCode={SETUP} code={TYPES_DEMO} />

The 11 held-out questions are kept aside and not looked at until the
module's last lesson;
[reading the numbers honestly](/05-rag-systems/02-measuring-retrieval/04-reading-the-numbers-honestly/#the-held-out-set)
explains why. The types exist because each later lesson targets a
different weakness, and a set that only held easy lookups would say every
technique works. A good set has the shapes of question real users ask,
including the awkward ones.

</Subsection>

<Subsection title="Labelling passages, not chunks" variant="b">

The obvious label is "the answer is chunk 412". It breaks the moment you
change how documents are split, which is exactly what Lesson 3 does: chunk
412 no longer exists, or holds different text. So each label here is a
**quote**, copied exactly from the document that answers the question:

<LiveDemo client:load dataFiles={RAG_EVAL_DATA} setupCode={SETUP} code={EVIDENCE_DEMO} />

Two structural choices are visible in that one query:

- **Alternatives within a group.** The rate limit is stated in both the
  API reference and the changelog. Either passage answers that part, so
  they're listed together as "any one of". Real corpora repeat facts, and a
  label that named only one copy would mark the other as wrong.
- **Several groups.** The question has two parts, the limit and the error,
  and an answer needs both. Each part is its own group, and all groups must
  be found.

A few queries carry extra fields that later lessons use: `history`, for a
follow-up that only makes sense after an earlier exchange; `stale_evidence`,
for a passage that's out of date and contradicts the current answer; and
`access_cases`, saying who should and shouldn't get an answer.

</Subsection>

<Subsection title="Deciding what counts as relevant" variant="a">

A quote is text; a search returns chunks. The rule that joins them: a
chunk is **relevant** to a quote if it comes from the same document and
contains at least half of the quote, unbroken. Those four functions are
already loaded for this whole lesson:

```python
import math

def load_queries() -> dict:
    """The labelled query set: main and held-out queries, each with its evidence."""
    return json.loads(Path("/data/rag/queries.json").read_text(encoding="utf-8"))

def normalize(text: str) -> str:
    return re.sub(r"\s+", " ", text).strip()

def is_relevant(chunk: dict, span: dict) -> bool:
    """True if the chunk comes from the span's document and holds at least half of the quote, unbroken."""
    if chunk["doc_id"] != span["doc_id"]:
        return False
    text, quote = normalize(chunk["text"]), normalize(span["quote"])
    half = math.ceil(len(quote) / 2)
    return any(quote[start:start + half] in text for start in range(len(quote) - half + 1))

def answerable(results: list[dict], query: dict) -> bool:
    """True if, for every evidence group, at least one result is relevant to one of its spans."""
    return all(any(is_relevant(chunk, span) for chunk in results for span in group)
               for group in query["evidence"])
```

Why half, and not the whole quote? Because splitting can cut a quote in
two, and one side should still count if it holds most of it:

<LiveDemo client:load dataFiles={RAG_EVAL_DATA} setupCode={SETUP} code={HALF_DEMO} />

The second part holds the core of the answer, "HTTP 429 with error
REG-1009", and counts. The first part holds only "Requests past the limit
get", and doesn't. Only one side of a cut can hold more than half, so a
split quote is counted at most once, except for a cut exactly through the
middle of a quote with an even number of characters, which leaves both sides
exactly half. That's rare enough to ignore. The rule is a proxy, too: half of
a quote's characters usually carries its core, but that's a judgement about
the labels, not a guarantee.

`answerable` then applies the groups. Here's the rate-limit question
against Lesson 1's keyword search:

Neither part is in the top five. That's a retrieval failure the set now
records, rather than one somebody has to notice.

</Subsection>

<Subsection title="Building the set" variant="b">

How the set was made matters as much as its contents:

- **The labels were written before any retrieval ran.** If you label by
  looking at what your search returned, you label your search's opinion,
  and it will score perfectly against itself.
- **Every quote is checked by code.** Labels are data, and data has bugs:
  a mistyped quote silently matches nothing, and every query using it
  looks like a retrieval failure. This check runs over every label:

<LiveDemo client:load dataFiles={RAG_EVAL_DATA} setupCode={SETUP} code={CHECK_DEMO} />

- **The set is versioned.** When a label is fixed, the version changes, and
  numbers from different versions aren't compared.
  [When the labels are wrong](/05-rag-systems/02-measuring-retrieval/05-when-the-labels-are-wrong/#a-label-that-was-right-and-incomplete)
  shows the first such fix.

</Subsection>

<Subsection title="Where real questions come from" variant="a">

This module's 57 questions were written by one author reading the corpus.
That's where a set starts, not where a team's set should end. An author
writes the questions they can imagine; users ask the ones nobody
imagined, in words nobody chose. Once a system has users, there are
better sources:

- **Query logs.** What people actually typed, misspellings included, in
  the proportions they type it. Logs are also personal data: people paste
  names, account details and secrets into search boxes. Use them only as
  far as your users agreed to, remove or mask what identifies people
  before anyone reads them for labelling, and give the labelled set the
  same access rules as the logs it came from.
- **Support tickets and escalations.** Questions that already went wrong
  once, often with a person's answer attached, which makes labelling
  faster. They over-represent the hard cases, which is useful as long as
  you know it.
- **Fresh samples, on a schedule.** What people ask drifts: a new feature,
  a new error code, a migration everyone is suddenly doing. A set frozen
  at launch slowly turns into a measure of last year's traffic. Add new
  questions regularly and keep the old ones, so each version still covers
  what the last one did.

Each refresh is a new version of the set, and the versioning rule above
still holds: numbers from different versions aren't compared.

</Subsection>

<Subsection title="Questions a model writes" variant="b">

Writing questions by hand is slow, so a common shortcut is to have a model
write them: show it a chunk, ask for a question the chunk answers, and
label the question with that chunk. It's cheap, it scales to every chunk
in the index, and the labels come for free.

It has a known bias. A model that has just read a passage tends to ask
about it in the passage's own words, and keyword search rewards exactly
that. The effect was documented before models wrote questions, with people
who wrote questions while looking at the answer: Lee, Chang and Toutanova
(2019) found that on question sets where the person asking already knew
the answer, a traditional keyword search such as BM25 was enough, while on
questions from people genuinely looking for an answer, learned retrieval
beat it by up to 19 points of exact match.

To see the bias on this corpus, 20 sections were drawn at random from the
company's own documents, and for each one a model was given the section
and the prompt "Write one question a user might ask that this passage
answers." These questions are **model-written**: Claude wrote them for the
course with each section in view, and they're stored with their prompts in
`generated-questions.json`. A second batch, for the same 20 sections, adds
the instruction generators use against this bias: "Don't reuse the
passage's key terms." Each question is labelled with a quote from the
section it was written from, and its quotes pass the same exactly-once
check as the set's own. Everything is scored as before, with Lesson 1's
keyword search at *k* = 5. The last column is the share of a question's
keywords that appear in its labelled section; for a question with several,
the one it shares most with:

<LiveDemo client:load dataFiles={GENERATED_DATA} setupCode={SETUP} code={GENERATED_DEMO} />

The questions written in the passage's own words were answerable 18 times
out of 20. That's far above this set's 19 of 43, and above its 19 of
31 one-part questions, the fairer comparison, since every generated
question has one part. The paraphrased batch, asking about the same 20
sections, found none. The overlap column shows the mechanism: 61% of the
first batch's keywords are in the section, against 45% for this set's
own questions and 9% for the paraphrases. One pair shows it: "Why does my agent
get told to slow down?" copies the FAQ's heading, while "Why is my bot
being throttled?" asks the same thing and shares only "why" with it.

Read this as a demonstration of a documented bias on 20 questions, not as
a benchmark. Neither batch estimates how this search does for real users.
The first flatters keyword search. The second overshoots the other way: it
calls every agent a "bot" and every model an "LLM", words the company's
documents never use. This set's own questions sit between the two: they
were written by someone who knew the documents too, but deliberately in
several shapes, paraphrases included. What follows for a team using
generated questions:

- **Don't let them stand alone.** Mix them with real questions and report
  the two separately, so a flattering batch can't lift the total.
- **Measure the overlap.** It's a few lines of code, and a generated batch
  sharing far more words with its sources than real questions do is a
  warning.
- **Expect missing labels.** A generated question is labelled with the
  chunk it came from, but other passages may answer it too: the API
  reference and the FAQ both explain rate limits. Those are the missing
  labels of
  [when the labels are wrong](/05-rag-systems/02-measuring-retrieval/05-when-the-labels-are-wrong/#a-label-that-was-right-and-incomplete).

Search by meaning, from Lesson 4, is built to close exactly the gap
between those two batches. These questions have no precomputed vectors, so
this page can't test that.

</Subsection>

<Subsection title="What the set can't score" variant="a">

Some query types are in the set for later lessons, and don't fit a
"did the right passage come back?" score:

- **Unanswerable questions** have no evidence. There's nothing to
  retrieve; what matters is that the system declines to answer, which is
  Lesson 10's subject.
- **Follow-up questions** are scored on their own words here, without the
  history, so "What should the second one move to?" is bound to fail.
  Rewriting it using the conversation is Lesson 8's subject.
- **Restricted questions** are scored as if the reader may see everything.
  Whether each reader gets only what they're allowed is Lesson 13's test.
- **Whole-corpus questions**, like "What recurring causes run through our
  incidents?", have evidence groups, but finding the passages is only the
  start: the answer is a synthesis. Lesson 12 is about them.

These still count in this lesson's totals, which is why the totals start
low. Later lessons report the types separately.

</Subsection>
