<Subsection title="A label that was right, and incomplete" variant="a">

Labels are written by a person reading documents, and a person misses
things. This module's first draft labelled "What does REG-1007 mean?" with
one passage: the error-code table's row. That's correct, and it isn't the
only passage that answers the question. Here's the stopword-fixed search
from earlier, scored against both versions of that label:

<LiveDemo client:load dataFiles={RAG_EVAL_DATA} setupCode={SETUP} code={TWO_LABELS_DEMO} />

All three results explain `REG-1007`: the API reference's section on
creating an agent says the request fails with it when the model isn't
allowed on the tier, and its section on errors shows the full error. The
first draft called two of them wrong. Nothing about the search changed
between the two lines of output. Only the labels did, and precision went
from 0.33 to 1.00.

This is the normal state of a labelled set, not a lapse in this one.
Nobody reads 1,145 sections for every question. Every missing label turns
a correct result into an apparent mistake, so incomplete labels make
retrieval look worse than it is, and they make it look worse
*unevenly*.

</Subsection>

<Subsection title="Pooling: judge what the searches found" variant="b">

Reading every section for every question is out of reach, even for a
corpus this size. The standard way through, used by large evaluations such
as TREC for decades, is **pooling**: run several different searches, take
the top results of each, and have a person judge everything in that pool
that isn't labelled yet. Anything no search ranked highly is assumed not
relevant.

Even a small pool is a lot of reading:

<LiveDemo client:load dataFiles={RAG_EVAL_DATA} setupCode={SETUP} code={POOL_DEMO} />

For this course's set, the review pooled the top 20 of the keyword search
and of a second keyword scorer, BM25, which is Lesson 6's subject. Two
shortcuts kept it to a manageable read, and both are judgments, stated
here so they can be checked:

- **For questions about the registry, only the registry's own sections
  were read.** Prometheus and PostgreSQL pages can't describe
  `REG-1007` or `support_agent`.
- **For the six questions about the public documentation, every pooled
  section was considered:** by its heading first, and by its text wherever
  the heading could plausibly hold the answer.

A section was added only if it states the answer, not if it's merely
about the same topic. The review found **19 missing passages across 12
questions**: nine in the main set and three held out. Reviewing the
held-out labels doesn't break the held-out rule: fixing what counts as an
answer chooses no setting, as long as the rule for what counts is the same
for every search. The REG-1007
question gained four. The public-docs questions gained passages from
pages the labels had never mentioned, such as Prometheus's best-practice
page on the `for` clause and Alertmanager's reference for inhibition
rules. That review moved the labels from version 1 to version 2.

</Subsection>

<Subsection title="Pools favour the searches that built them" variant="a">

Pooling has a known bias. A passage gets judged only if one of the pooled
searches ranked it highly. A **new** search that finds a relevant passage
none of them found is scored as if it made a mistake. Studies of TREC's
pools found them reasonably reliable for comparing the systems that took
part (Zobel, 1998), and also that pooled evaluation is inherently biased
against systems that didn't contribute to the pool (Büttcher and
colleagues, 2007).

For this module that matters directly. Both pooled searches match words, and Lesson 4 adds search by meaning, which ranks passages that share no words with the question: exactly the ones a word-matching pool is least likely to contain. So before this lesson was written, a search by meaning, using the embedding model Lesson 4 introduces and run offline, was pooled and judged the same way. It surfaced 18 more missing passages across 12 questions, ten in the main set and two held out, that neither word-matching search had ranked highly: the same fact stated in another document's words, incident timelines that name the affected agent, and glossary definitions in the vendor documentation. That moved the labels to version 3, which every labelled number in this module uses. Scored against version 2, search by meaning would have been penalised for exactly those finds.

The keyword search's own numbers show the other side. Across both reviews, its baseline barely moved: precision@5 went from 0.140 under version 1 to 0.153 under version 3, and the other metrics didn't change at all. Missing labels mattered little to the search that helped find them, and would have mattered most to one that hadn't taken part.

</Subsection>

<Subsection title="What labels can't settle" variant="b">

Three limits stay, however careful the review:

- **Relevance is a judgment.** "States the answer" is a rule a person
  applies, and two people will disagree at the edges. Every label here is
  one reader's judgment.
- **Relevance here is yes or no.** A section that answers the question
  completely and one that answers half of it both count. Metrics with
  graded relevance exist, and they need graded labels, which cost more to
  write.
- **Relevant isn't the same as good.** A retrieved passage can be relevant
  and out of date, like the monitoring guide's rate limit, or relevant and
  planted. What to do with those is for Lessons 10 and 13.

None of this makes the set less useful. It makes it a measuring instrument
with known error: good for comparing searches and finding failures, and
not a certificate of correctness.

</Subsection>
