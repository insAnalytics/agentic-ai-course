FILTER_SCHEMA = {
    "title": {"ops": ["contains"]},

    "date": {"ops": [">=", "<="], "type": "date"},

MATCHES = {
    "=": lambda have, want: have == want,
    "contains": lambda have, want: want.lower() in have.lower(),
    # dates are compared as YYYY-MM-DD text, which sorts in date order
    ">=": lambda have, want: have >= want,
    "<=": lambda have, want: have <= want,

    """True if the chunk meets every filter. It checks nothing: an unknown field or operator raises."""
    return all(MATCHES[f["op"]](chunk[f["field"]], f["value"]) for f in filters)

    everything = len(pipeline.bm25)

    meaning = [c for c in pipeline.meaning.search(vector, everything) if passes(c, filters)][:100]
    candidates = rrf([keyword, meaning])[:depth]
    return sorted(candidates, key=score, reverse=True)[:k]

export const REFERENCE = String.raw`import json
from datetime import date

def validate_filters(reply: str, schema: dict) -> list[dict]:
    """The filters in the model's JSON reply that are safe to apply, normalised. Anything else is dropped."""
    try:
        parsed = json.loads(reply)
    except ValueError:
        return []
    items = parsed.get("filters") if isinstance(parsed, dict) else None
    if not isinstance(items, list):
        return []
    safe = []
    for item in items:
        if not isinstance(item, dict):
            continue
        field, op, value = item.get("field"), item.get("op"), item.get("value")
        # permissions come from the reader, never from the model, whatever the schema says
        if field == "access" or not isinstance(field, str) or field not in schema:
            continue
        rules = schema[field]
        if op not in rules["ops"] or not isinstance(value, str) or not value.strip():
            continue
        value = value.strip()
        if "values" in rules:
            value = value.lower()
            if value not in rules["values"]:
                continue
        if rules.get("type") == "date":
            try:
                value = date.fromisoformat(value).isoformat()
            except ValueError:
                continue
        safe.append({"field": field, "op": op, "value": value})
    return safe

def filtered_search(bm25: BM25Index, text: str, filters: list[dict], k: int = 5) -> list[dict]:
    """BM25's ranking for text, keeping only chunks that pass every filter before the top k is taken.
    If no chunk passes, the unfiltered top k instead."""
    kept = [chunk for chunk in bm25.search(text, len(bm25)) if passes(chunk, filters)]
    return kept[:k] or bm25.search(text, k)

<Subsection title="Some words say which documents count" variant="a">

Part of a question often isn't about meaning at all. "What changed in
v2.4?" is about one version's entry in the changelog. "Incidents since
August" names a period, "what the vendor docs say" a kind of source, "in
the runbook" a document. Those words say which documents count, and every
search in this module treats them as more words to match. Keyword search
fares worst: as
[Lesson 9 found](/05-rag-systems/09-contextual-chunks/02-contextual-retrieval/#measured-through-the-pipeline),
BM25 splits "v2.4" at the dot and searches for "v2", which every changelog
entry contains. Search by meaning ranks other versions' entries far above
v2.4's, because a version number is a small part of what a passage means,
and here it's the part that matters.

The chunks already carry what's needed to apply those limits exactly.
[Every chunk has carried its document's metadata since Lesson 3](/05-rag-systems/03-chunking/03-structure-aware-splitting/#what-every-chunk-carries):
its title, its section path, its date and its source type. A limit on those
is a **filter**, and a filter is exact: a chunk's section either contains
"v2.4" or it doesn't. So the technique is one more model call, which reads
the question and writes filters on the metadata, and a search that applies
them
[before ranking, as Lesson 4 set out](/05-rag-systems/04-search-by-meaning/04-what-a-vector-store-adds/#filtering-and-filtering-in-the-wrong-place),
so that only chunks that pass compete for the places. It's usually called
**self-querying**, LangChain's name for it, or metadata extraction.

The prompt tells the model which fields it may use and what their values
look like:

```text
Some questions limit which documents count: a version, a period, a kind of source or a particular document. Reply with those limits as filters on the documents' metadata, as JSON and nothing else, like {"filters": [{"field": "title", "op": "contains", "value": "Runbook"}]}. The fields are:
- title (op "contains"): titles look like "Incident INC-2041: billing_agent unable to issue invoices" or "Runbook: rotating a registry key".
- section (op "contains"): the heading path, like "Registry changelog > v2.6 — 2026-08-18".
- source_type (op "="): official for the company's own documentation, wiki for the staff wiki, vendor for third-party product documentation such as Prometheus, Alertmanager and PostgreSQL.
- date (op ">=" or "<="): YYYY-MM-DD, the date the document was last updated.
Add a filter only when the question limits which documents count, not for everything it mentions. If it limits nothing, reply {"filters": []}.
```

The last rule matters as much as the fields. A question that mentions an
incident on the way to asking about something else isn't limited to that
incident's report. This code is loaded for every demo and exercise on this
page:

```python

    everything = len(pipeline.bm25)

```

`filtered_pipeline_search` is the module's pipeline with the filter in front
of every stage that takes a top k: keyword search, search by meaning, and
the 30 candidates the reranker reads. `passes` does no checking of its own,
which the third section of this page comes back to.

The question is still what gets searched, because only the labelled
questions have precomputed vectors. A full self-querying setup also takes
the filter's words out of the query: once the filter has kept only v2.4's
entry, "v2.4" has nothing left to do in the search.

  the incident report from third to first by removing the four chunks from
  other documents in the top five, two of them above it.
- **The two questions about "our incidents"** moved furthest, from 28th and
  9th to first. Unfiltered, not one of their top five came from an incident
  report. They're still not answered, because each needs a piece of every
  incident report, which makes them
  [the global questions Lesson 12 takes on](/05-rag-systems/12-graph-rag/01-when-similarity-search-is-the-wrong-shape/#a-question-about-everything).
- **"Rotated in July"** was first either way. Its date filter passed the
  security postmortem because the postmortem is dated 14 July, three days
  after the leak it describes was found. The filter tests when a document
  was last updated, not when the events in it happened, and a report about
  July that was edited in August would have been excluded.
- **The two vendor questions** changed nothing. Vendor documentation is
  1,893 of the 1,968 chunks, so the filter removed only the company's own 75,
  none of which were in the top five.

On this corpus, then, filters help little overall: one question gained. It
has one changelog with five versions and three incident reports, and search
by meaning with a reranker usually finds the right one anyway. Filters
matter where the documents are many and alike, the subject of the last
section.

</Subsection>

<Subsection title="The reply is untrusted" variant="a">

The filters come from a model, and they reach code that decides what the
search may see. The replies above were well-formed, so the demo applied them
as written. These six weren't. They were scripted for this page, each
showing a kind of reply a real model can give, whether by mistake or
because a question steered it:

<LiveDemo client:load dataFiles={FILTER_DATA} setupCode={SETUP} code={UNTRUSTED_DEMO} />

*These replies are scripted to show what can go wrong.*

None of them is caught by `passes`, which applies whatever it's given:

- **Three fail the whole search.** A field the chunks don't have raises
  `KeyError`, a sentence in front of the JSON makes the reply unreadable,
  and the access filter raises only because `access` holds a list. One bad
  filter shouldn't cost the question its search.
- **Three fail silently.** "Official" isn't `official`, so nothing passes.
  A date that doesn't parse is compared as text, and whether that keeps
  nothing or everything depends only on the operator: "last July" sorts
  after every date, and so does "end of July".
- **The access filter matters most.** Whatever it would have done, it has
  no business in the reply. Permissions
  [come from who the reader is](/05-rag-systems/13-permissions/01-permissions-at-retrieval-time/#where-a-reader-s-groups-come-from),
  never from the question or from a model, and this reply is both: a model
  following a question that claims its asker is on the security team. A
  system that builds its permission check from the same list of conditions,
  or merges them field by field, would let the reply replace the reader's
  groups. Checking fields against the schema drops it before anything runs.

Checking fields is the first rule. The full set, which is this concept's
exercise:

- **Only fields the schema lists, and never `access`,** even if someone
  later adds it to the schema. Permissions are applied separately, from the
  reader's identity, always.
- **Only the operators each field allows.**
- **Only values that can be applied:** a known source type, lower-cased; a
  date that parses, written as `YYYY-MM-DD` so it compares correctly; text
  that isn't empty.
- **Drop what fails and keep the rest.** A reply with nothing usable means
  no filters, not no search, the same rule as `split_query` falling back to
  the question.

Structured outputs, which
[Module 1 covered](/01-llm-foundations/10-structured-output-and-tool-calling/02-constrained-decoding/#a-hard-guarantee-not-a-soft-nudge),
can hold the reply to a JSON schema, with the field names and operators as
fixed lists. That removes the malformed replies. It can't remove the wrong
ones, since the guarantee covers the reply's shape and not whether its
values are right, and it doesn't hold for a reply cut off at the token
limit. The checks stay either way.

</Subsection>

<Subsection title="A filter can hide the answer" variant="b">

A valid filter can still be the wrong one. A filter doesn't lower an
excluded chunk's rank; it removes the chunk, and nothing reports that it
did. The "our incidents" filter above already does this once: the security
postmortem is part of that question's answer, and its title says "Security
postmortem", not "Incident", so no search of any depth can find it. The
filter matched the metadata's words, not the idea of an incident.

Here is a mistaken extraction for a labelled question, with the full
pipeline, then three questions written for this demo, with keyword search
only, since new text has no precomputed vectors. This demo builds the
pipeline, so allow a few seconds:

<LiveDemo client:load dataFiles={FILTER_DATA} setupCode={SETUP} code={WRONG_DEMO} />

*The q28 and latency runbook extractions are scripted mistakes; the other
two follow the prompt.*

- **q28 asks a multi-hop question** that mentions INC-2093 on the way to
  asking about an error code. The prompt says not to filter on that, but
  it's an easy mistake. Filtered, the incident's part of the answer comes
  into the top five, and the error code's part, in the error-code reference
  and the monitoring guide, goes out of reach at any depth.
- **"Since August"** works as intended: four chunks pass, all from
  INC-2093's report, and the answer moves from sixth to first.
- **"Since September"** leaves nothing, and here nothing is the truth: no
  incident report is dated after August.
- **"The latency runbook"** leaves nothing by mistake. The model
  paraphrased the title, which is "Runbook: agent latency spike", so no
  title contains the words it wrote.

An empty result is the easy failure to catch: **fall back to the unfiltered
search**. For the runbook question, that gets back the unfiltered results,
no better and no worse than not filtering at all. For September, it returns
older incidents, so the step that writes the answer needs to know the filter
was dropped, or it will present August's incident as September's.

A filter that's wrong but not empty, like q28's, is harder. It would be
convenient if its results were visibly weak, and the demo checks the most
obvious sign: the reranker's best score. Both filters lowered it, the
correct one for v2.4 as well as the mistaken one for q28, so falling back
whenever the filtered best is lower would have thrown away the one question
filters gained. A larger drop separates these two, but two questions can't
set a threshold. Like every other setting in this module, it would be chosen
by measuring on labelled questions, and a question type like q28's, which
names one thing to ask about another, belongs in them.

</Subsection>

<Subsection title="When filters earn their place" variant="a">

Filters gained one question here, and they're the only change in this lesson
that can make an exact promise: "only v2.4", "only since August". That
matters more as a corpus grows:

- **Many versions and dates.** Release notes for every version, documents
  for each product release, tickets going back years. Search by meaning
  can't reliably tell v2.3 from v2.4, or March from August; a filter can.
- **Many similar documents.** A thousand incident reports look alike to
  every search in this module. A filter on the one named in the question
  cuts through them.

Two limits carry over from this page. A filter is only as good as the
metadata it tests: here, dates belong to documents, so the changelog's
entries all share its August date, and a filter for changes "since July"
keeps every one of them, back to January's v2.2. And each extraction is
another model call before every search, though it can share a call with the
rewrite: self-querying usually asks for the search query and the filters in
one reply.

Every change in this lesson sits in a fixed pipeline, between the user's
words and the search. An agent that calls search as a tool, as in
[Lesson 11](/05-rag-systems/11-agentic-rag/01-from-pipeline-to-tool/), writes
its own queries. It already turns a follow-up into a standalone query, and
it can search once per part of a question, or again after reading the first
results. Given a search tool with filter parameters, it chooses the filters
too, and they're model-written arguments like any other: checked the same
way, with no parameter for permissions at all. A separate rewriting or
filtering call in front of an agent's search tool mostly pays twice for the
same work. What carries over are the rules: keep identifiers, add no facts
the question didn't state, check what the model writes before it runs, and
measure what a query change does. And when a question is genuinely
ambiguous, an agent has an option no pipeline has: ask the user what they
meant.

</Subsection>
