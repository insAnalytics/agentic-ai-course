graph = build_graph(load_graph_data()["triples"])
# the named entities: everything except the short phrases extracted as causes and monitoring gaps
NAMES = sorted({s for s, _, _ in graph} | {o for _, r, o in graph if r not in ("root_cause", "monitoring_gap")})

def plain(text: str) -> str:
    """Lowercase words only, so "registry-api", "Registry API" and "registry_api" all read "registry api"."""
    return " ".join(re.sub(r"[^a-z0-9]+", " ", text.lower()).split())

# every way of writing a name that's known in advance: the names themselves, and the alias table
KNOWN = {plain(name): name for name in NAMES} | {plain(alias): name for alias, name in ALIASES.items()}

def link_entities(question: str, floor: float = 0.8, margin: float = 0.05) -> list[tuple[str, list]]:
    """The entities a question names, as (words, [(score, entity), ...]) pairs. Every run of one to three
    words is looked up exactly first, then scored against every known way of writing a name. The best
    runs are kept first, no word is used twice, and a run keeps every entity within margin of its best."""
    words = plain(question).split()
    candidates = []
    for n in (3, 2, 1):
        for start in range(len(words) - n + 1):
            span = " ".join(words[start:start + n])
            if span in KNOWN:
                candidates.append((1.0, n, start, span, [(1.0, KNOWN[span])]))
                continue
            best = defaultdict(float)
            for written, name in KNOWN.items():
                best[name] = max(best[name], difflib.SequenceMatcher(None, span, written).ratio())
            top = max(best.values())
            if top >= floor:
                close = sorted(((score, name) for name, score in best.items()
                                if score >= max(floor, top - margin)), reverse=True)
                candidates.append((top, n, start, span, close))
    links, used = [], set()
    for top, n, start, span, close in sorted(candidates, key=lambda c: (-c[0], -c[1], c[2])):
        if used.isdisjoint(range(start, start + n)):
            used.update(range(start, start + n))
            links.append((span, close))
    return links

def show(question: str, floor: float = 0.8) -> None:
    print(question)
    links = link_entities(question, floor)
    if not links:
        print("   no entity found: answer it with search instead")
    for span, close in links:
        matches = " or ".join(f"{name} ({score:.2f})" for score, name in close)
        print(f'   "{span}" -> {matches}' + ("" if len(close) == 1 else ": too close to call"))

<Subsection title="One hop isn't enough" variant="a">

With the graph built, "which agents stop working if auth-service goes down?"
starts with the edges that point at auth-service:

<LiveDemo client:load dataFiles={RAG_GRAPH_DATA} setupCode={SETUP} code={HOP_DEMO} />

auth-service's direct dependents are two services, registry-api and
payments-gateway, and neither is an agent. The agents are one step further
out: `support_agent` depends on registry-api. That's the chain similarity
search couldn't follow, and in a graph, following it is just a loop. Notice
also what isn't a dependency: `RegistryUnreachable` watches the registry and
INC-2093 affected it, but neither stops working when it fails. The
traversal has to follow only the relations that mean "needs".

</Subsection>

<Subsection title="Walking the chain backwards" variant="b">

"What stops working if X fails?" means following dependency edges backwards,
from X to whatever depends on it, then to whatever depends on those, until
nothing new turns up. That's a **breadth-first search**:

- Start from the failed entity. For each entity reached, look at every edge
  whose object it is, with a dependency relation, `depends_on` or
  `hands_work_to`.
- Each subject found that hasn't been seen before is affected. Record it, and
  explore it in turn.
- Keep a record of *why*: the source chunks of every edge on the way from the
  failure to that entity. That's what the answer cites.
- Stop when there's nothing left to explore. Remembering what's been seen is
  what stops a cycle from looping forever.

Searching breadth-first, nearest entities first, means each entity is reached
by its shortest chain, which is also the shortest explanation of why it's
affected. That's this concept's exercise.

</Subsection>

<Subsection title="What the graph says, and what it doesn't" variant="a">

A traversal answers exactly, and cites every link, but it can only be as good
as the graph it walks:

- **It can't see a dependency that wasn't extracted.** If no chunk says that
  `notes_agent` uses the registry, no traversal will find that it does. The
  graph is a summary of what the documents state, filtered through the
  extraction prompt.
- **It treats every dependency as total.** An edge records that one thing
  needs another, not how badly. If kb-search goes down, `support_agent` loses
  its help-article search but can still look things up in the registry; the
  graph says it's affected, and so is everything that depends on it.
- **Mistakes compound.** A single wrong edge, or a wrong merge, can pull a
  whole branch of the graph into an answer, and a longer chain has more links
  that could be wrong. The cited chunks are what let someone check.

So the traversal's output isn't the final answer. It's a list of affected
entities and the chunks that justify each one, and those chunks go to the
model, through Lesson 10's answer step, like any other retrieved text.

</Subsection>

<Subsection title="Finding where to start" variant="b">

Every traversal on this page starts from a name it's handed:
`affected_by(graph, "auth-service")`. People don't ask questions in the
graph's own names. They write "the auth service", "the registry", or a name
with a typo in it. Before the graph can answer, something has to work out
which of its entities the question means. That's **entity linking**, the question's side of the
entity resolution the previous concept did on the extracted names.

The graph tool at the end of this lesson leaves it to the model: given a name
it doesn't know, the tool says so and lists every name it does know, and the
model tries again. That works with this graph's handful of services and
agents. With thousands of entities, the list wouldn't fit in a tool result,
and the linking has to happen before the traversal. Here's a small linker
over the graph's 20 named entities; the other nine are the cause and gap
phrases, which nobody names in a question. It looks each run of words up
exactly first, among the names and the alias table, and otherwise scores it
by string similarity with Python's `difflib`, keeping only matches above a
**floor**:

<LiveDemo client:load dataFiles={RAG_GRAPH_DATA} setupCode={SETUP} code={LINK_DEMO} />

Each question shows a different case:

- **Exact matches.** "auth-service" matches once case and punctuation are
  ignored, and "the registry" matches through the alias table.
- **A typo.** "paymnts gateway" scores 0.97 against payments-gateway. An exact
  lookup would have found nothing.
- **Ambiguity.** Bare "registry" scores 0.84 against registry-db and 0.80
  against registry-api, too close to pick one. The linker reports both rather
  than guessing, and the agent can ask which was meant, or traverse from each
  and say which answer belongs to which. ("The registry" is different: the
  alias table says what the documents meant by it.)
- **No entity.** "How do I rotate an API key?" names nothing in the graph,
  so it goes to search, where it belongs. So does "Is the login service
  down?", but for a worse reason: if people call auth-service "the login
  service", spelling similarity has no way to know that.
- **A wrong link.** "search" links to the Search team, with a perfect score.
  The alias was written for the extracted names, where "Search" meant the
  team; in a question, it's usually a verb. An exact match is only as good as
  the table behind it.

The floor is what stops the linker from finding an entity in every question.
Lowered to 0.6, it links "which agents" to `research_agent`. Too high, and it
misses typos; too low, and it links ordinary words. Like every threshold in
this module, it's a setting to measure on real questions.

At scale, linking is done by meaning rather than spelling: each entity's name
and description are embedded when the graph is built, and a question is
matched against those vectors, so it can find an entity by what it is, not
how it's spelt. That's how
[Microsoft GraphRAG's local search](https://microsoft.github.io/graphrag/query/local_search/)
starts: it embeds entity descriptions, finds the entities most related to the
question, then gathers their neighbours, relationships, source text and
community reports. This page can't run that for a new question, since the
browser can only compare text that was embedded in advance. Either way, a
link is a guess. A graph tool should say which entity it started from, so
the model, and the reader, can see when the guess was wrong.

</Subsection>
