<Subsection title="One query, two needs" variant="a">

"What is the registry's rate limit, and what error do you get when you go
over it?" asks for two facts that live in different places: the limit in the
API reference, the error in the error-code table. A search ranks chunks by
how well each matches the whole question, and a chunk that matches one half
well can outrank every chunk about the other half. With only a few results
to fill, one part can take them all.

The fix is to search for each part separately, which is
[goal decomposition](/02-the-agent-loop/08-planning-and-decomposition/01-goal-decomposition/#decomposing-before-executing-anything)
applied to a query: one model call splits the question, and each part gets
its own search. This function is loaded for every demo and exercise from
here to the end of the lesson:

```python
def split_query(client, prompt: str, question: str) -> list[str]:
    """Ask the model to split a question into one search query per thing it asks. Falls back to the question."""
    response = client.create([{"role": "user", "content": f"{prompt}\n\nQuestion: {question}"}])
    reply = "".join(block.text for block in response.content if block.type == "text")
    parts = []
    for line in reply.splitlines():
        line = line.strip()
        if line and line not in parts:
            parts.append(line)
    return parts or [question]
```

The reply is read line by line, blank and repeated lines are dropped, and a
reply with nothing usable falls back to the original question, so a failed
split never means no search at all. Here are the labelled set's three
multi-part questions, split:

<Subsection title="Splitting isn't enough: the merge decides" variant="b">

Two sub-queries produce two ranked lists, and only a few chunks go to the
model. How the lists are combined decides whether both parts get a place.
Here are the three questions with BM25 and room for two chunks: searched as
asked, and split with the two lists simply joined end to end:

<LiveDemo client:load dataFiles={RAG_VARIANTS_DATA} setupCode={SETUP} code={MERGE_DEMO} />

As asked, two of the three questions lose their second part. Split and
joined end to end, nothing improves: the first sub-query's results fill both
places before the second sub-query gets a turn. Splitting did its job, the
second list does contain the missing parts, but the merge threw that away.

A fair merge takes turns: the first result from each list, then the second
from each, skipping any chunk already taken. Every part is guaranteed a
place before any part gets two. That's this concept's exercise.

</Subsection>
