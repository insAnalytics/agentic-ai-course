<Subsection title="A scan has no text" variant="a">

Everything so far has relied on the PDF having a text layer: words, stored
as text, with positions. PDFs made by software have one. PDFs made by a
scanner, or by photographing a page, don't: each page is a single picture.
Here's [the support-tiers PDF](/data/rag/pdf/files/P02-support-tiers.pdf)
turned into what a scan would be, a page image and nothing else:

```python
import pypdf
import pypdfium2 as pdfium
import pytesseract

# simulate a scan: render the page to a greyscale image, and save a PDF holding only that image
page = pdfium.PdfDocument("P02-support-tiers.pdf")[0]
image = page.render(scale=200 / 72).to_pil().convert("L")
image.save("P02-scanned.pdf", resolution=200)
print("text layer:", repr(pypdf.PdfReader("P02-scanned.pdf").pages[0].extract_text()))
```

```text
text layer: ''
```

*Illustrative: pypdf, pypdfium2 and Tesseract don't run in this page's
sandbox. Run locally with pypdf 5.9.0, pypdfium2 5.6.0, pytesseract 0.3.13 and
Tesseract 5.3.4 on the committed support-tiers PDF; the output is real.*

An empty string. Every technique in this lesson so far, and every search in
this module, gets nothing from this page. Scanned contracts, signed forms,
older reports and faxed documents are common in real collections, and they
all look like this to an extractor.

</Subsection>

<Subsection title="OCR reads the pixels" variant="b">

**Optical character recognition (OCR)** turns the picture of text back into
text. Tesseract is a widely used free OCR engine. Here it is on the scanned
page:

```python
import time

import pypdfium2 as pdfium
import pytesseract

image = pdfium.PdfDocument("P02-scanned.pdf")[0].render(scale=200 / 72).to_pil().convert("L")
started = time.perf_counter()
text = pytesseract.image_to_string(image)
print(f"OCR took {time.perf_counter() - started:.1f} s for one page\n")
print(text)
```

*Illustrative, run locally as above. The timing is from one machine and will
vary.*

On a clean, 200 dpi scan of a born-digital page, it recovered almost every
word. It also brought back every problem from the first concept, and one
more:

- **Page furniture is back:** the running header and "Page 1" are in the text.
- **Structure is gone:** OCR returns lines, not headings; nothing marks
  "Severity levels" as one. There are no font sizes to rebuild them from, as
  the cleaning concept did, unless you ask the OCR engine for its layout data too.
- **Table lines become characters:** the ruling around cells turns into stray
  `|` marks in some places and nothing in others, so columns are only roughly
  separated.
- **It takes real time:** around two seconds per page here, which is minutes
  for a long report and hours for a large archive.

Quality depends heavily on the scan. Here's the same table row from the same
page, scanned at 200 dots per inch and at 72, a typical low-quality scan:

```python
import pypdfium2 as pdfium
import pytesseract

page = pdfium.PdfDocument("P02-support-tiers.pdf")[0]
for dpi in (200, 72):
    text = pytesseract.image_to_string(page.render(scale=dpi / 72).to_pil().convert("L"))
    row = next(line for line in text.splitlines() if line.startswith("standard"))
    print(f"scanned at {dpi} dpi: {row}")
```

```text
scanned at 200 dpi: standard | 1 hour 1 business day 99.5%
scanned at 72 dpi: standard | 1 hour ‘business day | 99.5%
```

*Illustrative, run locally as above.*

At 72 dpi, the "1" of "1 business day" became a quote mark. It's one
character, and it's exactly the kind of error that turns a correct answer
into a wrong one without anything looking broken. OCR output has to be
checked, at least by sampling, before it's trusted.

Cheap automatic checks find the worst pages before anyone reads a sample:
the number of characters on each page, where almost none means a missing
text layer or a failed OCR run; the share of words that aren't in a
dictionary, where a high share means garbled text; and the OCR engine's own
confidence, which Tesseract reports for every word. The
[recap's exercise](/05-rag-systems/05-document-parsing/06-recap-practice/)
builds the simplest of these, a warning for every page with no text.

</Subsection>

<Subsection title="Layout-aware parsers" variant="a">

Rules like the cleaning concept's, and OCR with cleanup, work when documents follow
simple conventions. Many don't: two columns, sidebars, footnotes, tables
without ruling lines, headings that are only bold. **Layout-aware parsers**
replace hand-written rules with models trained on many document pages to
recognise what each region is.

[Docling](https://github.com/docling-project/docling), from IBM Research and
released under the MIT licence, is a free example. Its documentation describes
page layout analysis, reading order, table structure recognition and OCR for
scanned pages, with output as Markdown or structured JSON, and it runs
locally. It downloads its layout models on first use, which this page's
sandbox can't do, so there's no demo here.
[Marker](https://github.com/datalab-to/marker) and
[MinerU](https://github.com/opendatalab/MinerU) are other open-source
converters in the same vein, combining several models for layout, text,
tables and formulas, with Markdown or JSON as output.

What such a parser changes is where the effort goes: fewer rules to write and
maintain, in exchange for model inference on every page at indexing time,
usually with a GPU for large collections, and output you still need to
spot-check, because models make mistakes too.

</Subsection>

<Subsection title="Vision-language models as parsers" variant="b">

A layout model labels the regions of a page, and other steps read them. A
**vision-language model (VLM)** can do the whole job in one step: given an
image of a page, it writes out what the page says, and it can be asked to
write it as Markdown, with headings marked and tables as tables.

Frontier multimodal models take this directly. Claude and Gemini both accept
a whole PDF in a request, as a content block alongside the text, like the
images in
[Module 1's lesson on non-text inputs](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/04-sending-non-text-inputs/#content-becomes-an-array-of-typed-blocks-not-a-plain-string):

```json
{
  "role": "user",
  "content": [
    {"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": "JVBERi0xLjcK..."}},
    {"type": "text", "text": "Transcribe this document as Markdown. Mark headings with #, write tables as Markdown tables, and leave out running headers and page numbers. Copy the text exactly: don't correct, complete or summarise anything."}
  ]
}
```

*Illustrative request shape for Anthropic's Messages API, not sent from this
page.*

[Anthropic's PDF support documentation](https://platform.claude.com/docs/en/build-with-claude/pdf-support)
says each page is converted into an image, and the page's text is extracted
and provided alongside it, so the model has both. It puts a page's text at
typically 1,500 to 3,000 tokens, with the page image billed on top as an
image. [Google's documentation](https://ai.google.dev/gemini-api/docs/document-processing)
describes Gemini processing PDFs with native vision in the same spirit. A
scan split into page images can be sent as image blocks instead.

The same idea comes in other forms:

- **Open models you run yourself.**
  [olmOCR](https://github.com/allenai/olmocr), from the Allen Institute for
  AI, is a fine-tuned vision-language model with 7 billion parameters that
  turns PDF pages and images into Markdown, released under Apache 2.0.
  [Docling's VLM pipeline](https://docling-project.github.io/docling/usage/vision_models/)
  swaps Docling's separate layout models for one small VLM, such as IBM's
  Granite-Docling, with 258 million parameters.
- **Managed services,** paid per page, with nothing to run:
  [LlamaParse](https://www.llamaindex.ai/llamaparse),
  [Mistral OCR](https://docs.mistral.ai/studio/document-processing/basic_ocr),
  [Azure AI Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0),
  whose layout model can return Markdown, and
  [Amazon Textract](https://aws.amazon.com/textract/features/), which returns
  layout, tables and form fields with a confidence score for each.

A VLM brings a risk that Tesseract doesn't have. Tesseract's errors are
misread characters: a quote mark for a "1", a stray `|`. A VLM writes fluent
text, and it predicts what's likely as well as reading what's there. So its
errors read like correct text: a plausible number that isn't on the page, a
typo quietly "fixed", a sentence completed past where the page cut it off, a
table cell filled in where the page had none. The
[olmOCR paper](https://arxiv.org/abs/2502.18443) reports this kind of
error: models prompted with only the page image were prone to completing
unfinished sentences, or to inventing longer passages where the image was
ambiguous.
Adding the text and positions from the PDF's own text layer to the prompt,
which the authors call document anchoring, gave significantly fewer
hallucinations.

So a VLM's output needs checking against something independent of it. Where
the PDF has a text layer, that's the text layer. Here's `to_markdown`'s
Markdown for the support-tiers page, and the same Markdown edited to carry
three errors of the kinds a VLM makes, each checked for words and numbers the
page's own text doesn't contain:

The faithful version passes, and two of the three errors are caught: the

"business", which the page uses elsewhere. The third error isn't caught. The
priority tier's first response was changed from 15 minutes to 30, and 30 is
on the page, in the severity table, so a check by vocabulary can't see that
it moved. It catches text that isn't on the page, not text in the wrong place.
A stricter check compares table by table, cell by cell, with the extractor's
own tables where they exist. Where there's no text layer at all, as with a
scan, compare with a cheap OCR pass, which errs differently, and look first
where the two disagree; failing that, sample pages by eye, numbers and table
cells first. The cheap checks described for OCR, such as characters per
page, apply here too.

</Subsection>

<Subsection title="Choosing an approach" variant="a">

There's no single best way to ingest documents. Here are the four
approaches side by side. The costs and speeds are relative, not measured,
apart from the OCR timing earlier on this page:

| Approach | What it needs | Cost per page | Speed | What it misses | How it fails |
|---|---|---|---|---|---|
| Text layer and rules, like `to_markdown` | A PDF with a text layer | Almost nothing | Fastest | Anything in an image; layouts the rules don't expect | Visibly and consistently: a missed heading or a scrambled order, on every page laid out alike |
| OCR, then rules | Page images, at a decent resolution | Low, on an ordinary CPU | About two seconds a page here | Structure, which has to be rebuilt; anything that isn't text | Misread characters, more on poor scans; dictionary checks and confidence scores catch some |
| Layout model, like Docling | Model inference, with a GPU for large collections | Moderate | Slower than rules | Layouts unlike the pages it was trained on | A region labelled wrongly: a table split, a heading read as body text |
| Vision-language model | A large model, by API or on your own GPU | Highest | Slowest: it writes out every word | Least, since it reads the whole page as an image | Fluently: text that isn't on the page, with nothing looking wrong |

The right one depends on what the documents are:

- **Born-digital PDFs with simple layouts,** like this lesson's: a plain
  extractor plus rules, like `to_markdown`. Fast, free and fully under your
  control.
- **Scans and photographs:** OCR first, then the same cleaning. Check the
  scan resolution, and sample the output by eye.
- **Complex layouts,** or many different document styles: a layout-aware
  parser, accepting its cost at indexing time.
- **Pages the others get wrong,** such as dense tables, handwriting or poor
  scans: a vision-language model, with its output checked against the text
  layer or an OCR pass, and sampled.
- **Mostly visual documents,** such as charts, diagrams and forms: image
  descriptions, or page-image retrieval like ColPali.

They also combine. One way is to use the cheapest approach that works for
each page, and to send only the pages that fail the cheap checks on to a more
expensive one.

Whichever you choose, the test is the one this module keeps coming back to:
labelled questions over your own documents, measured before and after. An
ingestion step that produces clean-looking text can still lose the one row a
question needs, as the rota showed.

</Subsection>
