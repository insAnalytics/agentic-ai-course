<Subsection title="Chaining: a fixed sequence, with a check in between" variant="a">

[Lesson 1's `run_workflow`](/02-the-agent-loop/01-agents-workflows-and-the-loop/02-agent-vs-workflow-vs-chatbot/#a-workflow-concretely-code-decides-the-sequence)
sketched `summarize` always before `translate` as illustrative `...`
bodies. **Prompt chaining** is that same fixed-sequence pattern, made
real: each step is a genuine scripted call, and the code checks a
step's output before ever starting the next one — not just piping text
through blindly:

<LiveDemo client:load setupCode={FAKE_CLIENT} code={`def run_chain(client, document: str) -> str:
    response = client.create(messages=[{"role": "user", "content": f"Summarize this document: {document}"}])
    summary = response.content[0].text

    if not summary.strip():
        return "Error: summarization produced an empty result, stopping before translation"

    response = client.create(messages=[{"role": "user", "content": f"Translate to French: {summary}"}])
    return response.content[0].text

client = FakeLLMClient(scripted_responses=[
    TextBlock(text="Agentic systems combine planning, tool use, and memory."),
    TextBlock(text="Les systèmes agentiques combinent planification, utilisation d'outils et mémoire."),
])

result = run_chain(client, "... a long document about agentic systems ...")
print(result)`} />

(The fake client's classes are already defined for this demo.) Two
genuinely separate calls happen, in a fixed order the code decided —
never the model. `if not summary.strip():` is the check: a chain that
never inspects a step's output before trusting it with the next one is
just blind piping, not a deliberately engineered sequence.

</Subsection>

<Subsection title="Stopping cleanly when a step's output fails the check" variant="b">

<LiveDemo client:load setupCode={FAKE_CLIENT} code={`def run_chain(client, document: str) -> str:
    response = client.create(messages=[{"role": "user", "content": f"Summarize this document: {document}"}])
    summary = response.content[0].text

    if not summary.strip():
        return "Error: summarization produced an empty result, stopping before translation"

    response = client.create(messages=[{"role": "user", "content": f"Translate to French: {summary}"}])
    return response.content[0].text

client = FakeLLMClient(scripted_responses=[
    TextBlock(text=""),
    TextBlock(text="this second response is never actually requested"),
])

result = run_chain(client, "... a document that produces an empty summary ...")
print(result)
print(f"calls actually made: {client.call_count}")`} />

`client.call_count` stops at **1** — the second, scripted translation
response sits unused. The check caught a bad intermediate result before
wasting a call (and real cost) on translating nothing.

</Subsection>

<Subsection title="Routing: a scripted classification, then dispatch to a fixed path" variant="a">

**Routing** adds a classification step choosing between *fixed*
downstream paths — and that classification is itself a real, scripted
LLM call, not an argument handed in from outside:

<LiveDemo client:load setupCode={FAKE_CLIENT} code={`def handle_billing(request: str) -> str:
    return f"Routed to billing: {request}"

def handle_technical(request: str) -> str:
    return f"Routed to technical support: {request}"

ROUTES = {"billing": handle_billing, "technical": handle_technical}

def run_router(client, request: str) -> str:
    response = client.create(messages=[{"role": "user", "content": f"Classify this support request as exactly 'billing' or 'technical': {request}"}])
    category = response.content[0].text
    handler = ROUTES[category]
    return handler(request)

client = FakeLLMClient(scripted_responses=[TextBlock(text="billing")])
print(run_router(client, "My invoice is wrong"))`} />

`ROUTES[category]` —
[the exact dispatch-dict mechanism from Lesson 4's `TOOL_REGISTRY`](/02-the-agent-loop/04-writing-the-loop-by-hand/03-handling-multiple-tools/#the-fix-a-dict-mapping-names-to-actual-callables)
— dispatches to a handler based on the model's own classification. The
*paths themselves* (`handle_billing`, `handle_technical`) are still
fixed in code, never freely chosen the way
[an agent picks its own next tool](/02-the-agent-loop/01-agents-workflows-and-the-loop/02-agent-vs-workflow-vs-chatbot/#the-same-task-as-an-agent-instead-the-model-decides-the-sequence).
This is exactly the workflow side of that earlier distinction: an LLM
call genuinely happens and genuinely decides *which* path, but the
*set of possible outcomes* was decided when the code was written, not
at runtime.

</Subsection>
