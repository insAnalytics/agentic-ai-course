<Subsection title="The payoff Lesson 8 pointed at" variant="a">

[Lesson 8's dependency graph](/02-the-agent-loop/08-planning-and-decomposition/02-plan-representations/#dependency-graph-prerequisites-not-strict-sequence)
noted that tasks with no dependency on each other could run
concurrently, not just in either sequential order — this concept is
that payoff, actually implemented with
[Module 0's async coverage](/00-python-essentials/07-async-python/03-asyncio-gather/#asyncio-gather-actually-running-things-concurrently):

<LiveDemo client:load code={`import asyncio
import time

async def create_agent_async(name: str, model: str) -> str:
    await asyncio.sleep(0.5)
    return f"created {name} with {model}"

async def main():
    print("calling both concurrently...")
    start = time.perf_counter()
    results = await asyncio.gather(
        create_agent_async("research_agent", "claude-sonnet"),
        create_agent_async("support_agent", "claude-haiku"),
    )
    elapsed = time.perf_counter() - start
    print(results)
    print(f"elapsed: {elapsed:.1f}s")

asyncio.run(main())`} />

`asyncio.gather` runs both calls concurrently, not sequentially — total
time is `~0.5s`, the single longest wait, not `1.0s`, the sum. This is
exactly
[the timing proof from Module 0's asyncio.gather concept](/00-python-essentials/07-async-python/03-asyncio-gather/#asyncio-gather-actually-running-things-concurrently),
now applied to two genuinely independent sub-tasks identified by a
dependency graph, rather than a generic example.

</Subsection>

<Subsection title="The same idea, applied to independent LLM calls themselves" variant="b">

The sub-tasks don't have to be plain function calls — they can just as
easily be independent LLM calls, run concurrently and then combined:

<LiveDemo client:load setupCode={FAKE_CLIENT} code={`import asyncio

async def summarize_async(client, topic: str) -> str:
    await asyncio.sleep(0.1)   # standing in for real network latency
    response = client.create(messages=[{"role": "user", "content": f"Summarize: {topic}"}])
    return response.content[0].text

async def run_parallel_summaries(client, topics: list) -> str:
    summaries = await asyncio.gather(*(summarize_async(client, topic) for topic in topics))
    return " ".join(summaries)

client = FakeLLMClient(scripted_responses=[
    TextBlock(text="Agents plan, act, and observe in a loop."),
    TextBlock(text="Workflows fix the sequence of steps in code."),
])

result = asyncio.run(run_parallel_summaries(client, ["agents", "workflows"]))
print(result)`} />

(The fake client's classes are already defined for this demo.) Neither
summary depends on the other's content, so both requests genuinely
overlap — the *combining* step (`" ".join(summaries)`) only happens
once both are back, which is the whole shape of this pattern: dispatch
several independent calls together, then merge what comes back.

</Subsection>

<Subsection title="The other kind of parallel: several tool calls in one response" variant="a">

There's a second, entirely different form of parallelism this module
already built:
[a single response carrying two or more `tool_use` blocks together](/02-the-agent-loop/05-react-and-reasoning-in-the-loop/01-the-react-pattern/#why-every-tool-call-needs-its-own-result-in-the-same-message),
which Lesson 5's corrected loop dispatches *all* of before replying.
That's not `asyncio.gather` — it's a single model turn requesting
several independent actions at once — but it's the same underlying
idea as this concept: independent work, recognized as independent, run
together rather than one at a time. Two different mechanisms, the same
payoff.

</Subsection>
