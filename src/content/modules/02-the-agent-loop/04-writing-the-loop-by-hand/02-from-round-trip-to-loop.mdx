<Subsection title="The actual loop, written and running for real" variant="a">

[Lesson 1 introduced the loop conceptually](/02-the-agent-loop/01-agents-workflows-and-the-loop/01-the-perceive-reason-act-observe-cycle/),
using an illustrative, pre-scripted sequence of decisions. Using
[the fake client from Concept 1](/02-the-agent-loop/04-writing-the-loop-by-hand/01-the-fake-llm-client/),
this concept writes the real thing — a genuine `while` loop, actually
calling a client, actually executing a tool, actually deciding when to
stop:

<LiveDemo client:load setupCode={FAKE_CLIENT} code={`def get_weather(location: str) -> str:
    return f"It's sunny in {location}."

client = FakeLLMClient(scripted_responses=[
    ToolUseBlock(name="get_weather", input={"location": "Paris"}),
    TextBlock(text="It's sunny in Paris today!"),
])

messages = [{"role": "user", "content": "What's the weather in Paris?"}]

while True:
    response = client.create(messages=messages)
    block = response.content[0]

    if block.type == "tool_use":
        result = get_weather(**block.input)
        messages.append({"role": "assistant", "content": [block]})
        messages.append({"role": "user", "content": [{"type": "tool_result", "tool_use_id": block.id, "content": result}]})
    elif block.type == "text":
        print(f"final answer: {block.text}")
        break

print(f"total messages: {len(messages)}")`} />

(The `FakeLLMClient` and block classes from the previous concept are
already defined for this demo. Note the tool result carries the tool
call's `id` as `tool_use_id`, the pairing
[Module 1's round trip](/01-llm-foundations/10-structured-output-and-tool-calling/05-the-full-round-trip/)
showed a real API requires.)

`get_weather(**block.input)` —
[the exact `**` argument-unpacking mechanism from Module 0](/00-python-essentials/03-functions-and-reuse/02-args-and-kwargs/)
— unpacks `block.input`'s dict directly into keyword arguments, since
`block.input` is exactly `{"location": "Paris"}` and `get_weather` takes
`location` as a parameter. The loop checks `block.type` at each
iteration: `"tool_use"` means execute the tool, append both the request
and result, and keep looping; `"text"` means the model has produced its
actual final answer, and the loop breaks.

</Subsection>

<Subsection title="Deliberately minimal — one hardcoded tool" variant="b">

This loop deliberately only knows about one tool, `get_weather`,
hardcoded directly into the `if` branch. That's a real limitation, worth
naming honestly rather than pretending it isn't there: the moment a
second tool exists, this exact structure doesn't generalize at all —
[exactly what the next concept fixes](/02-the-agent-loop/04-writing-the-loop-by-hand/03-handling-multiple-tools/). This concept's job was getting the
smallest possible *correct* loop actually running, end to end, before
addressing that real gap.

</Subsection>
