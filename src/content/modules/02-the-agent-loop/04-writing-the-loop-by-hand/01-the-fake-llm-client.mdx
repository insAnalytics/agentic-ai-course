A genuine shift from the previous lessons: since there's no real network
call involved, this fake client — and everything built on top of it for
the rest of this module — genuinely runs live in this course's sandbox,
unlike the illustrative-only examples in earlier lessons.

<Subsection title="Why a fake client, and what it actually needs to do" variant="a">

Every exercise from here forward in this module needs a way to run a real
agent loop's *code* against something that behaves exactly like
[a real LLM API's response shapes, from Module 1](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/02-the-response-shape/)
— without making a real, non-deterministic network call. A **fake LLM
client** does exactly this: it mirrors a real client's call pattern and
response structure, but returns a pre-configured, scripted sequence of
responses instead of anything actually generated.

</Subsection>

<Subsection title="A minimal working version" variant="b">

```python
import itertools

_ids = itertools.count(1)

class ToolUseBlock:
    def __init__(self, name: str, input: dict):
        self.type = "tool_use"
        self.id = f"toolu_fake_{next(_ids):02d}"
        self.name = name
        self.input = input

class TextBlock:
    def __init__(self, text: str):
        self.type = "text"
        self.text = text

class FakeResponse:
    def __init__(self, content: list):
        self.content = content

class FakeLLMClient:
    def __init__(self, scripted_responses: list):
        self.scripted_responses = scripted_responses
        self.call_count = 0

    def create(self, messages: list) -> FakeResponse:
        response_block = self.scripted_responses[self.call_count]
        self.call_count += 1
        return FakeResponse(content=[response_block])
```

`ToolUseBlock` and `TextBlock` mirror
[the exact content-block shapes from Module 1's tool-calling coverage](/01-llm-foundations/10-structured-output-and-tool-calling/04-tool-calling/#the-full-shape-concretely)
— `.type`, and either `.name`/`.input` or `.text` — as attribute-style
objects, the way a real SDK hands them back (earlier illustrative
snippets wrote them as plain dicts). `ToolUseBlock` also gets an `.id`,
generated automatically, because a real tool call carries one and its
result has to be sent back with a matching `tool_use_id`, as
[the round trip in Module 1](/01-llm-foundations/10-structured-output-and-tool-calling/05-the-full-round-trip/)
showed. `FakeLLMClient.create()` mirrors a real client's call pattern —
though a real one also takes a model name, `max_tokens`, and so on; this
keeps only what the loop needs — and instead of generating anything, it
simply returns the *next* item from a scripted list, advancing one
position per call.

</Subsection>

The first call returns the scripted tool-use response; the second call
returns the scripted text response — exactly the two-step shape

fully deterministic, known completely in advance.

</Subsection>

<Subsection title="Why this makes grading possible at all" variant="b">

Because the exact sequence of responses is scripted by whoever wrote the
exercise, the loop's *correct* behavior at each step is fully known in
advance — did the code correctly recognize a `tool_use` response and
execute the right tool? Did it correctly append the result and continue?
Did it correctly recognize the `text` response and stop? This is exactly
the right scope for grading in this module: the loop's *structural
correctness*, never whether a model's underlying decision was a good one
— that judgment question belongs to a later module entirely,
[not this one](/02-the-agent-loop/01-agents-workflows-and-the-loop/03-the-honest-case-for-not-using-an-agent/#what-an-agent-s-dynamism-actually-costs).

</Subsection>
