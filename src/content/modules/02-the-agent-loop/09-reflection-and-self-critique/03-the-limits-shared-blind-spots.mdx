<Subsection title="Reflection doesn't bring in a second, independent perspective" variant="a">

[The evaluator-optimizer pattern and the case for a second pass showed real, genuine value in reflection](/02-the-agent-loop/09-reflection-and-self-critique/01-the-evaluator-optimizer-pattern/)
— but there's a category of problem it structurally cannot reliably
catch. The evaluation step isn't an independent check by some other
source of knowledge; it's the *same* model, with the *same* underlying
understanding, being asked a different question about the same content.
If a gap in that understanding caused the original mistake, that
identical gap is very likely present during evaluation too.

The standard partial fix is to make the evaluator less "same": use a
*different* (often stronger) model as the judge, or at least run the
same model in a fresh context, without the generator's reasoning to
anchor it. That genuinely helps. Its limit is that models trained on
similar data share many blind spots, and LLM judges measurably favor
text that resembles their own (a known *self-preference bias*). So a
second model narrows the problem without removing it.

</Subsection>

<Subsection title="Grounded directly in Module 1's hallucination mechanism" variant="b">

[Recall the Einstein example](/01-llm-foundations/04-how-llms-generate-text/04-hallucination-as-a-direct-consequence/#plausible-isn-t-the-same-as-rare-sometimes-it-s-a-popular-misconception):
a popular misconception can genuinely outscore the correct fact during
generation, because it's more heavily represented in training data —
not a random error, a real, systematic pattern in what the model
actually learned. Asking that same model to "check this for accuracy"
doesn't introduce anything new; it's drawing on the exact same learned
pattern, both times:

*(This demo's scripted output is fixed by design — it illustrates the
structural point, not evidence that this specific outcome is likely
with any real model.)*

The mechanism ran completely correctly — a candidate was generated, an
evaluation genuinely happened, the loop returned the evaluated result —
and yet the actual factual error (Einstein's prize was for the
photoelectric effect, not relativity) sailed straight through uncaught.
This isn't a bug in the pattern; it's the honest limit of what
reflection alone can do, when the exact same underlying blind spot
produced both the mistake and the check on it.

</Subsection>

<Subsection title="Not a reason to avoid reflection — a reason not to over-trust it" variant="a">

This doesn't undo
[the earlier concepts' real value](/02-the-agent-loop/09-reflection-and-self-critique/02-when-a-second-pass-helps/)
for omissions, format violations, and checkable inconsistencies —
reflection genuinely helps with exactly that category of problem. What
it isn't is a general reliability guarantee, and it shouldn't be relied
on as the *sole* defense against a model being confidently,
systematically wrong about something it fundamentally doesn't know
correctly. Real grounding — retrieval against verified sources,
tool-checked facts — is a genuinely different, more robust defense
against that specific category of problem, covered properly in later
modules (the RAG Systems module), not something reflection alone was
ever going to solve.

</Subsection>

<Subsection title="The strongest check an agent has: feedback from the world" variant="b">

There's a kind of second pass that doesn't share the model's blind
spots at all, because it doesn't ask a model anything: **check the work
by doing something with it.** Run the code's tests. Execute the query
and look at what comes back. Call the API and see whether the booking
exists. The result comes from the world, not from the model's opinion of
its own output, so a gap in the model's knowledge can't quietly approve
it.

This is exactly what an agent can do and a plain chat model can't,
because an agent has tools. The loop has the same shape as the
evaluator-optimizer pattern; only the evaluator changes:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`def run_tests(code: str) -> str | None:
    """Run the candidate for real. Returns None if every check passes, or the failure."""
    namespace = {}
    try:
        exec(code, namespace)
        assert namespace["price_with_tax"](100) == 120, "price_with_tax(100) should be 120"
        assert namespace["price_with_tax"](0) == 0, "price_with_tax(0) should be 0"
    except Exception as e:
        return f"{type(e).__name__}: {e}"
    return None

def generate_and_test(generation_client, prompt: str, max_attempts: int = 3) -> str:
    current_prompt = prompt
    for attempt in range(max_attempts):
        candidate = generation_client.create(messages=[{"role": "user", "content": current_prompt}]).content[0].text
        failure = run_tests(candidate)      # the world is the evaluator
        if failure is None:
            return candidate
        print(f"attempt {attempt + 1} failed its tests: {failure}")
        current_prompt = f"{prompt}\\n\\nPrevious attempt:\\n{candidate}\\nTest failure: {failure}\\nPlease fix it."
    return f"Error: no candidate passed the tests after {max_attempts} attempts"

generation_client = FakeLLMClient(scripted_responses=[
    [TextBlock(text="def price_with_tax(price):\\n    return price * 0.2")],
    [TextBlock(text="def price_with_tax(price):\\n    return price * 1.2")],
])
print(generate_and_test(generation_client, "Write price_with_tax(price), adding 20% tax."))`} />

*(Scripted, as before. `exec` here stands in for a proper sandbox,
which [Module 3's code execution lesson](/03-tool-design-for-agents/08-code-execution-as-a-tool/00-intro/)
covers.)*

The first attempt returned the tax instead of the price with tax. A
model judging its own code might well have read it and approved it. The
test didn't need to understand anything: 100 went in, 20 came out, and
the failure message says precisely what was expected. That specific,
factual critique is also a much better thing to revise from than a
model's general impression.

Research backs up how much this matters. Huang et al. (2023), "Large
Language Models Cannot Self-Correct Reasoning Yet", found that asking a
model to review and correct its own reasoning, *without* any feedback
from outside, often didn't improve its answers and sometimes made them
worse. The self-correction results that hold up tend to have an external
signal behind them: tests, a tool's output, a checkable fact. So when an
agent's work can be checked by doing, prefer that to asking. Keep model
judges for the qualities nothing can execute, like whether a summary
reads well. And remember that the world is only as good a judge as the
checks you write: code that passes weak tests is still wrong.

</Subsection>
