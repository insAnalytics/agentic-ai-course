<Subsection title="The check that couldn't be deterministic" variant="a">

[Lesson 6's goal-state check](/02-the-agent-loop/06-termination-failure-and-control/04-goal-state-termination-checks/#a-deterministic-check-on-real-state)
was deliberately scoped to a *deterministic*, code-side condition — "does
this agent name now exist in the registry," something a plain `if`
statement can verify directly. Not every success condition is checkable
that way — "does this summary actually read well and cover the key
points" isn't something code can evaluate mechanically at all. That's
exactly the gap this concept closes: the **evaluator-optimizer pattern**,
where the *model itself* judges whether a candidate output satisfies
explicit criteria.

</Subsection>

<Subsection title="The pattern: generate, evaluate, revise, repeat" variant="b">

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`class EvaluationBlock:
    def __init__(self, passed: bool, critique: str = ""):
        self.type = "evaluation"
        self.passed = passed
        self.critique = critique

generation_client = FakeLLMClient(scripted_responses=[
    [TextBlock(text="Our product helps businesses manage inventory.")],
    [TextBlock(text="Our cloud-based inventory management software helps small businesses track stock levels, automate reordering, and reduce waste in real time.")],
])

evaluation_client = FakeLLMClient(scripted_responses=[
    [EvaluationBlock(passed=False, critique="Too vague -- doesn't mention specific features or the target audience.")],
    [EvaluationBlock(passed=True)],
])

def run_evaluator_optimizer(generation_client, evaluation_client, prompt: str, criteria: str, max_attempts: int = 3) -> str:
    current_prompt = prompt
    for attempt in range(max_attempts):
        gen_response = generation_client.create(messages=[{"role": "user", "content": current_prompt}])
        candidate = gen_response.content[0].text

        # the evaluator gets the task and explicit criteria, not just the candidate
        eval_message = f"Task: {prompt}\\nCriteria: {criteria}\\nCandidate: {candidate}\\nDoes the candidate meet every criterion? If not, say which it misses and why."
        eval_response = evaluation_client.create(messages=[{"role": "user", "content": eval_message}])
        evaluation = eval_response.content[0]

        if evaluation.passed:
            return candidate
        print(f"attempt {attempt + 1} failed evaluation: {evaluation.critique}")
        current_prompt = f"{prompt}\\n\\nPrevious attempt: {candidate}\\nCritique: {evaluation.critique}\\nPlease revise."
    return f"Error: no passing candidate produced after {max_attempts} attempts"

result = run_evaluator_optimizer(
    generation_client, evaluation_client,
    "Write a one-sentence product description.",
    criteria="Names the kind of product, at least one concrete feature, and who it is for.",
)
print(result)`} />

(The updated fake client is already defined for this demo;
`EvaluationBlock` is new.) `EvaluationBlock` is a teaching stand-in, not
a real API block type: in practice an evaluation arrives as structured
output, such as a JSON object with a pass/fail field and a critique.

Look at what the evaluator is sent: the original task, the **criteria**
a good answer must meet, and the candidate. All three matter. An
evaluator that only sees "Evaluate this: …" has nothing to check
against, so it falls back on a vague sense of "good", which is exactly
the open-ended judgment this pattern is meant to avoid. Writing the
criteria down, as concrete and checkable as you can make them, is most
of the work of a useful evaluator. It's also what makes a critique
actionable: "misses the target audience" gives the next attempt
something specific to fix.

The first candidate fails — the critique becomes part of the prompt for
the *next* attempt, exactly
[the scaffolding-through-context effect from Lesson 2's chain-of-thought](/02-the-agent-loop/02-prompting-fundamentals/04-chain-of-thought-prompting/#the-fix-asking-for-the-reasoning-explicitly),
now applied to feeding a critique forward rather than an intermediate
reasoning step. The second, revised candidate passes, and the loop returns
it —
[`max_attempts`, the same backstop pattern from Lesson 6](/02-the-agent-loop/06-termination-failure-and-control/02-max-steps/#the-simplest-possible-guard-a-hard-cap-unconditionally),
catches the case where a passing candidate is never actually produced.

</Subsection>

<Subsection title="Two genuinely different kinds of check" variant="a">

Worth holding side by side: Lesson 6's `if target_agent_name in
tools._registry` and this concept's `evaluation.passed` are answering
fundamentally different questions. One is a fact about real, external
state, checkable with certainty by ordinary code. The other is a
judgment call — genuinely requiring the kind of qualitative assessment
only a model (or a human) can make. Neither is a substitute for the
other; they fit different kinds of success conditions entirely.

</Subsection>
