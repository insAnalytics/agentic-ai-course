    serializable = []
    for message in messages:
        content = message["content"]
        if isinstance(content, list):
            content = [block.to_dict() if hasattr(block, "to_dict") else block for block in content]

<Subsection title="The pain: the scratchpad isn't plain JSON-serializable data" variant="a">

Saving the scratchpad to a file — needed for checkpoint and resume,
covered next — means converting it to text first, and
[JSON is the natural choice](/00-python-essentials/06-files-errors-and-validation/02-working-with-json/#json-is-just-text-and-it-maps-directly-onto-dicts-and-lists).
But the scratchpad's assistant-turn entries contain real Python objects —
`ThinkingBlock`, `ToolUseBlock` instances — not plain dicts:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`import json

    {"role": "user", "content": "What's the weather in Paris?"},
    {"role": "assistant", "content": [ThinkingBlock(thinking="I should check."), ToolUseBlock(name="get_weather", input={"location": "Paris"})]},
]

json.dumps(messages)`} />

(The fake client's block classes are already defined for this demo. The
crash is the point: run it and it ends in a `TypeError`.)

This is a related but genuinely different failure from
[Module 0's JSON coverage](/00-python-essentials/06-files-errors-and-validation/02-working-with-json/#when-the-json-itself-is-malformed-jsondecodeerror)
— that was about *parsing* malformed JSON text; this is the reverse
direction, *serializing* something that was never JSON-shaped data to begin
with.

</Subsection>

<Subsection title="The fix: a to_dict() method, and a helper that applies it" variant="b">

Give each block class a `to_dict()` method converting it into a plain,
JSON-serializable dict, then write a helper that walks the scratchpad,
applying that conversion wherever it's actually needed:

<LiveDemo client:load code={BLOCKS + "\n" + SERIALIZE + `
messages = [
    {"role": "user", "content": "What's the weather in Paris?"},
    {"role": "assistant", "content": [ThinkingBlock(thinking="I should check."), ToolUseBlock(name="get_weather", input={"location": "Paris"})]},
]

import json
serialized = serialize_messages(messages)
print(json.dumps(serialized, indent=2))`} />

(This demo defines its own copies of the block classes so it runs on its
own. `ToolUseBlock` keeps its `id` in `to_dict()`, because a saved scratchpad
that dropped it would leave every later `tool_result` pointing at a tool
call that no longer has an `id` to match.)

`hasattr(block, "to_dict")` — Python's built-in check for whether an
object has a given attribute — correctly handles a *mixed* content list: a
real `ThinkingBlock`/`ToolUseBlock` gets converted via `.to_dict()`, while
an already-plain dict (like a `tool_result` entry, built directly as a
dict from the start) passes through unchanged, since it has no `to_dict`
method to call at all.

Worth knowing for when this stops being a fake client: a real SDK's
response objects (Claude's `ToolUseBlock`, `TextBlock`, and the rest)
are actually Pydantic models under the hood, so they already come with
[`.model_dump()`](/00-python-essentials/05-typed-data-models/04-pydantic-fundamentals/#getting-the-data-back-out-model-dump)
built in — no hand-written `to_dict()` needed at all. This lesson still
writes `to_dict()` by hand because it's teaching *why* serialization is
necessary and what it actually has to do, not because a real project
would reimplement something Pydantic already provides for free.

There's a second reason to prefer `.model_dump()` with a real model: it
keeps *every* field. A real thinking block carries a `signature`, which
[the API checks when the block is sent back](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/06-reasoning-output-in-responses/#sending-thinking-back-leave-it-exactly-as-it-came).
A hand-written `to_dict()` that saves only the `thinking` text, like the
teaching one here, would produce a checkpoint that looks complete but
can't be resumed with a thinking model: the restored blocks no longer
match what the model produced. Whatever you use, a saved scratchpad has
to round-trip byte for byte.

</Subsection>
