<Subsection title="Why this matters: interrupted work shouldn't mean starting over" variant="a">

A long-running task, interrupted partway through — a crash, a planned
pause, a process restart — shouldn't mean redoing every step already
completed,
[re-paying real cost for work already done](/01-llm-foundations/11-quantization-cost-and-operational-concerns/03-token-based-pricing/#the-basic-pricing-mechanics).
Saving the scratchpad periodically, and being able to load it back to
resume exactly where things left off, is the fix — a direct application of
[Module 0's file I/O](/00-python-essentials/06-files-errors-and-validation/01-file-io-and-context-managers/#with-guaranteed-cleanup-even-on-exception),
combined with
[the earlier serialization concept](/02-the-agent-loop/07-agent-state-and-the-scratchpad/02-serializing-state/#the-fix-a-to-dict-method-and-a-helper-that-applies-it).

</Subsection>

<Subsection title="Saving and loading" variant="b">

```python
import json

def save_checkpoint(messages: list, filepath: str) -> None:
    serialized = serialize_messages(messages)
    with open(filepath, "w") as f:
        json.dump(serialized, f, indent=2)

def load_checkpoint(filepath: str) -> list:
    with open(filepath, "r") as f:
        return json.load(f)
```

Worth noticing what `load_checkpoint` *doesn't* need to do: it doesn't
reconstruct `ThinkingBlock`/`ToolUseBlock` objects from the saved dicts
— resuming the loop only ever needs `messages` to be valid,
re-sendable data going forward, not the exact original Python objects.
Serialization is genuinely a one-way trip; nothing about resuming
requires reversing it.

</Subsection>

(The fake client, its block classes with a `to_dict()` each, and
`serialize_messages` from the serializing-state concept are already defined for this demo.
The tool result carries its call's `id` as `tool_use_id` as before, and
because `to_dict()` keeps the tool call's `id`, that pairing survives the
trip through the file.)

The second "session" — a completely fresh client, only holding the
*remaining* scripted response — never redoes the `get_weather` call at
all. It resumes with all three already-recorded messages loaded
directly from the file, and produces the correct final answer using
exactly that resumed state, precisely as though the first session had
simply continued uninterrupted.
