<Subsection title="The simplest possible guard: a hard cap, unconditionally" variant="a">

The most basic fix for
[the previous concept's pain](/02-the-agent-loop/06-termination-failure-and-control/01-the-pain-a-loop-that-never-stops/):
a hard limit on the number of loop iterations, enforced by the code
itself, regardless of what the model wants to keep doing. Once the cap is
reached, the loop stops — cleanly, not via a crash — whether or not the
task was actually completed.

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`def get_weather(location: str) -> str:
    return f"It's sunny in {location}."

def run_agent_loop(client, messages, max_steps: int = 10):
    for step_count in range(1, max_steps + 1):
        response = client.create(messages=messages)
        messages.append({"role": "assistant", "content": response.content})

        tool_calls = [block for block in response.content if block.type == "tool_use"]
        if not tool_calls:
            return "".join(block.text for block in response.content if block.type == "text")

        results = []
        for call in tool_calls:
            output = get_weather(**call.input)
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": str(output)})
        messages.append({"role": "user", "content": results})
    return f"stopped after reaching the maximum of {max_steps} steps without a final answer"

repeated_responses = [[ToolUseBlock(name="get_weather", input={"location": "Paris"})] for _ in range(20)]
client = FakeLLMClient(scripted_responses=repeated_responses)

result = run_agent_loop(client, [{"role": "user", "content": "What's the weather in Paris?"}], max_steps=10)
print(result)`} />

(As before, the fake client is already defined for this demo, and each
tool result carries its call's `id` as `tool_use_id`.)

`for step_count in range(1, max_steps + 1)` —
[the same `range()` pattern already covered back in Module 0](/00-python-essentials/01-python-basics/02-control-flow-and-syntax/#for-loops-iterate-over-values-not-a-counter)
— caps the loop at exactly `max_steps` iterations. Against the exact same
20-item repeated-call scenario
[from the previous concept](/02-the-agent-loop/06-termination-failure-and-control/01-the-pain-a-loop-that-never-stops/#watching-it-actually-happen),
this version stops cleanly after 10 steps with a clear, informative
message — no crash, no `IndexError`, and critically, this now works
identically against a real model that could otherwise continue
indefinitely, not just against a finite demo script.

</Subsection>

<Subsection title="The honest limitation: max steps can't tell useful work from waste" variant="b">

Worth being direct about what this fix doesn't do: `max_steps` treats
every situation identically once the count is reached, regardless of
*why* it took that many steps. A task that genuinely needed 15 steps of
real, productive work and a task that looped uselessly on the exact
same pointless call for 15 steps both get cut off at the same fixed
number, with the exact same generic message — max steps has no way to
distinguish "this agent is making real progress and just needs more
room" from "this agent is stuck and will never actually finish." A
sharper fix — one that can actually notice *why* a loop might be
stuck, not just *how long* it's been running — is
[covered next](/02-the-agent-loop/06-termination-failure-and-control/03-repeated-action-detection/).

</Subsection>
