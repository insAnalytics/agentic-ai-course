<Subsection title='A sharper signal than "too many steps"' variant="a">

[Max steps, from the previous concept](/02-the-agent-loop/06-termination-failure-and-control/02-max-steps/#the-simplest-possible-guard-a-hard-cap-unconditionally),
only notices a problem after a fixed count is reached — regardless of
what actually happened along the way. **Repeated-action detection**
notices something more specific and genuinely diagnostic: the *exact
same* tool call — same name, same arguments — happening more than once.
That's a strong, concrete signal the loop is stuck, catchable far earlier
than any fixed step count would ever trigger.

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`def get_weather(location: str) -> str:
    return f"It's sunny in {location}."

def run_agent_loop(client, messages, max_steps: int = 10):
    seen_calls = []
    for step_count in range(1, max_steps + 1):
        response = client.create(messages=messages)
        messages.append({"role": "assistant", "content": response.content})

        tool_calls = [block for block in response.content if block.type == "tool_use"]
        if not tool_calls:
            return "".join(block.text for block in response.content if block.type == "text")

        results = []
        repeated = None
        for call in tool_calls:
            current_call = (call.name, call.input)
            if current_call in seen_calls:
                # don't run it again, but still answer it: every tool_use needs a tool_result
                repeated = call.name
                results.append({"type": "tool_result", "tool_use_id": call.id, "content": "Error: this exact call was already made, so it wasn't run again"})
                continue
            seen_calls.append(current_call)
            output = get_weather(**call.input)
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": str(output)})
        messages.append({"role": "user", "content": results})
        # stop only once every call in this response has its result
        if repeated:
            return f"stopped after detecting a repeated call to {repeated} with the same arguments"
    return f"stopped after reaching the maximum of {max_steps} steps without a final answer"

repeated_responses = [[ToolUseBlock(name="get_weather", input={"location": "Paris"})] for _ in range(20)]
client = FakeLLMClient(scripted_responses=repeated_responses)

result = run_agent_loop(client, [{"role": "user", "content": "What's the weather in Paris?"}], max_steps=10)
print(result)`} />

(The fake client is already defined for this demo, and each tool result
carries its call's `id` as `tool_use_id`, as before.)

`current_call = (call.name, call.input)` builds a tuple; `current_call
in seen_calls` checks it against every previously-seen call — this
works correctly on a plain list, without needing anything more exotic,
since Python's `in` operator on a list checks equality (`==`) between
items, and
[dicts already support direct equality comparison](/00-python-essentials/02-collections/03-dicts/)
— no special hashable representation is needed. Against the exact same
scenario from the earlier two concepts, this version stops after just **2**
steps — the first call gets recorded, the second identical call triggers
the detection immediately — instead of running all the way to the
`max_steps=10` limit.

Notice *where* the loop stops. The repeated call isn't run, but it still
gets a `tool_result`, and the loop only returns after that step's results
have been appended. Returning the moment the repeat is spotted would
leave that `tool_use` block, and any other calls in the same response,
without results, which breaks
[the rule that every call gets its own result in the very next message](/02-the-agent-loop/05-react-and-reasoning-in-the-loop/01-the-react-pattern/#why-every-tool-call-needs-its-own-result-in-the-same-message).
Nothing notices while the run ends here, but the moment anyone continues
that conversation, by resuming it or handing it back to the user, a real
API rejects it.

Answering the repeat with an error also opens a gentler option than
stopping at all: send that result back and let the loop go on. The model
sees "this exact call was already made", which is often enough for it to
change course, and the loop only gives up if it keeps happening. That's
[the errors-as-observations idea later in this lesson](/02-the-agent-loop/06-termination-failure-and-control/05-tool-errors-as-observations/)
applied to a guard. This concept stops on the first repeat because it's
the simplest rule to see working.

One caveat before relying on this: an identical repeat isn't always a
sign of being stuck. Polling a job's status, or re-checking after a
write (check → create → check again to verify), legitimately repeats
the exact same call once the world has changed in between. Real
implementations usually loosen the rule: allow a small number of
repeats before stopping, or only flag a repeat when its result was also
identical to last time.

</Subsection>

<Subsection title="Complementary, not a replacement for max steps" variant="b">

Repeated-action detection catches one specific, diagnosable pattern —
exact repetition — but it doesn't catch every way a loop could fail to
make real progress; an agent bouncing between several *different*,
still-unproductive calls would slip right past it. `max_steps` remains
a necessary backstop regardless — a hard ceiling that catches whatever
repeated-action detection doesn't, even if it's slower and less
specific about *why* it's stopping.

</Subsection>
