<Subsection title="Decompose, dispatch to many, aggregate" variant="a">

Genuinely distinct from both prior patterns: routing picks *one* fixed
path; orchestrator-workers decomposes a task into several sub-tasks —
[the same shape as Lesson 8's `PlanBlock`](/02-the-agent-loop/08-planning-and-decomposition/01-goal-decomposition/#decomposing-before-executing-anything)
— dispatches *all* of them to workers, and aggregates the results into
one output.

<LiveDemo client:load code={`import asyncio

async def worker(sub_task: str) -> str:
    await asyncio.sleep(0.3)
    return f"completed: {sub_task}"

async def run_orchestrator(sub_tasks: list) -> str:
    worker_results = await asyncio.gather(*(worker(task) for task in sub_tasks))
    return "\\n".join(worker_results)

sub_tasks = ["Create research_agent", "Create support_agent", "Create billing_agent"]
summary = asyncio.run(run_orchestrator(sub_tasks))
print(summary)`} />

Each worker has a fixed job — run its one sub-task, report back — never
deciding what to do next dynamically the way
[a full agent loop from Lesson 4 onward](/02-the-agent-loop/04-writing-the-loop-by-hand/00-intro/)
would. This is genuinely different from a full agent loop, not a
smaller version of one: the sub-tasks are already known upfront,
[Concept 2's parallel dispatch](/02-the-agent-loop/10-workflow-patterns/02-parallelization/)
runs them together, and aggregation is a final, fixed join step — no
open-ended decision-making anywhere in the structure.

</Subsection>
