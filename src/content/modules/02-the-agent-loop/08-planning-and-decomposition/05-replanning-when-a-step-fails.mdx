<Subsection title="More than just retrying the failed step" variant="a">

[Lesson 6 covered a single step failing in isolation](/02-the-agent-loop/06-termination-failure-and-control/05-tool-errors-as-observations/#the-fix-catch-it-and-let-the-model-see-it)
— retry with backoff, or a graceful give-up. In a plan-and-execute agent,
a step failing has an *additional* consequence a reactive loop never had
to worry about: the plan's *remaining* steps might have been built on an
assumption that just turned out to be wrong, making them invalid too —
not just the one step that failed.

</Subsection>

<Subsection title="The scenario: a plan built on a false assumption" variant="b">

A plan assumes `"Create research_agent"` will succeed, and its second
step, `"Configure research_agent's model"`, was written expecting that
first step to have actually happened. But execution reveals
`research_agent` already exists — a definitive conflict,
[exactly like Lesson 6's failure case](/02-the-agent-loop/06-termination-failure-and-control/05-tool-errors-as-observations/#the-pain-an-unhandled-tool-error-crashes-the-entire-loop),
not something retrying would fix. Simply skipping the failed step and
continuing to step two isn't safe either — step two's own assumptions may
no longer hold.

</Subsection>

<Subsection title="The fix: call the planner again, with what was actually learned" variant="a">

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`class PlanBlock:
    def __init__(self, sub_tasks: list):
        self.type = "plan"
        self.sub_tasks = sub_tasks

class FailureBlock:
    def __init__(self, reason: str):
        self.type = "failure"
        self.reason = reason

def run_plan_execute_replan(planning_client, execution_client, goal: str) -> list:
    plan_response = planning_client.create(messages=[{"role": "user", "content": goal}])
    plan = plan_response.content[0]
    results = []

    remaining_tasks = list(plan.sub_tasks)
    while remaining_tasks:
        sub_task = remaining_tasks.pop(0)
        done = "; ".join(str(r) for r in results) or "nothing yet"
        step_message = f"Goal: {goal}\\nDone so far: {done}\\nYour step: {sub_task}"
        response = execution_client.create(messages=[{"role": "user", "content": step_message}])
        result_block = response.content[0]

        if result_block.type == "failure":
            print(f"step failed: {result_block.reason} -- replanning remaining work")
            replan_response = planning_client.create(messages=[
                {"role": "user", "content": f"Original goal: {goal}. Done so far: {done}. The step '{sub_task}' failed: {result_block.reason}. What should the remaining steps be?"}
            ])
            new_plan = replan_response.content[0]
            remaining_tasks = list(new_plan.sub_tasks)
            print(f"revised plan now has {len(remaining_tasks)} remaining steps")
        else:
            results.append(result_block.text)
    return results

])

(The updated fake client is already defined for this demo, and `PlanBlock`
is repeated from earlier so it runs on its own.)

`remaining_tasks = list(new_plan.sub_tasks)` — this is the actual
replanning: the *entire remaining plan* gets replaced with a fresh one,
built with the failure's actual reason included as new context, rather
than either retrying the same doomed step or blindly executing a
second step written for a world that turned out not to be true. The
revised plan correctly drops "create" (already unnecessary) in favor of
"update" — genuinely different from the original, because it now
reflects what was actually learned.

What goes into that replan message matters as much as calling the
planner at all. It carries three things: the original goal, what has
**already been done**, and what failed and why. Without the completed
steps, a planner can happily re-plan work that already happened, like
creating an agent that step one already created. Each executor call
gets the same goal and results so far, as in
[the previous concept](/02-the-agent-loop/08-planning-and-decomposition/04-plan-and-execute-vs-reactive/#plan-and-execute-concretely).
(`FailureBlock` is a teaching
stand-in too: in practice a failed step arrives as a tool error, like
the `"Error: ..."` results from Lesson 6.)

One gap to close in real code: nothing here limits how many times the
planner is called again. A step that keeps failing would loop forever —
fail, replan, fail, replan. Cap replans the same way
[`max_steps` caps loop iterations](/02-the-agent-loop/06-termination-failure-and-control/02-max-steps/#the-simplest-possible-guard-a-hard-cap-unconditionally),
and stop cleanly with a message once the cap is hit.

</Subsection>
