<Subsection title="Naming a choice this module has already been making" variant="a">

Every loop built in
[Lessons 4–7](/02-the-agent-loop/04-writing-the-loop-by-hand/00-intro/)
has actually been making a specific architectural choice, without it ever
being named directly: deciding *one step at a time*, based only on current
state, with no advance structure — **purely reactive**. This lesson's
earlier concepts opened up the alternative: decompose the goal into a plan
*before* any execution begins, then actually execute that predetermined
structure — **plan-and-execute**.

</Subsection>

<Subsection title="Plan-and-execute, concretely" variant="b">

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`class PlanBlock:
    def __init__(self, sub_tasks: list):
        self.type = "plan"
        self.sub_tasks = sub_tasks

planning_client = FakeLLMClient(scripted_responses=[
    [PlanBlock(sub_tasks=["Create research_agent", "Create support_agent"])],
])

execution_client = FakeLLMClient(scripted_responses=[
    [TextBlock(text="research_agent created.")],
    [TextBlock(text="support_agent created.")],
])

def run_plan_and_execute(planning_client, execution_client, goal: str) -> list:
    plan_response = planning_client.create(messages=[{"role": "user", "content": goal}])
    plan = plan_response.content[0]
    print(f"plan has {len(plan.sub_tasks)} known sub-tasks -- the shape of the work is known before execution starts")

    results = []
    for sub_task in plan.sub_tasks:
        # the executor gets the goal and what's been done so far, not just its own step
        done = "; ".join(results) or "nothing yet"
        step_message = f"Goal: {goal}\\nDone so far: {done}\\nYour step: {sub_task}"
        response = execution_client.create(messages=[{"role": "user", "content": step_message}])
        results.append(response.content[0].text)
    return results

results = run_plan_and_execute(planning_client, execution_client, "Set up research_agent and support_agent")
print(results)`} />

(The updated fake client is already defined for this demo, and `PlanBlock`
is the one from the goal decomposition concept, repeated so the demo runs on its own.)

Before executing a single sub-task, the shape of the work is already
known: `2` sub-tasks, not "however many turn out to be needed, found out
only by actually running the loop."

Two details in the executor matter more than they look:

- **Each step gets context, not just its own instruction.** The message
  carries the goal and the results so far. A sub-task on its own is
  often ambiguous or depends on an earlier result: "Configure the new
  agent" means nothing unless the executor knows which agent step one
  created. Sending a sub-task alone is a common way plan-and-execute
  agents go wrong.
- **One call per step is a simplification.** Here each sub-task is a
  single model call, so the step count is exactly the plan's length. In
  real plan-and-execute systems, each sub-task usually runs as its own
  small agent loop, with tool calls until that step is done. The plan
  bounds the number of *sub-tasks*, but each one still needs
  [Lesson 6's guards](/02-the-agent-loop/06-termination-failure-and-control/00-intro/)
  on its own loop.

</Subsection>

<Subsection title="The real tradeoff" variant="a">

Plan-and-execute buys genuine **predictability and foresight**: you
know the shape of the whole task before spending anything on execution
— useful for estimating cost upfront, catching an obviously flawed plan
before wasting real execution effort, or letting a human review a plan
before it runs at all. What it trades away is **adaptiveness**: if
something genuinely unexpected happens mid-execution — something the
plan never accounted for — a plan-and-execute agent following a fixed,
predetermined structure isn't naturally built to notice and adjust.

A purely reactive loop is the mirror image: maximum adaptiveness,
deciding fresh at every step based on whatever's actually happening —
but genuinely no foreknowledge of how many steps it'll take, or what it
will actually do, until it's already doing it. This is exactly
[the unpredictable cost and latency risk from Lesson 1's honest case against always using an agent](/02-the-agent-loop/01-agents-workflows-and-the-loop/03-the-honest-case-for-not-using-an-agent/#what-an-agent-s-dynamism-actually-costs),
and exactly why
[Lesson 6 needed real guards — `max_steps`, repeated-action detection](/02-the-agent-loop/06-termination-failure-and-control/00-intro/)
— as a defensive backstop, precisely *because* a reactive loop has no
upfront bound on its own step count the way plan-and-execute naturally
does.

</Subsection>
