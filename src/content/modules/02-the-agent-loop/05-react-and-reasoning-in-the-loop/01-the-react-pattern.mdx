<Subsection title="Jumping straight from state to action" variant="a">

[Lesson 4's loop](/02-the-agent-loop/04-writing-the-loop-by-hand/02-from-round-trip-to-loop/#the-actual-loop-written-and-running-for-real)
goes directly from receiving a response to acting on it — a `tool_use`
block means "execute this," with no explicit reasoning step captured
anywhere in between. **ReAct** (Reasoning + Acting) adds that missing
step back in: an explicit `"thinking"` block, alongside `tool_use` and
`text`, where the model's reasoning about *why* it's about to act becomes
its own visible, distinguishable part of the response —
[exactly chain-of-thought from Lesson 2](/02-the-agent-loop/02-prompting-fundamentals/04-chain-of-thought-prompting/#the-fix-asking-for-the-reasoning-explicitly),
now applied specifically to *choosing an action* inside the loop, not
just reasoning toward a standalone final answer.

</Subsection>

<Subsection title="Extending the fake client: multiple blocks, one response" variant="b">

This requires a real evolution of
[the fake client from Lesson 4](/02-the-agent-loop/04-writing-the-loop-by-hand/01-the-fake-llm-client/#a-minimal-working-version):
a single response can now contain *more than one* content block together
— a `thinking` block followed by the actual action —
[matching the exact multi-block response shape from Module 1's reasoning-output coverage](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/06-reasoning-output-in-responses/#where-the-thinking-from-lesson-8-actually-shows-up),
rather than one block per response as before.

```python
class ThinkingBlock:
    def __init__(self, thinking: str):
        self.type = "thinking"
        self.thinking = thinking

class FakeLLMClient:
    def __init__(self, scripted_responses: list):
        self.scripted_responses = scripted_responses   # now: a list of block-lists
        self.call_count = 0

    def create(self, messages: list) -> FakeResponse:
        content_blocks = self.scripted_responses[self.call_count]
        self.call_count += 1
        return FakeResponse(content=content_blocks)
```

`scripted_responses` now holds a *list of lists* — each inner list is
one full response's content, potentially containing several blocks
together.

</Subsection>

<Subsection title="The pain: reacting to only one block silently drops the rest" variant="a">

A real response's content is a *list*, and a model can put more than
one action-shaped block in it — for instance, a short text remark
*alongside* a tool call, in either order. A loop that jumps straight to
the first block that looks like a decision — exactly what Lesson 4's
loop does, reading only `response.content[0]` — breaks the moment that
first block isn't the one that actually matters:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`calls_made = []

def check_price(item: str) -> str:
    calls_made.append(item)   # records every real call, so we can actually check

TOOL_REGISTRY = {"check_price": check_price}

# Lesson 4's loop, unchanged -- reacts only to the very first block
def naive_agent_loop(client, messages):

(The fake client's classes are already defined for this demo.)

`response.content[0]` is the `TextBlock`, so the loop returns
`"Let me check that for you."` immediately and stops — the `ToolUseBlock`
sitting right next to it in the very same response never runs at all.
Nothing crashed; the loop just silently did the wrong thing, which is
exactly the kind of bug a demo scripted one-block-per-response could
never have surfaced.

</Subsection>

<Subsection title="The fix: gather every tool call, act on all of them, reply once" variant="b">

The fix isn't "look harder for the right block" — it's to stop reacting
to a single block at all. Instead: collect *every* `tool_use` block in
the response; if there are none, the response is the final answer;
otherwise, run every collected call and send back *all* of their
results together, in one message:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`def check_price(item: str) -> str:
    return "$4.50" if item == "notebook" else "unknown"

TOOL_REGISTRY = {"check_price": check_price}

def run_agent_loop(client, messages):
    while True:
        response = client.create(messages=messages)
        for block in response.content:
            if block.type == "thinking":
                print(f"[reasoning]: {block.thinking}")
        messages.append({"role": "assistant", "content": response.content})

        tool_calls = [block for block in response.content if block.type == "tool_use"]
        if not tool_calls:
            return "".join(block.text for block in response.content if block.type == "text")

        results = []
        for call in tool_calls:
            tool_function = TOOL_REGISTRY[call.name]
            output = tool_function(**call.input)
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": output})
        messages.append({"role": "user", "content": results})

# the exact same "text before the tool call" response from the pain demo
client = FakeLLMClient(scripted_responses=[
    [TextBlock(text="Let me check that for you."), ToolUseBlock(name="check_price", input={"item": "notebook"})],
    [TextBlock(text="The notebook costs $4.50.")],
])

result = run_agent_loop(client, [{"role": "user", "content": "How much is a notebook?"}])
print(f"loop returned: {result!r}")`} />

(The fake client's classes are already defined for this demo.)

Three things hold true on every single iteration now, regardless of how
many blocks a response contains or what order they arrive in: the
assistant's *entire* response gets appended to `messages` exactly once;
the loop only stops once a response contains *no* tool calls at all
(any accompanying text before then is just conversational filler,
correctly not treated as the final answer); and when there are tool
calls, every one of them gets executed and its result goes back
together, in a single follow-up message.

</Subsection>

<Subsection title="Why every tool call needs its own result, in the same message" variant="a">

A response can just as easily contain *two* `tool_use` blocks together
— a model asking for two independent pieces of information in one
turn:

```python
[
    ToolUseBlock(name="check_price", input={"item": "notebook"}),
    ToolUseBlock(name="check_price", input={"item": "pencil"}),
]
```

A loop that acts on the first tool call and then moves on — the way an
easy, tempting fix for the pain demo above might look, stopping the
`for` loop the moment *any* tool call is found — would leave the second
call with no `tool_result` at all.
[Module 1's round trip](/01-llm-foundations/10-structured-output-and-tool-calling/05-the-full-round-trip/)
already established that every `tool_use` needs a matching
`tool_result`; a real API expects *all* of them accounted for in the
very next message, not just however many the loop got around to. The
fixed loop above handles this correctly for exactly this reason: it
builds one `results` list covering every collected call, and appends
it as a single message only once every call has actually run.

</Subsection>

<Subsection title="A complete run" variant="b">

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`def get_weather(location: str) -> str:
    return f"It's sunny in {location}."

TOOL_REGISTRY = {"get_weather": get_weather}

def run_agent_loop(client, messages):
    while True:
        response = client.create(messages=messages)
        for block in response.content:
            if block.type == "thinking":
                print(f"[reasoning]: {block.thinking}")
        messages.append({"role": "assistant", "content": response.content})

        tool_calls = [block for block in response.content if block.type == "tool_use"]
        if not tool_calls:
            return "".join(block.text for block in response.content if block.type == "text")

        results = []
        for call in tool_calls:
            tool_function = TOOL_REGISTRY[call.name]
            output = tool_function(**call.input)
            print(f"called {call.name}({call.input}) -> {output}")
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": output})
        messages.append({"role": "user", "content": results})

client = FakeLLMClient(scripted_responses=[
    [ThinkingBlock(thinking="The user wants the weather in both Paris and Berlin. I should check both."),
     ToolUseBlock(name="get_weather", input={"location": "Paris"}),
     ToolUseBlock(name="get_weather", input={"location": "Berlin"})],
    [ThinkingBlock(thinking="I now have what I need to answer."), TextBlock(text="It's sunny in both Paris and Berlin today!")],
])

messages = [{"role": "user", "content": "What's the weather in Paris and Berlin?"}]
final = run_agent_loop(client, messages)
print(f"final answer: {final}")`} />

(The updated fake client and the block classes are already defined for
this demo. The loop from above is repeated here so the demo runs on its
own.)

Every action — both tool calls *and* the eventual final answer — is now
preceded by its own explicit reasoning, visible and inspectable, and
both `get_weather` calls genuinely run and get paired with their own
result in the single follow-up message, rather than one of them
silently going unanswered.

</Subsection>
