<Subsection title="What a schema does and doesn't cover" variant="a">

[A tool's schema — a Pydantic model converted to JSON Schema, from Module 1](/01-llm-foundations/10-structured-output-and-tool-calling/03-from-a-pydantic-model-to-a-schema/)
— describes the *shape* of a tool call: the right argument names, the
right types (with strict mode on, constrained decoding guarantees the arguments match the schema; without it, they're usually but not always well-formed). It says nothing at all about *when* the
model should actually decide to call that tool, or how it should
interpret and act on whatever comes back. That's a separate, genuinely
distinct kind of guidance. It belongs in the tool's description (which
travels with the tool definition, as the next module shows) and/or the
system prompt — the *argument schema* is the one part that can't carry
it.

<LiveDemo client:load code={`from pydantic import BaseModel

class CheckInventoryArguments(BaseModel):
    book_title: str

schema = CheckInventoryArguments.model_json_schema()
print(schema)`} />

This schema constrains the *format* of a `check_inventory` call
completely — but it's silent on every strategic question: should the
model call this for every book-related question, or only some? What
should it do with a result of zero? None of that lives here.

</Subsection>

<Subsection title="Strategic guidance, in the system prompt" variant="b">

```
System prompt (tool guidance section): "Use check_inventory whenever a
customer asks about a specific book's availability. Do not use it for
general questions about store hours or return policy. If
check_inventory returns zero, tell the customer the book is currently
out of stock — do not suggest it might still be available without
checking again."
```

This is
[the same "request, not guarantee" category as prompt-specified output format from Lesson 2](/02-the-agent-loop/02-prompting-fundamentals/03-output-format-and-delimiters/#this-is-a-request-not-a-guarantee-and-that-s-worth-being-precise-about)
— a strong behavioral nudge, not a mechanical constraint. It's genuinely
necessary alongside the schema, not optional: a tool with a perfectly
well-defined schema but no strategic guidance can still get called at the
wrong moment, skipped when it should have been used, or have its results
misinterpreted — the schema was never responsible for any of that in the
first place.

</Subsection>

<Subsection title="Why both pieces are needed together" variant="a">

The schema and the tool guidance answer two genuinely different
questions: the schema answers *"if the model decides to call this, what
should the call look like"*; the system prompt guidance answers *"when
should the model actually decide to call this, and what should it do with
what comes back."* An agent missing either piece is incomplete in a
different way — missing the schema means calls that don't reliably parse;
missing the guidance means calls that happen at the wrong time, or
results the agent doesn't know how to actually use.

</Subsection>
