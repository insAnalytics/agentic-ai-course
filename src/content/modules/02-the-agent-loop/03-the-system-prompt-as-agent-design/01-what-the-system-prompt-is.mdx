<Subsection title="Why a system prompt carries weight in the first place" variant="a">

[Module 1 established that message roles are a learned convention](/01-llm-foundations/07-the-training-pipeline/03-preference-training-and-message-roles/#where-message-roles-actually-come-from),
not a hardcoded architectural channel — the model was trained, during
post-training (the chat format introduced through SFT's formatted
examples, then reinforced by preference training), on countless examples
where responses appropriately following `system`-role content were rated
as better, reinforcing a strong, consistent behavioral pattern to
generally treat it as higher-priority, persistent instruction. That's the
actual mechanism behind why a system prompt genuinely shapes an agent's
behavior — a real, strong, training-reinforced tendency, not an
unbreakable technical guarantee baked into the architecture itself.

</Subsection>

<Subsection title="Standing instructions vs. the per-turn task" variant="b">

Structurally, the system prompt is where instructions that should hold
across an *entire* interaction go — as opposed to the user turn's actual
task or query, which changes with every interaction:

<LiveDemo client:load code={`system_prompt = "You are a helpful assistant for a small bookstore. Answer questions about inventory, prices, and store hours concisely."

def build_messages(user_query: str) -> list:
    return [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_query},
    ]

conversation_a = build_messages("Do you have any copies of Dune in stock?")
conversation_b = build_messages("What time do you close on Sundays?")

print(conversation_a)
print(conversation_b)`} />

`system_prompt` is defined exactly once, and reused unchanged across two
entirely different user queries — this is the actual structural role a
system prompt plays: fixed, standing behavior that applies regardless of
what the specific interaction turns out to be about. (The demo puts the
system prompt in the `messages` list as a `system`-role message, the
generic shape; some real APIs, like Anthropic's, take it as a separate
top-level `system` field instead, as
[covered back in Module 1](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/01-the-request-shape/#real-providers-differ-in-the-details).
Either way it's the same standing instruction.)

Worth connecting to
[Module 1's statelessness](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/03-multi-turn-conversations/#the-api-itself-has-no-memory-between-calls)
directly: the system message still gets resent in full on every single
API call, exactly like everything else in the conversation — nothing
about it is magically "remembered" separately — its distinguishing
feature is that its *content* typically doesn't change turn to turn, not
that it's transmitted any differently.

</Subsection>
