<Subsection title="Four things, two already built by hand" variant="a">

A framework packages the same core pieces this module built from
scratch, plus two new ones:

- **The loop** —
  [Lesson 4's `while`/dispatch structure](/02-the-agent-loop/04-writing-the-loop-by-hand/02-from-round-trip-to-loop/#the-actual-loop-written-and-running-for-real),
  now hidden behind a method call.
- **State handling** —
  [Lesson 7's scratchpad and serialization](/02-the-agent-loop/07-agent-state-and-the-scratchpad/00-intro/),
  managed internally rather than a `messages` list you build yourself.
- **Tracing hooks** — new: structured visibility into what the loop
  actually did at each step, without hand-adding `print()` statements
  everywhere the way this module's demos have throughout.
- **A deployment path** — new: a defined way to actually run this agent
  as a real, reachable service, beyond a local script. Kept as a
  forward-pointer here — full deployment technique belongs to a much
  later module.

None of this is new capability the hand-rolled version couldn't do —
it's the same mechanisms, packaged and given a stable, reusable API.

</Subsection>

<Subsection title="The pain: visibility by print() only" variant="b">

Every demo in this module has shown what the loop did the same way: a
`print()` placed by hand at whatever point seemed interesting. That works
for a demo, but the output is just text on a screen. Nothing else can
read it, count it, or store it. And the next time you want to see
something different, you have to edit the loop itself to move the
`print()` calls around.

</Subsection>

<Subsection title="The fix, by hand: a tracing hook" variant="a">

A tracing hook replaces those `print()` calls with one structured
**event** per thing that happened, handed to a function the *caller*
supplies. The loop below is the same collect-every-tool-call loop this
module has used since
[Lesson 5's fix](/02-the-agent-loop/05-react-and-reasoning-in-the-loop/01-the-react-pattern/#the-fix-gather-every-tool-call-act-on-all-of-them-reply-once),
plus an `on_event` parameter:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`def run_agent(client, user_message: str, tools: dict, on_event, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": user_message}]
    for step in range(1, max_steps + 1):
        response = client.create(messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        tool_calls = [block for block in response.content if block.type == "tool_use"]
        on_event({"step": step, "event": "model_call", "tool_calls": [call.name for call in tool_calls]})

        if not tool_calls:
            return "".join(block.text for block in response.content if block.type == "text")

        results = []
        for call in tool_calls:
            output = tools[call.name](**call.input)
            on_event({"step": step, "event": "tool_result", "tool": call.name, "output": output})
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": output})
        messages.append({"role": "user", "content": results})
    return f"stopped after reaching the maximum of {max_steps} steps without a final answer"

def get_weather(location: str) -> str:
    return f"It's sunny in {location}."

client = FakeLLMClient(scripted_responses=[
    [ThinkingBlock(thinking="I should check the weather."), ToolUseBlock(name="get_weather", input={"location": "Paris"})],
    [TextBlock(text="It's sunny in Paris today!")],
])

trace = []
answer = run_agent(client, "What's the weather in Paris?", {"get_weather": get_weather}, on_event=trace.append)

print("answer:", answer)
for event in trace:
    print(event)
print("tool results recorded:", sum(1 for event in trace if event["event"] == "tool_result"))`} />

The loop itself never decides what to do with an event. Here the caller
passed `trace.append`, so every event landed in a list. That list is
real data: the last line counts tool results straight from it, with no
text to parse. Pass a different function and the same loop could print
events, write them to a file, or send them to a tracing service,
without changing a line of the loop. That's what a framework's tracing
hooks are: this `on_event` parameter, already wired into every step, with
ready-made functions to plug in. Where those events end up and how to
read them is observability, a topic a later module covers properly.

</Subsection>
