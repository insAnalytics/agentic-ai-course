<Subsection title="Explicit becomes implicit — not gone, just hidden" variant="a">

Everything
[the framework version from earlier in this lesson](/02-the-agent-loop/11-from-hand-rolled-to-a-runtime/02-rebuilding-in-langchain/)
does, the hand-rolled version also did — but several things that were
explicit and inspectable by hand are now internal to the framework.
Most of what follows is genuinely still the same mechanism, just no
longer visible; one is worse than that — a case where adopting the
framework's default actually changes the behavior itself, not just how
much of it you can see:

- **The step cap doesn't just stop being visible — it stops behaving
  the same way.**
  [`recursion_limit`, from the previous concept](/02-the-agent-loop/11-from-hand-rolled-to-a-runtime/02-rebuilding-in-langchain/),
  counts in a different unit than
  [Lesson 6's `max_steps`](/02-the-agent-loop/06-termination-failure-and-control/02-max-steps/#the-simplest-possible-guard-a-hard-cap-unconditionally)
  did (roughly half as many loop iterations as the number suggests),
  and it fails differently too — `GraphRecursionError` crashes the run,
  where `max_steps` was built specifically to avoid that and return a
  clean message instead. Reaching for the default without knowing this
  isn't a visibility problem to shrug off; it's a real behavior
  regression a framework's convenient default can quietly introduce,
  exactly why `ModelCallLimitMiddleware`'s `exit_behavior="end"` exists
  as the closer match — but nothing forces you to reach for it if you
  don't already know `recursion_limit` alone isn't equivalent.
- **Exactly how state serializes** —
  [Lesson 7's `to_dict()`/`serialize_messages`](/02-the-agent-loop/07-agent-state-and-the-scratchpad/02-serializing-state/)
  happens somewhere inside `agent.invoke()`, not in code you wrote or
  can trace line by line.
- **Exactly what the dispatch mechanism does** on an unexpected input —
  [Lesson 6's `execute_tool_safely`](/02-the-agent-loop/06-termination-failure-and-control/07-recap-practice/)
  was fully yours to read; a framework's equivalent is a black box
  unless you go looking for its source.

This isn't a criticism of frameworks — it's the actual, honest trade
[this course has named repeatedly](/02-the-agent-loop/08-planning-and-decomposition/04-plan-and-execute-vs-reactive/):
less code to write, at the cost of less direct visibility into exactly
what's happening. Knowing this loop's real mechanics by having built it
yourself is what makes that trade a genuine choice, not a leap of
faith.

</Subsection>

<Subsection title="The step-cap difference, run side by side" variant="b">

LangGraph itself can't run in this sandbox, so the demo below uses a
**stand-in**: `run_graph_style` is not LangGraph, just a loop that counts
steps the way the previous concept described LangGraph counting them.
The model call is one step, running the tools is another, and going
past the limit raises an exception. Both versions get the same
misbehaving script, where the model asks for a tool on every turn and
never gives a final answer, and the same number, 6:

<LiveDemo client:load setupCode={REACT_FAKE_CLIENT} code={`class GraphRecursionError(Exception):
    pass

def check_status() -> str:
    return "still pending"

TOOLS = {"check_status": check_status}

def never_finishes() -> FakeLLMClient:
    return FakeLLMClient(scripted_responses=[[ToolUseBlock(name="check_status", input={})] for _ in range(20)])

def run_tools(response) -> list:
    results = []
    for call in [block for block in response.content if block.type == "tool_use"]:
        results.append({"type": "tool_result", "tool_use_id": call.id, "content": TOOLS[call.name](**call.input)})
    return results

def run_with_max_steps(client, max_steps: int) -> str:
    messages = [{"role": "user", "content": "Is the job done?"}]
    for step in range(1, max_steps + 1):
        response = client.create(messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        results = run_tools(response)
        if not results:
            return "".join(block.text for block in response.content if block.type == "text")
        messages.append({"role": "user", "content": results})
    return f"stopped after reaching the maximum of {max_steps} steps without a final answer"

def run_graph_style(client, recursion_limit: int) -> str:
    messages = [{"role": "user", "content": "Is the job done?"}]
    graph_steps = 0
    while True:
        graph_steps += 1   # the model call counts as one step
        if graph_steps > recursion_limit:
            raise GraphRecursionError(f"Recursion limit of {recursion_limit} reached")
        response = client.create(messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        results = run_tools(response)
        if not results:
            return "".join(block.text for block in response.content if block.type == "text")
        graph_steps += 1   # running the tools counts as another
        if graph_steps > recursion_limit:
            raise GraphRecursionError(f"Recursion limit of {recursion_limit} reached")
        messages.append({"role": "user", "content": results})

client = never_finishes()
print("max_steps=6       ->", run_with_max_steps(client, max_steps=6))
print("   model calls actually made:", client.call_count)

client = never_finishes()
try:
    print(run_graph_style(client, recursion_limit=6))
except GraphRecursionError as e:
    print("recursion_limit=6 -> crashed:", e)
print("   model calls actually made:", client.call_count)`} />

The call counts come from the fake client's own `call_count`, so they're
a record of what really happened, not a claim. The same number, 6, gave
the model six turns in one version and three in the other. And one
version returned a message the caller can show the user, while the
other raised an exception the caller has to catch or else crash. Nothing
about this is visible from the line `config={"recursion_limit": 6}`
alone.

</Subsection>
