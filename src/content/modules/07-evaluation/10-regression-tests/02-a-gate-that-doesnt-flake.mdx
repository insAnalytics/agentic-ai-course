<Subsection title="What a gate is for" variant="a">

A regression test ends in a decision: ship the change, or stop and look.
Written as code, that decision is a **gate**, the same idea as
[Module 0's tests](/00-python-essentials/10-testing-fastapi-apps/09-test-reports-and-coverage/#beyond-reading-terminal-output)
failing a build, applied to a suite of agent runs. A gate has two ways to
be wrong:

- **It misses a regression.** The change made the agent worse and the
  gate passed it.
- **It flakes.** Nothing got worse and the gate failed anyway, because
  the agent's results vary from run to run.

The second sounds harmless and isn't. A gate that fails on noise gets
rerun until it passes, and then ignored, and an ignored gate catches
nothing. The way to keep it honest is to set its thresholds from the
noise you've measured, not from round numbers.

</Subsection>

*(`passes` is
[Lesson 9's setup](/07-evaluation/09-ablations/03-compaction-on-and-off/),
and `pass_rate` and `paired_difference` are
[Lesson 9's exercise](/07-evaluation/09-ablations/01-one-piece-on-and-off/),
all loaded for you. Only the main pool's tasks were run twice; 77 of them
are dev tasks.)*

Most tasks didn't move at all, and the suite as a whole moved about a
point, inside an interval that includes zero. A suite-level rule built on
Lesson 9's paired interval would pass this pair, as it should.

The tasks are a different story. One task, q25, failed all five trials in
the first run and passed all five in the second. Reading them, the two
runs answered in two different ways: the first listed the models the
agent could move to, the second recommended one, which is what the
question asked. Nothing changed between them but the sampling seeds. Why
all five trials in each run went the same way is something this module's
data can't settle, but it means a single run's trials of one task aren't
always independent, and a task-level rule has to allow for swings this
large.

So the thresholds follow from the noise:

- **For the suite,** fail only if the paired interval lies wholly below
  zero *and* the drop is bigger than a small tolerance, here 2 points.
  The interval keeps chance out; the tolerance keeps a real but trivial
  drop from blocking a change.
- **For single tasks,** flag only a fall in pass rate of 0.8 or more,
  four trials in five. In the no-change pair, no task fell by more than one
  trial. The threshold limits flaky flags rather than preventing them: the
  same pair has q25 rising from 0 of 5 to 5 of 5, and a swing that size
  downward would be flagged.

</Subsection>

<Subsection title="The gate on this module's changes" variant="a">

<LiveDemo client:load dataFiles={ABLATIONS_DATA} setupCode={LOAD_ABLATIONS + "\n\n" + PAIRED_DIFFERENCE + "\n\n" + GATE} code={GATE_DEMO} />

*(`gate` is the exercise's reference version, loaded for you. The
known-good run is the baseline, and the no-change pair compares its two
batches on the main pool. Every gate here runs on the dev tasks only.)*

The gate does what it should on the two clear cases. The baseline run
again passes, with nothing flagged. Module 6's layers fail on both rules,
with 22 tasks flagged. Removing the labels passes: a gain is not a
regression.

Forced compaction is the instructive one. It passes too: its interval
crosses zero, and no task falls far enough to be flagged. That doesn't
make it a good change.
[Lesson 9](/07-evaluation/09-ablations/03-compaction-on-and-off/#why-it-cost-that)
found it bought this agent nothing and made it repeat work. A gate catches
regressions; whether a change is worth making is a separate question,
which an ablation answers.

The gate's weak point runs the other way: a per-task rule run on many
tasks will, now and then, flag a task that's merely flaky. Nothing here
was, but q25's five-trial swing in the no-change pair shows it can happen.
A flag should send a person to read the task's runs, not block a release
on its own, and how many flags to expect by chance is the next concept's
question.

</Subsection>
