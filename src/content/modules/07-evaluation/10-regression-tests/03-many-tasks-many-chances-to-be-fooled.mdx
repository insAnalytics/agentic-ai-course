<Subsection title="One test per task" variant="a">

The gate in [the last concept](/07-evaluation/10-regression-tests/02-a-gate-that-doesnt-flake/)
flagged any task whose pass rate fell by 0.8 or more. That threshold came
from reading the noise, which works but doesn't say how surprising a
given drop is. A statistical test does: for one task, how likely is a
drop at least this large if nothing had changed?

With pass/fail trials on both sides, the standard choice is **Fisher's
exact test**. Given how many passes there were across both runs
together, it computes the exact chance that the new run would get this
few of them by luck alone. Here it is, one-sided because a regression
gate only cares about drops:

*(`passes` is [Lesson 9's setup](/07-evaluation/09-ablations/03-compaction-on-and-off/),
loaded for you; the no-change pair is the baseline's two batches on the
main pool.)*

Two numbers in that output decide this whole concept.

- **The no-change pair produced no task with p below 0.05.** The
  one-sided test asks about drops, and q25's big swing was a gain.
- **Five trials can't prove much about one task.** The strongest possible
  evidence, 5/5 falling to 0/5, gives p = 0.004. That sounds small, but
  with 77 or 97 tasks tested at once, small p-values turn up by chance.
  Lesson 9's Bonferroni correction divides the 0.05 by the number of
  tests, here a threshold of about 0.0005 to 0.0006, which no task can ever
  reach
  with five trials. A per-task gate built that way would never fire.
- **The test assumes a task's trials are independent.** When they move
  together, as q25's did, its p-values come out too small. Lesson 11's A/A
  test shows the same effect for users' runs.

</Subsection>

<Subsection title="Controlling the share of false flags" variant="b">

Bonferroni guards against even one false flag across all the tests. For
a gate whose flags send a person to read runs, that's the wrong goal: a
flag list that's 95% right is useful, and one that can never contain
anything isn't. Benjamini and Hochberg's method (1995) controls something
else, the **false discovery rate**: the expected share of flagged tests
that are false. Set it at 5%, and it keeps the expected share of
false flags at or below 1 in 20, however many tests there are.

It's a short procedure:

1. Sort the m p-values from smallest to largest.
2. Find the largest rank k where p(k) ≤ k / m × q.
3. Flag the k smallest.

A test can be flagged even if it missed its own threshold, as long as a
test ranked after it passed. That's what lets many moderate signals
together flag a regression no single one could prove.

</Subsection>

<Subsection title="Every change, three ways" variant="a">

<LiveDemo client:load dataFiles={ABLATIONS_DATA} setupCode={LOAD_ABLATIONS + "\n\n" + FISHER_DROP + "\n\n" + BENJAMINI_HOCHBERG} code={THREE_WAYS_DEMO} />

*(`fisher_drop` is the first demo's, and `benjamini_hochberg` the
exercise's reference version, both loaded for you. The known-good run is
the baseline throughout.)*

- **Uncorrected,** p below 0.05 flags tasks only for layers v2 and the
  original layers, much the same tasks the gate's 0.8 rule flags, and
  nothing for the four changes that didn't regress, compaction included.
  That's a useful reading list, but with 97 tests, a few flags would be
  expected by chance even when nothing changed.
- **Bonferroni** flags nothing anywhere, not even for Module 6's original
  layers, which cost 30 points. With five trials per task, it can't.
- **Benjamini–Hochberg** flags 13 tasks for the original layers, where
  many tasks fell together, and nothing for layers v2, where fewer tasks
  fell.

So with five trials per task, the suite can confirm a broad regression
task by task, but an isolated drop in one task stays a suspicion. That
suggests how to spend a budget: run the whole suite at five trials to
find suspects, then rerun only the flagged tasks with many more trials,
on both versions. The flags were chosen because the known-good run's
trials happened to be high and the new run's low, so reusing those trials
would overstate the drop. Twenty fresh trials on each version for the
eight tasks layers v2 flagged is about two-thirds of one dev-suite run,
and turns "worth a look" into an answer.

</Subsection>
