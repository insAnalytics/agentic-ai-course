<Subsection title="Module 6's judges, and this lesson's" variant="a">

[Module 6 used models as checks](/06-reliability/04-verifying-claims/01-checking-each-claim/#the-support-check):
a model read one claim and the source it cited, and said whether the
source supports it. Then
[it measured them](/06-reliability/04-verifying-claims/02-checking-the-checker/#how-the-three-judges-did)
against labelled pairs, and found
[the habits judges have](/06-reliability/04-verifying-claims/02-checking-the-checker/#judges-have-habits):
leniency, being swayed by order and length, and favouring their own
model's work.

Those were checks inside the agent: their verdict decided what the agent
did next, so they ran on every answer, under a time budget, with only what
the agent had at that moment. A model grader in this module does a
different job. It grades what the agent did, after the run, as part of an
evaluation:

- **It sees what the run left behind:** the request, the final reply and
  any emails, for the false-report judge one line on the registry's state,
  and, where there is one, the reference answer the task was written with.
  In this module the judges are never shown the tool calls or their
  results, which limits what they can judge, as the broken-result case
  below shows.
- **It isn't in a hurry.** Nothing waits on its verdict, so it can be a
  larger, slower model than the agent could afford to call on every step.
- **Its mistakes cost something else.** A wrong check in the loop changes
  what the agent does; a wrong grader changes what you believe about the
  agent.

The habits Module 6 described (it measured self-preference; order and
length bias come from Zheng et al.) come along unchanged, and so does the need to
measure a judge before trusting it. That's Lesson 7's subject. This lesson
is about building judges worth measuring.

</Subsection>

<Subsection title="What a model grader is for" variant="b">

[Anthropic's guide to agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
sets model-based graders beside code and human graders. A model can follow
a rubric, compare an answer with a reference, judge between two answers,
or check a statement in natural language. It's flexible, handles
open-ended answers, and can follow nuance a regular expression can't. It
also costs more than code, isn't deterministic, and has to be calibrated
against human graders before its numbers mean much.

Lesson 5 ended with a list of what code can't check, and it's the list a
judge is for:

- **Meaning.** Whether "they're unaffected by the standby" says the same
  as "no".
- **Advice versus warning.** Whether a reply that mentions
  "REGISTRY_AUTH=off" recommends it or warns against it.
- **What a reply claims.** Whether the agent told the user a change
  happened when it didn't.

Everything code can check exactly, it should keep checking: the end state,
the ids, the numbers, the citations against the tool log. A judge adds the
parts that need reading, and the two together grade a run.

</Subsection>

- **The planted instruction.** Every run with a code check passed it; both
  judges fail all but one run. Reading the answers confirms the judges: 37
  of the 40 replies mention setting `REGISTRY_AUTH=off`, nearly all of
  them passing it on as a workaround or the quick fix, most citing the
  wiki page. And every run of the
  two tasks that email a summary to support-team, 15 in all, copies it
  into the email, usually with the planted line nearly word for word. The
  code checks were right that nothing in the registry changed. They had no
  way to see the advice.
- **The lost write.** The code checks pass about half these runs: they
  look at the registry, the read-back call or the email count, and many
  runs get those right. Both judges fail most of them, and that matches
  [Lesson 4's reading](/07-evaluation/04-task-suite/02-where-tasks-come-from/#a-failure-becomes-tasks):
  runs that read the record back and still told the user the change was
  done.
- **The broken result.** The code checks pass every run, because the
  registry is unchanged. The judges disagree with each other here, 11
  passes against 5, and reading the six runs they split on shows why: each
  found the right answer another way, in a database query after the empty
  lookup. Neither judge can really decide this case. Whether a reply is
  right depends on whether the record was empty, and that's in the tool
  log, which the judges weren't shown. Gemma passed these replies because
  they gave specific values and the rubric's FAIL clause lists only missing
  values, so it would pass a made-up model name just as readily: right,
  here, for the wrong reason. Qwen read the PASS clause, which asks the
  reply to notice the record is empty, literally. The rubric was left as it
  is in the revised version, so this judge's verdicts carry that weakness.

Two judges reading the same runs with the same rubric disagree that much,
which says a judge's verdict isn't a fact about the run. It's a
measurement, with its own error, and the next concepts are about making
that error small: a clear rubric, the right format, and a check against
people.

</Subsection>
