<Subsection title="What a useful note looks like" variant="a">

A note from open coding has one job: to let someone who wasn't there find
the problem, and later, to sit next to other notes like it. That asks four
things of it:

- **The first failure.** Husain and Shankar recommend noting the first
  thing that went wrong, because a mistake early in a run causes others
  later, and a note about a knock-on effect points at the wrong fix. One
  note per run is enough to start with.
- **Specific.** "Moved support_agent without asking which of
  support-team's three agents was meant" can be checked against the trace
  and grouped with other notes. "Bad action" can't.
- **Observable.** Write what the agent did, not what you think was going
  on inside it. "Took the empty record at face value" is something you can
  see; "was confused" isn't.
- **In your own words, not a category's.** The categories come later, from
  all the notes together. Naming a category while reading pulls each run
  towards the list you already have, which is the thing open coding is
  meant to avoid.

The reading standard adds one more rule that shapes the notes: judge the
run as it ended, with all its turns, not as it might have gone if the
conversation had continued.

</Subsection>

<Subsection title="Why a person reads" variant="b">

Finding the first failure sounds like something a model could do.
Research on exactly that task says not yet. The Who&When benchmark (Zhang
et al., ICML 2025) collected failure logs from 127 multi-agent systems,
annotated with which agent caused each failure and at which step, and
tested automated methods, strong models among them, on finding both. The
best method named the responsible agent 53.5% of the time but the decisive
step only 14.2% of the time, and some methods did worse than random. Later
work improves on those figures, but finding where a run first went wrong
is still hard to automate reliably.

So the reading here was split. Simar, who knows the registry, labelled 40
of the 100 traces. Claude, the model this course is drafted with, labelled
the other 60, under the written standard. Ten of the 23 failures counted in
this lesson come from Claude's labels alone, which is a reason to treat the
smaller categories as drafts a person should confirm.

</Subsection>

<Subsection title="A note that can be acted on" variant="b">

Notes get better with practice, and two pairs from the reading show how:

<LiveDemo client:load dataFiles={NOTES_DATA} setupCode={NOTES_SETUP} code={REWRITE_DEMO} />

*(The q07 rewrite is Simar's own, after a second look; the q30/3 note is
Claude's.)*

- **q07.** The first note says the answer was wrong but not how, so it
  can't be grouped with anything. The rewrite says what the user needed
  (the whole list), what the agent gave (a query with a row limit) and why
  that fails (it recreates the problem). That's the version that later
  became its own category, *misses the user's real need*.
- **q30.** Both notes are true, for two different runs of the same task.
  The second also says where the answer was: the agent's first searches
  had already returned the section that answers the question. That changes
  what the failure looks like. It isn't "couldn't find the answer", it's
  "found it and kept searching", which points at a different fix.

</Subsection>

<Subsection title="Passes worth a note" variant="a">

A run that passes can still be worth a sentence. The reading page had an
optional "how" field for this: anything about how the agent got there,
including a pass that got there by luck or by a route that won't hold up.
Four runs Claude read, all passes:

<LiveDemo client:load dataFiles={NOTES_DATA} setupCode={NOTES_SETUP} code={PASSES_DEMO} />

*(The notes are Claude's.)*

- **a02/2 and a02/0** both passed the same task. One read the record back
  after the change and one didn't. Here it made no difference, because the
  write landed; on the lost-write tasks, it made all the difference. A pass
  by the second route is a pass that wouldn't have caught the fault.
- **m05/1** passed but contradicted itself between turns.
- **m03/1** got there in the end, after three searches that found nothing
  relevant.

None of these change a verdict, but they're the material for checks and
for the question of *how* the agent reached a result, which this lesson
comes back to at the end.

</Subsection>
