export const REFERENCE = String.raw`from collections import Counter


def trajectory_matches(actual: list[str], expected: list[str], mode: str) -> bool:
    """Whether the tools a trial called (actual) match a reference path (expected).

    mode "exact":     the same tools, in the same order, with nothing extra
    mode "in_order":  every expected tool appears in order; extra calls in between are allowed
    mode "any_order": every expected tool appears, in any order; extra calls are allowed
    Each expected call needs a call of its own: two expected get_agent calls need two in actual.
    Any other mode raises ValueError.
    """
    match mode:
        case "exact":
            return actual == expected
        case "in_order":
            # "in" on an iterator consumes it up to the match, so each expected tool is looked for after the last one
            remaining = iter(actual)
            return all(tool in remaining for tool in expected)
        case "any_order":
            return Counter(expected) <= Counter(actual)
        case _:
            raise ValueError(f"unknown mode: {mode!r}")


path = ["get_agent", "set_model", "get_agent"]
for mode in ("exact", "in_order", "any_order"):
    print(mode, trajectory_matches(path, ["get_agent", "set_model"], mode))

<Subsection title="Two things a grader can look at" variant="a">

Anthropic's guide says a grader looks at the transcript, the outcome, or
both. For the registry agent, that comes to three
checks worth separating, because the last concept showed they can disagree:

- **The end state.** What the world looks like when the run is over: the
  registry's records, and the outbox. A grader checks it in code, against
  what the task should have changed and what it shouldn't.
- **The final reply.** What the user was told. It isn't the outcome, which is
  the end state, but it's part of what the run delivered, so a complete
  grade checks it too. In task p08, the end state was what a lost write
  leaves behind, and every reply told the user the opposite. A refusal is
  only useful if the reply says why.
- **The path.** Which tools the agent called, in what order, with what
  arguments. This comes from the transcript.

The industry's evaluation tools grade all of these, under slightly
different names:

- **LangSmith** describes three kinds of agent evaluation: the final
  response, a single step (such as whether the agent picked the right
  tool), and the trajectory, meaning whether the agent took the expected
  path of tool calls.
- **OpenAI's trace grading** scores a run's whole trace, and lists
  questions such as whether the agent picked the right tool.
- **Google's Agent Development Kit (ADK)** has a built-in metric,
  `tool_trajectory_avg_score`, that compares the tools an agent called with
  a list of expected calls, arguments included, in one of three match
  modes: `EXACT`, `IN_ORDER` and `ANY_ORDER`.
- **Anthropic's guide** gives example eval definitions that mix all three:
  a `state_check` on the database, `tool_calls` that must be made, and a
  rubric for the reply.

The single-step kind is the subject of the next concept. This one is about
the outcome and the path, and what goes wrong when you lean on the path.

</Subsection>

<Subsection title="Matching a path against a reference" variant="b">

A path check needs a **reference path**: the calls the person writing the
eval expects. ADK's three modes differ in how strictly a run has to follow
it:

- **Exact**: the same calls, in the same order, with nothing extra.
- **In order**: every expected call appears in the expected order; extra
  calls in between are allowed.
- **Any order**: every expected call appears, in any order; extra calls are
  allowed.

In the last two, each expected call needs a call of its own: a reference
with two `get_agent` calls isn't met by a run that made one.

ADK compares each call's arguments as well as its name. That works when the
arguments are predictable, like an agent's id. It fails on free text: across
the 4B's pilot runs, 26 searches used 24 different wordings, so an
exact-argument check on `search_docs` would fail almost every run that
searched. The exercise below compares tool names only, which is enough to
see how the modes behave. A check that cares about one argument, such as
which agent was changed, is better written as its own check on the log, and
the end of this page comes back to that.

</Subsection>

*(Real runs of the registry agent, recorded offline. `trajectory_matches`
is the exercise's reference version, already loaded for you.)*

Every mode is wrong on 4 of the 9 runs, in two different ways:

- **It fails runs that did the job.** Exact match fails a run for reading
  the record back (p06/1) and for looking up the rules after the refusal
  (p07/2). Loosening the mode fixes those two, which is what ADK's own
  evaluation guide suggests when extra calls cause failures. It doesn't fix
  p07/1, which looked up the rules first and never tried the change at all.
  That's a different valid route, not an extra step, and no mode accepts a
  route the reference didn't foresee.
- **It passes runs that didn't.** Every p08 run made the reference's calls,
  read-back included, and then told the user something false. In-order and
  any-order matching pass all three. Exact matching fails two of them, but
  only because those runs made extra calls, not because it noticed anything
  wrong. It passes the third.

This is the brittleness Anthropic's guide warns about. Its advice, from
experience across many teams, is that checking for a specific sequence of
tool calls is too rigid, because agents regularly find valid approaches the
eval's author didn't anticipate, so it's usually better to grade what the
agent produced than the path it took. The pilot shows the other half too: a
run can follow the expected path exactly and still get the result wrong.

</Subsection>

<Subsection title="When the path is the right thing to check" variant="b">

Grading the path isn't always wrong. Anthropic's own example eval for a
support agent requires a `verify_identity` call and a `process_refund` call
for no more than 100. Neither is a guess about how the agent will probably
succeed: each is a rule the agent must follow whatever route it takes.
That's the line to draw:

- **Required steps that are rules.** Verifying identity before a refund.
  Reading back a write that matters, which
  [Module 6 made a check in code](/06-reliability/07-safe-actions/02-reading-the-result-back/).
- **Forbidden actions.** A call that must never happen in a given task,
  such as changing an agent the user didn't name.
  [Module 6's intent check](/06-reliability/10-layered-checks/02-layering-the-checks/)
  blocks this while the agent runs; a grader checks the same thing
  afterwards. These checks usually care about one argument, so they're
  written against the log ("no `set_model` on any agent but
  `notes_agent`"), not as a reference path.
- **Limits.** A cap on turns or tool calls, like the 10-turn limit in
  Anthropic's example.

Even a required step only proves the call was made, not that the agent used
what came back. Every p08 run read the record back, saw the old model, and
explained it away. So a path check sits beside the outcome checks rather
than replacing them. For the registry agent, that means checking the end
state, the reply, and only the steps that are rules in their own right.

</Subsection>
