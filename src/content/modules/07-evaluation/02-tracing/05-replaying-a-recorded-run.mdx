<Subsection title="Record once, replay as often as you like" variant="a">

The pilot's runs needed a GPU and a model; the browser has neither. They
can still be run here, because every model reply was recorded. **Record and
replay** is an established testing technique for exactly this: run against
the real service once, save every request and response, and from then on
answer requests from the recording.

VCR.py, a widely used Python library for testing code that makes HTTP
requests, is a well-known example. It saves a test's HTTP traffic to a file
it calls a cassette and replays it on later runs, which its documentation
says makes tests fast, able to run offline, and completely deterministic.
One of its settings matters most here: in its strictest mode, a request
that isn't on the cassette raises an error instead of reaching the real
service, so the test can't quietly do something new.

This course's replay works the same way, at the level of the agent's loop
rather than HTTP:

- **The model's turns are replayed.** Each request the loop makes is
  answered with the recorded reply. So are the simulated user's replies,
  where a task has one.
- **Everything else runs for real.** The tools run against a fresh registry
  world, the checks run, and the loop is Module 6's, unchanged.
- **Every request is checked.** The recording holds a hash of each request
  the model was sent. Before answering, the replay hashes the request it's
  been given, and if the two differ it stops with `ReplayDiverged`, just as
  VCR.py's strict mode does.

If a replay finishes without diverging, the browser has re-run the recorded
run: the same requests, the same tool calls and results, the same answers.

</Subsection>

<Subsection title="What a replay can't do" variant="b">

A replay only works while every request matches the recording. Here's a
change that looks harmless: `get_agent` returns the same record, just laid
out more readably.

<LiveDemo client:load dataFiles={REPLAY_DATA} setupCode={REPLAY_SETUP} code={DIVERGE_DEMO} />

The replay stops at call 1, the first request that includes `get_agent`'s
result. The new layout means the model would have seen different text, and
the recording can't say what it would have done with it. It might have made
the same choices, or not. That's not a flaw in the replay; it's the
boundary of what a recording can tell you. VCR.py's documentation says the
same about its cassettes: when the service you're testing against changes,
delete the recording and record again.

So replay is for changes that shouldn't alter what the model sees, and for
everything that only reads a run:

- **Deterministic demos and tests.** Every page in this module runs the
  pilot's runs this way, with no model.
- **Debugging.** A recorded run can be replayed step by step, with the real
  tools, as often as you need.
- **Checking a change that's meant to change nothing.** A refactor of a
  tool's internals, or new tracing, should replay cleanly. If it diverges,
  it changed what the model sees.
- **Grading old runs with new graders.** A grader reads the recording; it
  doesn't need the model at all.

A change that does alter what the model sees, such as a new prompt, a
tool's output format, or a different model, can only be evaluated by
running the model again, many times, and comparing with the runs before.
That's regression testing, and it's Lesson 10.
