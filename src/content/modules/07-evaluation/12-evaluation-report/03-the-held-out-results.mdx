<Subsection title="Opening the held-out set" variant="a">

[Lesson 4](/07-evaluation/04-task-suite/05-holding-tasks-out/#two-kinds-of-task-in-one-suite)
kept 28 tasks back so that, at the end of the module, there'd be a
measurement on tasks no decision was made on. This is that measurement,
for the baseline agent, with the same graders and the same headline
method as the dev results:

<LiveDemo client:load dataFiles={DATA} setupCode={SETUP} code={HELD_OUT_DEMO} />

*(`headline` is the previous concept's reference, loaded for you.)*

The held-out tasks pass more often than the dev tasks: 85.7% against
73.6%, and higher in both of the large groups. Two explanations fit, and
the report should give both rather than pick one:

- **The held-out tasks are easier.** Lesson 4 already said so of the
  registry tasks, which were picked by hand and lean towards things the
  agent does well. The 11 held-out questions were Module 5's held-out
  questions, and
  [Module 5's finished pipeline](/05-rag-systems/15-a-new-corpus/03-one-honest-number/)
  also did better on them than on its main set: 9 of 10 answerable ones
  in the top five, against 36 of 43.
- **Chance.** The two intervals overlap. A rough comparison of the two
  rates, using each one's clustered standard error, puts the difference
  at about 1.8 standard errors: suggestive, not conclusive.

What the result shows is no sign of the failure a held-out set exists to
catch. If the work on the dev tasks had made the agent fit them and fail
elsewhere, the held-out tasks would likely score lower, and they don't.
That isn't proof: if the held-out tasks are easier, they could hide some
of that cost.

</Subsection>

<Subsection title="Every contact, disclosed" variant="b">

Lesson 4 promised a set of tasks no decision was made on. That promise
wasn't kept in full, and the report says exactly how. Leaks like these
are the usual way held-out sets go wrong: not someone tuning on the
answers, but the held-out tasks quietly riding along in comparisons and
dashboards. The contact log, and what the held-out score looks like with
the most-seen tasks left out:

<LiveDemo client:load dataFiles={DATA} setupCode={SETUP} code={CONTACTS_DEMO} />

*(The contact log was compiled from the module's pages and its working
notes.)*

The log has two kinds of entry, and they matter differently:

- **Aggregate contact.** In Lessons 9 and 10, every comparison and gate
  ran over all 125 tasks, so held-out results sat inside every number
  that decided which changes ship. Those comparisons should have used dev
  tasks only. That's a fault in the method, and it's recorded for the
  course's final review.
- **Per-task contact.** Fourteen held-out tasks had something about them
  alone shown or read: a triage pattern, a placement in the capability or regression suite, a
  step-limit fix, an answer read, or
  a name on a flagged list.

What the leaks could have done is narrower than it looks:

- **The baseline's held-out score isn't inflated by any of them.** The
  baseline's prompt and configuration were fixed before it first ran,
  before any of these contacts. The only changes made since were to
  graders, and those were made from dev tasks: s25's new step limit was
  copied from its dev twin without reading s25's runs, which is the
  legitimate kind of fix Lesson 4 described.
- **The decisions on changes are where the risk is.** Prompt v2 and FP8
  were judged to ship by a gate that could see held-out results. A
  held-out score for those changes would be slightly optimistic, which is
  one reason this report evaluates the baseline and treats the changes as
  approved candidates.
- **The sensitivity check agrees.** Without h08, the rate barely moves.
  On the 14 tasks never seen alone it's higher, not lower, so if the
  contact did anything, it didn't flatter the agent.

</Subsection>

<Subsection title="After the report: the set is spent" variant="a">

Once these numbers are written into a report, the held-out set has done
its job. Every future decision would be made in full knowledge of how the
agent does on it, so it can't be held out from the next round.
[Module 5 ended in the same place](/05-rag-systems/15-a-new-corpus/03-one-honest-number/#reading-it)
and the answer is the same:

- **Fold the old held-out tasks into the dev set.** Their runs can now be
  read, their failures named and their checks fixed, like any other dev
  task.
- **Hold out a fresh set** for the next report, chosen within each
  category, as Lesson 4 did for the newer suite tasks, so it covers what
  the dev set covers.
- **Keep the contact log as you go.** The log above had to be
  reconstructed from the module's pages after the fact. Recording each
  time held-out results are shown, at the moment it happens, is cheaper
  and more complete, and so is the habit it builds: filter to dev tasks
  first, every time.

</Subsection>
