<Subsection title="The decisions, and their evidence" variant="a">

Lessons 9 and 10 made six decisions about changes to the agent, each on
the dev tasks, with the held-out set kept out. Here they are with the
evidence behind each:

<LiveDemo client:load dataFiles={DATA} setupCode={SETUP} code={DECISIONS_DEMO} />

*(Each difference is the change minus the baseline on the dev tasks,
paired by task, with a 95% interval from resampling tasks;
`paired_difference` is Lesson 9's, loaded for you.)*

- **Module 6's layers, and the fixed layers v2: stop.** Both cost the
  agent heavily, and
  [Lesson 9's reading](/07-evaluation/09-ablations/04-module-6s-layers-on-real-runs/#what-the-layers-did)
  and
  [Lesson 10's](/07-evaluation/10-regression-tests/04-three-real-changes/#reading-a-failure-the-layer-fix)
  explain why: false alarms, then a claim splitter with bugs.
- **Prompt v2: ship.** About five points better, with an interval above
  zero. Most of the gain is the lost-write tasks, which
  [Lesson 10 traced](/07-evaluation/10-regression-tests/04-three-real-changes/#reading-a-pass-the-prompt-change)
  to the new read-back line. Those tasks are graded by the false-report
  judge, whose pass rate on good replies has never been measured, so the
  gain rests on that judge and on one run read.
- **FP8 serving: ship.** No regression.
- **Compaction: don't adopt.** It passes the gate, with no measurable
  cost and nothing flagged. But it buys this agent nothing, and it makes
  runs repeat work at about 13% more tokens per success, as
  [the security and cost table](/07-evaluation/12-evaluation-report/05-decisions-limits-and-whats-next/#security-and-what-it-costs)
  shows. A gate only says a change does no harm; here nothing argues for
  it. It would earn its place on runs that outgrow the context window,
  which this suite doesn't have.
- **The source labels: remove, after one check.** Removing them gains
  about five points, and
  [the gain survives correcting for eighteen comparisons](/07-evaluation/09-ablations/05-a-piece-that-doesnt-earn-its-place/#the-result).
  Part of it is
  [the citation check passing answers that cite nothing](/07-evaluation/09-ablations/05-a-piece-that-doesnt-earn-its-place/#what-a-gain-is-made-of),
  so the check gets fixed and the comparison rerun before the labels go.

Each line names its evidence and how firm that evidence is. That, more
than the verdict itself, is what lets a reader disagree with a decision.

</Subsection>

<Subsection title="Security, and what it costs" variant="b">

A pass rate mixes two questions an agent with tools has to answer
separately: does it do its job, and does it resist being misled?
[Module 6](/06-reliability/02-reliability-tradeoffs/01-four-things-every-technique-trades/#a-refusal-can-be-a-reliability-failure)
judged a defence on both at once, as AgentDojo does: how often attacks
succeed, next to how many ordinary tasks still get done. Cost needs the
same treatment. [Kapoor et al.](https://arxiv.org/abs/2407.01502) argue
that agents should be reported with cost beside accuracy, because a small
gain can come at a large price. Here are both lines for every graded
condition, on the dev tasks:

<LiveDemo client:load dataFiles={DATA} setupCode={SETUP} code={SECURITY_DEMO} />

*(Planted runs passing are runs of the five planted-instruction tasks that
passed their code checks and the planted-instruction judge; benign is
every other dev task; tokens are the agent's own model calls; in-loop
judge calls are the layers' support-judge calls per run, whose tokens
weren't recorded.)*

- **The layers bought security with usefulness.** Planted-instruction runs
  passing went from none of 25 to 8, the third of planted runs
  [Lesson 9 saw](/07-evaluation/09-ablations/04-module-6s-layers-on-real-runs/)
  become safe. But the benign pass rate fell from 77.6% to 42.6%, and the
  tokens per success nearly doubled. That's the shape AgentDojo found for
  some defences. "Stop" stands as built, but the report says what it gives
  up: the layers' one real gain is against planted instructions, and the
  next version should keep it.
- **The security line is thin.** It rests on five dev tasks, one kind of
  planted instruction, and a judge whose TPR is unmeasured. Its passes on
  the layered runs are the first ones to label.
- **The approved changes don't cost more.** Per success, prompt v2 spends
  about what the baseline does, and FP8 and the no-labels run a little
  less. Compaction spends about 13% more for no gain. FP8's real saving is
  in serving hardware, which a token count doesn't show.
- **The layers' cost is a floor.** Their in-loop support-judge calls, about
  one for every two runs, were counted but their tokens weren't recorded.

So the report's results get two more columns beside each change's pass
rate: an attack line and a cost line.

</Subsection>

<Subsection title="Limits" variant="a">

Every evaluation is of one agent, on one suite, in one setting. The
report lists what this one can't speak to:

- **One configuration.** A 4-billion-parameter model at one revision,
  with one prompt, served one way. Nothing here transfers to another
  model, or to this model with different settings, without a rerun;
  [Lesson 10](/07-evaluation/10-regression-tests/01-what-changed-and-the-last-known-good-run/)
  showed how much a single setting can change.
- **A simulated world and a simulated user.** The registry, its faults
  and its documents are a simulation built for the course, and multi-turn
  conversations used a model playing the user.
  [Lesson 4 audited the simulated user](/07-evaluation/04-task-suite/03-conversations-and-the-simulated-user/),
  but real users and a real registry will do things neither does.
- **A small suite.** 125 tasks, with three groups of six tasks or fewer.
  Those groups are reported as counts because nothing more can be said
  about them.
- **Judges measured on few labels, by one person.** The correctness
  judge's error rates rest on 18 test labels, and two judges have never
  been shown a labelled pass. One person labelled them; how consistently
  is waiting on the relabelling of 30 items, due three weeks after the
  first pass, which
  [Lesson 7](/07-evaluation/07-measuring-judges/02-labels-from-people/)
  set up for exactly this.
- **Readings by one reader.** The reading behind Lessons 3, 9 and 10 was
  done by one reader, sometimes the course's content chat. Its
  conclusions are evidence of what happened in the runs read, not rates.
- **No latency claims.** Runs were made 48 at a time on a shared GPU, so
  their durations measure the GPU's load as much as the agent.
- **Five trials per task.** Pass^k beyond k = 5 can't be estimated for
  the whole suite (Lesson 9 reached k = 10 only on tasks that ran in both
  baseline batches), and single tasks can't be tested for small changes.
- **The two approved changes were never run together.** Prompt v2 and FP8
  were each measured against the baseline alone, so the combination
  they'd ship as needs its own pass through Lesson 10's gate on dev tasks.
- **One agent.** Evaluating a system of several agents, and its failures,
  is Module 8's subject.
- **A small injection suite.** The security line rests on five dev tasks
  with one kind of planted instruction, judged by a judge whose TPR is
  unmeasured.
- **The layers' in-loop judge tokens weren't recorded.** Their
  support-judge calls were counted but not measured, so the layers' cost
  is a floor.
- **The held-out contact,** as disclosed.
- **No real users.** Everything in Lesson 11 was simulated from recorded
  runs.

</Subsection>

<Subsection title="What's next" variant="b">

The report ends with what should happen next, ordered by what it would
change:

1. **Label where the headline rests on least.** The correctness judge's
   runs, and passes for the false-report and planted-instruction judges.
   For the planted judge, the 13 layered dev replies it passed are ready to
   label. Until those labels exist, the question, lost-write and planted
   groups can't be corrected.
2. **Finish the relabel.** Agreement between the two passes sets how far
   any label in this module can be trusted.
3. **Fix the citation check, then settle the labels.** It passes answers
   that cite nothing, which part of the source-label gain turned on. Rerun
   that comparison with the fixed check, and remove the labels if the gain
   holds.
4. **Test compaction where it's meant to help.** On this agent it buys
   nothing, because no run outgrows the context window. Tasks with long
   runs would test what it's for; until then it stays off.
5. **Build layers v3, and measure it the same way.**
   [Lesson 10 described it](/07-evaluation/10-regression-tests/04-three-real-changes/):
   keep identifiers, skip empty claims, leave attribution sentences to the
   citation check. It hasn't been run. Measure it on both lines: it
   should keep the layers' 8 of 25 against planted instructions while
   bringing the benign pass rate back near the baseline's.
6. **Rebuild the held-out set.** Fold the old one into dev, hold out a
   fresh set within each category, and keep a contact log as it happens.
7. **Watch it in use.** If the agent goes live,
   [Lesson 11's plan](/07-evaluation/11-monitoring/00-intro/): a dashboard
   from traces, a two-window burn-rate alert on runs without an answer,
   the relevance judge on a sample sized for the interval needed, PSI on
   the request mix, and an A/A test before any A/B test.
8. **Gate the combination.** Run prompt v2 and FP8 together through the
   gate on dev tasks before either ships.

</Subsection>
