<Subsection title="A report serves a decision" variant="a">

Eleven lessons have produced a great many numbers about the registry
agent. A report is not all of them. It's the subset someone needs to make
a decision, with enough about each number to know how far to trust it.
Three readers matter:

- **Whoever decides** whether the agent is fit for its job, which changes
  ship, and where effort goes next. They need the headline results, how
  sure those results are, and what wasn't measured.
- **Whoever maintains the agent.** They need the exact configuration that
  was evaluated, so a later run can be compared with it, and the failures
  to work on.
- **Whoever evaluates it next.** They need to know how the suite was built
  and graded, what each grader gets wrong, and which tasks have already
  been seen, so the next round doesn't repeat this one's mistakes.

[Anthropic's guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
says its teams don't take an eval score at face value until someone has
read some of the transcripts behind it. A report should make that
possible for its readers: every number names the runs it came from, so
anyone can open them.

</Subsection>

<Subsection title="A shape that already exists" variant="b">

Reports on machine-learning systems have a standard starting shape.
[Mitchell et al. (2019)](https://arxiv.org/abs/1810.03993) proposed
**model cards**: short documents that travel with a model and report its
evaluation in nine sections. Each has a counterpart for an agent:

- **Model details** → the agent's exact configuration: model and
  revision, sampling settings, the hash of its prompt and tool
  definitions, how it was served. For an agent graded by judges, the
  judges' model, rubric version and the task file's version belong here
  too: a change to any of them moves every number.
- **Intended use** → what the agent is for and what it isn't. The
  registry agent looks up agents, checks their health, answers questions
  from the company's documents, changes models and emails owners; it
  isn't for decisions its tools can't verify.
- **Factors** → the groups results should be broken down by: here, the
  kinds of task, from documentation questions to lost writes and planted
  instructions.
- **Metrics** → what counts as a pass, and the other numbers reported:
  pass^k, runs without an answer, cost.
- **Evaluation data** → the suite: where its tasks came from, and how dev
  and held-out tasks were chosen.
- **Training data** → for an agent built on a pretrained model, what the
  agent was developed against: the dev tasks its prompt and checks were
  shaped on.
- **Quantitative analyses** → the results, overall and broken down by the
  factors, rather than one number.
- **Ethical considerations** → what could go wrong when the agent acts:
  changes it makes to the registry, instructions planted in documents,
  documents some users may not read.
- **Caveats and recommendations** → the limits of the evaluation, and
  what to do next.

An agent needs three sections a model card doesn't have:

- **The graders, and how often they're wrong.** A model card's metrics
  are usually computed exactly. An agent's are often a judge's verdicts,
  which
  [Lesson 7 measured](/07-evaluation/07-measuring-judges/01-a-judge-is-a-measurement/).
- **Decisions on changes.** The pieces that were switched on and off, and
  the changes that were gated, with what was decided and why.
- **How it's watched in use.** The dashboard, alerts and sampled judging
  from
  [Lesson 11](/07-evaluation/11-monitoring/01-what-to-watch-on-every-run/).

Model developers now also publish system cards for models and the agents
built on them. They extend the model-card idea with safety evaluations,
such as how often an agent follows instructions injected into what it
reads, reported alongside how well it does its job.

</Subsection>

<Subsection title="Three kinds of statement" variant="b">

Every sentence in an evaluation report is one of three kinds, and the
report should make it obvious which:

- **Measured.** A number, with how many tasks and trials it rests on, an
  interval, and the graders that produced it. "The baseline passes 74% of
  dev trials" is incomplete until it says over how many tasks, how sure,
  and graded by what.
- **Read.** Something a person saw reading runs: that grounding's
  objections were mostly false alarms, say. It's evidence, but of a
  different kind, and it should say how many runs were read, how they
  were chosen, and by whom. Several of this module's readings were done
  by one reader, sometimes the course's content chat (the Claude model
  this course is drafted with, not a person), and the report
  should say so.
- **Not measured.** An assumption, or a question nobody has tested yet.
  Saying so explicitly is part of the report, not a weakness in it: a
  reader can't distinguish an untested risk from a tested one unless
  they're told.

The second and third kinds are where model cards' "caveats and
recommendations" live, and where most of a report's honesty is. The rest
of this lesson builds the registry agent's report section by section: the
headline numbers with their uncertainty, the held-out results and their
history, how far to trust each grader, and the decisions, limits and next
steps.

</Subsection>
