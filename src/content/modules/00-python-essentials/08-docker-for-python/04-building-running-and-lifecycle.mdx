`docker build -t my-app .` reads the `Dockerfile` in the current
directory, producing an image tagged `my-app`. `docker run my-app`
starts a container from that image —
[an instance from that class](/00-python-essentials/08-docker-for-python/02-images-vs-containers/#the-analogy-a-class-and-its-instances),
in the terms of the earlier concept.

</Subsection>

<Subsection title="Reaching a container from outside: port mapping" variant="b">

A process running *inside* a container is, by default, only reachable
from inside that container. `-p` maps a port on your machine to a port
inside the container:

<TerminalGroup
  client:load
  panes={[
    {
      label: "Port mapping",
      steps: [
        { command: "docker run -p 8000:5000 my-app" },
        { output: "Starting app on port 5000..." },
        { output: "Connected successfully" },
      ],
    },
  ]}
/>

`8000:5000` reads as "your machine's port 8000 forwards to the
container's port 5000." From outside, you'd reach the app at
`localhost:8000`, even though the app itself, inside the container,
might be listening on 5000. Recall
[`EXPOSE` alone doesn't do this](/00-python-essentials/08-docker-for-python/03-writing-a-dockerfile/#expose-documentation-not-a-port-mapping)
— `-p` is what actually publishes the port.

</Subsection>

<Subsection title="Overriding configuration at run time" variant="a">

[`ENV` sets a default baked into the image](/00-python-essentials/08-docker-for-python/03-writing-a-dockerfile/#three-pairs-worth-knowing-apart);
`-e` at `docker run` time overrides it for a specific container, without
needing to rebuild the image:

<TerminalGroup
  client:load
  panes={[
    {
      label: "Overriding LOG_LEVEL at run time",
      steps: [
        { command: "docker run -p 8000:5000 -e LOG_LEVEL=debug my-app" },
        { output: "Starting app on port 5000... (log level: debug)" },
        { output: "Connected successfully" },
      ],
    },
  ]}
/>

</Subsection>

<Subsection title="Running in the background: -d" variant="b">

Every example so far ties up the terminal — the container runs in the
foreground, printing its output directly, until you stop it or it exits.
`-d` ("detached") starts it in the background instead, immediately
returning control of the terminal and printing the new container's ID:

<TerminalGroup
  client:load
  panes={[
    {
      label: "Running detached",
      steps: [
        { command: "docker run -d -p 8000:5000 my-app" },
        { output: "a1b2c3d4e5f67890abcdef1234567890fedcba0987654321abcdef012345678" },
      ],
    },
  ]}
/>

This is the normal way to run something you intend to keep running while
you do other things — including, as covered next, actually inspecting
and managing it.

</Subsection>

<Subsection title="The lifecycle: seeing, reading, entering, and stopping a container" variant="a">

`docker ps` lists currently running containers; `docker logs` shows
everything a container has printed, even running detached; `docker exec`
runs a command *inside* an already-running container, useful for
inspecting or debugging something live without stopping it; `docker
stop` sends a shutdown signal and waits for a graceful exit, and `docker
rm` actually removes the stopped container — its filesystem, its logs,
everything. A stopped container still exists until it's explicitly
removed:

<TerminalGroup
  client:load
  panes={[
    {
      label: "The full lifecycle, one command at a time",
      steps: [
        { command: "docker ps" },
        {
          output:
            "CONTAINER ID   IMAGE     COMMAND            PORTS                    NAMES\na1b2c3d4e5f6   my-app    \"python3 app.py\"   0.0.0.0:8000->5000/tcp   happy_turing",
        },
        { command: "docker logs a1b2c3d4e5f6" },
        { output: "Starting app on port 5000...\nConnected successfully" },
        { command: "docker exec a1b2c3d4e5f6 cat /app/requirements.txt" },
        { output: "flask==3.0.0" },
        { command: "docker stop a1b2c3d4e5f6" },
        { command: "docker rm a1b2c3d4e5f6" },
      ],
    },
  ]}
/>

You can refer to a container by its full ID, a shortened prefix (as
shown above), or the auto-generated name `docker ps` displays (like
`happy_turing`) — all three work interchangeably with every command in
this section.

</Subsection>

image as `my-app`, start it detached with `8000:5000` mapped and
