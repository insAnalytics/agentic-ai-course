<Subsection title="@app.websocket -- a different kind of route" variant="a">

A WebSocket route uses its own decorator, not `@app.get`/`@app.post` —
it's handling something structurally different from a normal HTTP
request/response cycle:

```python
from fastapi import FastAPI, WebSocket

app = FastAPI()

@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()   # completes the handshake -- connection is now open and persistent
    while True:   # keeps handling messages for as long as the connection stays open
        message = await websocket.receive_text()   # pauses here, in place, until a message arrives
        await websocket.send_text(f"echo: {message}")
```

`curl` can't hold a WebSocket connection open the way it can an SSE
stream — `websocat` (a small CLI WebSocket client) is used here
instead, connecting once and then sending whatever's typed:

Two things worth noticing: the connection only happened once — every
line after it reuses the same open channel, no reconnecting per
message — and each line typed gets its own echoed response back
immediately, in the order it was sent, exactly the request/reply shape
`while True:` inside `websocket_endpoint` is built to keep handling for
as long as the connection stays open.

`await websocket.accept()` completes the protocol handshake — a
WebSocket connection starts as a normal HTTP request, then "upgrades"
to the WebSocket protocol; `accept()` is what agrees to that upgrade.
After it, `websocket` represents a genuinely persistent, open
connection — not a single request being handled once, but a channel
that stays open until something closes it.

</Subsection>

<Subsection title="The message loop" variant="b">

Unlike a normal route, which runs once per request and returns, a
WebSocket route typically runs a `while True:` loop for as long as the
connection stays open —
[an intentional, correct use of an infinite loop](/00-python-essentials/01-python-basics/02-control-flow-and-syntax/#while-loops-and-no),
since the connection itself, not a fixed number of iterations,
determines when the loop ends. `receive_text()` and `send_text()` are
both `await`-able —
[genuinely I/O-bound operations](/00-python-essentials/07-async-python/01-why-concurrency-matters/#why-this-is-wasteful),
waiting on the network exactly the way any other I/O this course has
covered does.

That `await` is what actually makes this a WebSocket route rather than
an HTTP one: it pauses `websocket_endpoint` in place — connection still
open — until the client sends something, then resumes right there. A
normal route has no equivalent; it returns once and the connection
ends with it. Looped, that pause-and-resume is the server listening on
one open channel instead of answering once and leaving.

</Subsection>

<Subsection title="receive_json() / send_json() -- the convenience version" variant="a">

Sending plain text and parsing it yourself is rarely how real messages
look — `receive_json()`/`send_json()` handle
[the JSON conversion from the I/O lesson](/00-python-essentials/06-files-errors-and-validation/02-working-with-json/#json-is-just-text-and-it-maps-directly-onto-dicts-and-lists)
automatically, working with dicts directly instead of strings:

```python
@app.websocket("/ws/agent")
async def agent_websocket(websocket: WebSocket):
    await websocket.accept()
    while True:
        message = await websocket.receive_json()   # parsed into a dict automatically -- no json.loads() needed
        if message["action"] == "start_task":
            await websocket.send_json({"status": "started", "progress": 0})
        elif message["action"] == "cancel":
            await websocket.send_json({"status": "cancelled"})
```

`send_json({"status": "started", "progress": 0})` handles the reverse
serialization the same way.

</Subsection>
