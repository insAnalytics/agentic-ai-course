<Subsection title="Path parameters — part of the URI itself" variant="a">

A `{"{...}"}` segment in a route's path becomes a function parameter,
automatically extracted from the actual URI a request came in on:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/agents/{agent_id}")
def get_agent(agent_id: int):
    return {"agent_id": agent_id, "name": "research_agent"}
```

A request to `/agents/42` calls `get_agent(agent_id=42)` — as an actual
`int`, already converted, not the string `"42"`. This is
[the same automatic-validation mechanism from the previous concept](/00-python-essentials/09-building-apis-with-fastapi/02-what-is-fastapi/#why-this-fits-agent-backends-specifically),
now applied to a path segment: the type hint isn't just documentation
here, it's a real parsing step.

Requesting `/agents/not-a-number` — something that can't be parsed as an
`int` — never reaches `get_agent` at all:

<TerminalGroup

  panes={[

      steps: [
        { command: "curl http://127.0.0.1:8000/agents/42" },

    },

/>

That second response is automatic — HTTP status `422`, a structured
error body, and `get_agent` never actually running. No manual
`isinstance` check, no `try`/`except` needed for this case at all.

</Subsection>

<Subsection title="Query parameters — everything else in the function signature" variant="b">

Any function parameter *not* named in the path becomes a **query
parameter** instead — read from the URI's `?key=value` portion:

```python
@app.get("/agents")
def list_agents(model: str = None, limit: int = 10):
    return {"model_filter": model, "limit": limit}
```

<TerminalGroup
  client:load
  panes={[
    {
      label: "Query parameters from the URI",
      steps: [
        { command: "curl \"http://127.0.0.1:8000/agents?model=claude-sonnet&limit=5\"" },
        { output: '{"model_filter": "claude-sonnet", "limit": 5}' },
      ],
    },
  ]}
/>

That request calls `list_agents(model="claude-sonnet", limit=5)`. A
default value (`= None`, `= 10`) makes the parameter optional — omitting
it from the URI just uses the default, exactly like
[a regular function's default argument](/00-python-essentials/03-functions-and-reuse/01-function-fundamentals/#default-arguments).

</Subsection>

<Subsection title="Query() and Path() — validation beyond just the type" variant="a">

A type hint alone only checks *shape* (is this an `int`). `Query()` and
`Path()` add real constraints — a minimum, a maximum, a length limit —
directly in the function signature:

```python
from fastapi import FastAPI, Query, Path

app = FastAPI()

@app.get("/agents")
def list_agents(limit: int = Query(default=10, gt=0, le=100)):
    return {"limit": limit}

@app.get("/agents/{agent_id}")
def get_agent(agent_id: int = Path(gt=0)):
    return {"agent_id": agent_id}
```

<TerminalGroup
  client:load
  panes={[
    {
      label: "Constraints beyond just type",
      steps: [
        { command: "curl \"http://127.0.0.1:8000/agents?limit=500\"" },
        {
          output:
            '{"detail": [{"type": "less_than_equal", "loc": ["query", "limit"], "msg": "Input should be less than or equal to 100", "input": "500"}]}',
        },
        { command: "curl http://127.0.0.1:8000/agents/0" },
        {
          output:
            '{"detail": [{"type": "greater_than", "loc": ["path", "agent_id"], "msg": "Input should be greater than 0", "input": "0"}]}',
        },
      ],
    },
  ]}
/>

`Query(default=10, gt=0, le=100)` means: default to `10` if omitted,
reject anything not strictly greater than `0`, reject anything above
`100` — `limit` never even reaching `list_agents` in the first case
above. `Path(gt=0)` does the same for a path parameter — the second
case — refusing an `agent_id` of `0` or negative, even though it's
already a valid `int`.

</Subsection>

<Subsection title="Header() and Cookie() — the same mechanism, different source" variant="b">

**Headers** are metadata attached to a request or response, separate
from the URI and the body — they describe something *about* the
request rather than being part of the resource itself: what format the
body is in, an auth token, a request ID for tracing a call through
logs. `X-Request-Id: abc123` in the demo below is exactly that kind of
header — information about this specific call, not data belonging to
`/whoami` the resource.

**Cookies** are a specific header (`Cookie` on requests, `Set-Cookie` on
responses) with one particular job: letting the server recognize the
*same client* across multiple separate requests. Recall from
[REST's statelessness principle](/00-python-essentials/09-building-apis-with-fastapi/01-rest-api-fundamentals/#rest-s-guiding-principles)
that the server itself remembers nothing between requests — a cookie is
how a client carries its own continuity along, sending the same value
back on every request so the server can look it up, most commonly for
session identification.

Extracting either one works identically to a query or path parameter — a
parameter typed with `Header()` or `Cookie()` instead of
`Query()`/`Path()`:

```python
from fastapi import Header, Cookie

@app.get("/whoami")
def whoami(x_request_id: str = Header(default=None), session_id: str = Cookie(default=None)):
    return {"request_id": x_request_id, "session_id": session_id}
```

<TerminalGroup
  client:load
  panes={[
    {
      label: "Reading a header and a cookie",
      steps: [
        { command: 'curl http://127.0.0.1:8000/whoami -H "X-Request-Id: abc123" --cookie "session_id=xyz789"' },
        { output: '{"request_id": "abc123", "session_id": "xyz789"}' },
      ],
    },
  ]}
/>

FastAPI automatically converts a parameter name like `x_request_id` to
the header name `X-Request-Id` — headers conventionally use hyphens,
Python identifiers can't, so this conversion happens for you.

</Subsection>

<Subsection title="The route-ordering gotcha" variant="a">

Routes are matched top to bottom, and the *first* matching route wins —
worth being careful with, since a dynamic path segment matches almost
anything:

```python
@app.get("/agents/{agent_id}")
def get_agent(agent_id: str):
    return {"agent_id": agent_id}

@app.get("/agents/me")
def get_current_agent():
    return {"agent_id": "current-user's-agent"}
```

<TerminalGroup
  client:load
  panes={[
    {
      label: "/agents/{agent_id} defined first — wrong",
      steps: [
        { command: "curl http://127.0.0.1:8000/agents/me" },
        { output: '{"agent_id": "me"}' },
      ],
    },
  ]}
/>

That request matches `/agents/{agent_id}` *first* — `me` is a perfectly
valid string for `agent_id` — so `get_current_agent` never actually
runs; `get_agent(agent_id="me")` handles it instead. The fix is ordering
the more specific, static route *before* the dynamic one:

```python
@app.get("/agents/me")
def get_current_agent():
    return {"agent_id": "current-user's-agent"}

@app.get("/agents/{agent_id}")
def get_agent(agent_id: str):
    return {"agent_id": agent_id}
```

<TerminalGroup
  client:load
  panes={[
    {
      label: "/agents/me defined first — fixed",
      steps: [
        { command: "curl http://127.0.0.1:8000/agents/me" },
        { output: '{"agent_id": "current-user\'s-agent"}' },
      ],
    },
  ]}
/>

Same request, same two routes, just reordered — now the specific route
actually gets a chance to match before the dynamic one swallows it.
This is
[the same top-to-bottom, first-match-wins principle from except clause ordering](/00-python-essentials/01-python-basics/03-error-handling/#order-matters-with-multiple-except-clauses),
applied to routes instead of exception types: list the more specific
case first, or it never gets a chance to match.

</Subsection>
