<Subsection title="Every piece has a price" variant="a">

This module built a lot of machinery, and
[the previous concept](/04-context-and-memory/12-assembling-the-context-step/02-measuring-the-before-and-after/)
measured what all of it costs together. On a short task, the full context
step cost half as much again as a naive loop that simply fit. Each piece
earns its place only when the problem it solves is actually present, and
each has a price when it isn't:

- **Money:** rewrites break the cache, anchors are restated every turn, and
  summaries are extra calls.
- **Round trips:** offloaded results and tools loaded on demand have to be
  fetched.
- **Loss:** summaries and trimming are lossy by design.
- **Complexity:** every piece is more code to get wrong, and more places to
  look when the agent misbehaves.

Anthropic's advice for building agents applies to context management
exactly: [find the simplest solution possible, and only increase complexity
when needed](https://www.anthropic.com/news/building-effective-agents), and
add complexity *only* when it demonstrably improves outcomes.

</Subsection>

<Subsection title="Start by measuring" variant="b">

The module's first and last tools are the ones to reach for before anything
else.
[Lesson 1's `TurnTracker`](/04-context-and-memory/01-the-context-budget/03-watching-it-grow-across-the-loop/)
shows where a request's tokens go and how fast they grow.
[`run_report`](/04-context-and-memory/12-assembling-the-context-step/02-measuring-the-before-and-after/)
shows what a run cost and what went missing from it. The piece to add is the
one that answers what they show.

</Subsection>

<Subsection title="A guide to what to add" variant="a">

**Almost every agent:**

- **A stable prefix,** from
  [Lesson 3](/04-context-and-memory/03-prompt-caching/00-intro/). The tools
  and the system prompt are fixed, with nothing changing near the start. It
  costs nothing but care, and pays on every request.
- **Keeping failed attempts visible, and restating the goal and rules at the
  end,** from
  [Lesson 2](/04-context-and-memory/02-context-that-fits-but-still-hurts/00-intro/).
  The anchor
  [costs one message of cache reuse per turn](/04-context-and-memory/03-prompt-caching/03-where-lesson-2s-techniques-stand-and-the-fights-ahead/),
  and it's what keeps a long run on track.

**Long single tasks,** when the tracker shows the history heading for the
window:

- **Fit in batches, clearing before cutting**
  ([Lesson 4](/04-context-and-memory/04-when-the-window-fills/00-intro/)).
  Fitting in batches broke the prefix
  [3 times in 30 turns instead of 17](/04-context-and-memory/04-when-the-window-fills/03-clear-before-you-cut-and-cut-in-batches/).
- **Offload large results when they arrive**
  ([Lesson 6](/04-context-and-memory/06-offloading-context-to-storage/00-intro/)).
  One large log sent about
  [a tenth of the tokens](/04-context-and-memory/06-offloading-context-to-storage/01-keep-the-reference-not-the-result/),
  at the price of two extra round trips.
- **Compact only after clearing**
  ([Lesson 5](/04-context-and-memory/05-compaction-and-summarization/00-intro/)).
  Clearing alone
  [matched summarization in the JetBrains study](/04-context-and-memory/05-compaction-and-summarization/01-what-clearing-cant-do/),
  and summaries are lossy. Compaction earns its place when clearing can no
  longer keep up. And on long enough runs,
  [fold the summaries](/04-context-and-memory/12-assembling-the-context-step/02-measuring-the-before-and-after/)
  too.

**Many tools, or long instructions,** when definitions or runbooks dominate
the request:

- **Load them on demand**
  ([Lesson 7](/04-context-and-memory/07-just-in-time-context-and-dynamic-tool-exposure/00-intro/)).
  The prefix shrank
  [26 times](/04-context-and-memory/07-just-in-time-context-and-dynamic-tool-exposure/00-intro/),
  but cost fell only about 21% on that task, because searches are round
  trips. If a provider offers built-in tool search, prefer it, since it
  keeps each tool's schema enforced.

**Large data the task searches through,** such as logs, documents or a
codebase:

- **Let the agent explore it**
  ([Lesson 7](/04-context-and-memory/07-just-in-time-context-and-dynamic-tool-exposure/04-data-on-demand/)).
  A one-line map up front, and bounded list, search and read tools for the
  rest, sent over ten times fewer tokens than pasting the files in. The
  price is round trips, and the risk is an agent that never looks, so the
  rules that must always apply stay in the prefix.

**Across sessions,** when users come back and shouldn't have to repeat
themselves:

- **Long-term memory, with its write rules from the start**
  ([Lessons 8–10](/04-context-and-memory/08-long-term-memory/00-intro/)). If
  an agent has memory at all,
  [the source rule](/04-context-and-memory/10-deciding-what-to-remember/03-memory-poisoning-and-the-source-rule/#the-source-rule)
  isn't optional: one planted instruction replays in every future session.
- **Scoring and forgetting once the store grows**
  ([Lesson 11](/04-context-and-memory/11-forgetting-aging-and-retrieval-quality/00-intro/)).
  They matter after months of sessions, not in the first week.

**Short tasks that fit:** none of the fitting, compaction or offloading
machinery. The canonical loop, with a stable prefix, is the right design.

</Subsection>

<Subsection title="Where the module leaves off" variant="b">

Several questions this module raised belong to later modules:

- **Retrieval by meaning,** rather than by keywords, for tools, notes and
  memories: Module 5.
- **Guardrails** on what an agent may do with what it recalls: Module 6.
- **Measuring whether any of this makes the agent better at its task,**
  which is the question every choice here ultimately depends on: Module 7.
- **Sub-agents** that keep messy work out of the main context altogether:
  Module 8.
- **Showing users their memories, and letting them edit them:** Module 9.
- **Retention, deletion rights and compliance:** Module 10.

</Subsection>
