<Subsection title="A request is more than the conversation" variant="a">

When people picture what a model "sees", they picture the conversation:
the user's messages and the model's replies. For an agent, that's the
smallest part of the story. Every request
[the loop from Module 2](/02-the-agent-loop/05-react-and-reasoning-in-the-loop/01-the-react-pattern/)
sends is assembled from several pieces, and all of them occupy the same
context window:

- **The system prompt.** The agent's standing instructions,
  [its identity and rules](/02-the-agent-loop/03-the-system-prompt-as-agent-design/01-what-the-system-prompt-is/).
  Sent in full on every request.
- **The tool definitions.** Every tool's name, description and schema. Also
  sent in full on every request, because
  [the model API is stateless](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/03-multi-turn-conversations/),
  and
  [Module 3 showed how large these get](/03-tool-design-for-agents/07-connecting-an-agent-to-mcp-servers/03-when-there-are-too-many-tools/)
  once several servers are connected.
- **The scratchpad.**
  [Everything the loop has accumulated](/02-the-agent-loop/07-agent-state-and-the-scratchpad/01-the-scratchpad/):
  the user's messages, each assistant turn with its text, `tool_use` and
  thinking blocks, and every `tool_result`. This is the part that grows.
- **Room for the reply.** The space reserved for the model's answer, set by
  `max_tokens`.

This lesson measures each of these, because the rest of the module is about
managing them, and you can't manage what you haven't measured.

</Subsection>

<Subsection title="Counting tokens" variant="b">

Everything in this module is measured in tokens,
[the unit models actually read](/01-llm-foundations/01-tokenization/00-intro/).
A real count needs the model's own tokenizer, and different models'
tokenizers give slightly different numbers for the same text. This course
uses one simple helper instead, the same "about four characters per token"
estimate
[Module 3's result-size lesson](/03-tool-design-for-agents/03-shaping-what-tools-return/01-why-a-huge-tool-result-hurts/)
used:

```python
import json
import math

def _plain(x):
    # turn content-block objects into plain dicts, so everything can be written as JSON
    if isinstance(x, (str, int, float, bool)) or x is None:
        return x
    if isinstance(x, dict):
        return {key: _plain(value) for key, value in x.items()}
    if isinstance(x, (list, tuple)):
        return [_plain(value) for value in x]
    return _plain(vars(x))

def count_tokens(x) -> int:
    """Approximate token count: about 4 characters per token. Deterministic, not a real tokenizer."""
    if isinstance(x, str):
        return math.ceil(len(x) / 4)
    return math.ceil(len(json.dumps(_plain(x))) / 4)
```

*(already loaded for every demo and exercise in this module)*

It's an approximation, deliberately. What it gives you is consistency:
every budget number in this module comes from this one function, so the
arithmetic always agrees with itself. `math.ceil` rounds up, so even a
single character counts as one token. Anything that isn't a plain string, a
tool definition, a content block, a whole list of messages, is counted by
its JSON form, which is roughly how it's sent to a real API.

</Subsection>

<Subsection title="The reply comes out of the same window" variant="a">

The last piece is the one most often forgotten.
[Module 1's context-window lesson](/01-llm-foundations/06-context-windows-and-kv-cache/02-max-output-length-vs-context-window/)
made the point: the context window isn't a limit on the input with the
output on top. It's one budget, shared. Whatever you reserve for the reply
with `max_tokens` has to fit alongside everything you send:

<LiveDemo client:load code={FITS_DEMO} />

200,000 tokens is a common window size, used here as an example. The same
input fits or doesn't depending on how much room is reserved for the reply.
That's why "how much context do I have left?" always means *window minus
input minus reply room*, never window minus input alone. And an agent is the
worst case for this: its input grows every turn, while the reply room it
needs stays about the same.

</Subsection>
