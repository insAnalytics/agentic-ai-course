<Subsection title="More than just the generated text comes back" variant="a">

*Same caveat as the previous concept: the response JSON below is
illustrative of a real API's actual shape, not fetched from a live call.
The Python demos that parse it, however, are ordinary dict access and
genuinely run live.*

A response includes the generated content, but also real metadata about
*how* that generation happened — two fields in particular are the
direct payoff for concepts this module built up over several lessons
without ever showing them as something you'd actually read from a real
response.

```json
{
  "id": "msg_01XyZ",
  "type": "message",
  "model": "claude-haiku-4-5",
  "role": "assistant",
  "content": [
    {"type": "text", "text": "The capital of France is Paris."}
  ],
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {
    "input_tokens": 24,
    "output_tokens": 9
  }
}
```

*(illustrative response shape — not fetched from a live call)*

<LiveDemo client:load code={`response_data = {
    "content": [{"type": "text", "text": "The capital of France is Paris."}],
    "stop_reason": "end_turn",
    "usage": {"input_tokens": 24, "output_tokens": 9},
}

print(response_data["content"][0]["text"])
print(f"used {response_data['usage']['input_tokens']} input tokens, {response_data['usage']['output_tokens']} output tokens")
print(f"stopped because: {response_data['stop_reason']}")`} />

*(the underlying `response_data` dict is illustrative, but this parsing
code is ordinary Python)*

Field names differ a little between providers — for instance,
OpenAI-style responses put the text under `choices[0].message.content`
and report `usage.prompt_tokens` / `usage.completion_tokens` — but the
same three things are always there: the generated content, a token
count, and a reason generation stopped.

</Subsection>

<Subsection title="usage — tokens, finally readable after the fact" variant="b">

`usage.input_tokens` and `usage.output_tokens` are the direct, concrete
payoff for
[everything Lessons 1 and 6 established about tokens being the actual unit an LLM operates in](/01-llm-foundations/01-tokenization/03-tokens-in-practice-and-cost/)
— not just a conceptual fact anymore, but a real number returned after
every single call, telling you exactly how much of
[your shared input/output budget, from Lesson 6](/01-llm-foundations/06-context-windows-and-kv-cache/02-max-output-length-vs-context-window/),
that specific call actually consumed.

</Subsection>

<Subsection title="stop_reason — why generation actually stopped" variant="a">

This field (`stop_reason`, or `finish_reason`, depending on the
provider) directly reflects
[Lesson 5's decoding controls](/01-llm-foundations/05-decoding-strategies-and-generation-controls/06-stop-sequences-and-nondeterminism/)
and
[Lesson 6's shared token budget](/01-llm-foundations/06-context-windows-and-kv-cache/02-max-output-length-vs-context-window/):
did generation end naturally, hit an explicit stop sequence, or get cut
off by hitting `max_tokens`? (There are other values too — a model
deciding to call a tool, or declining a request, each get their own.)

<LiveDemo client:load code={`truncated_response = {
    "content": [{"type": "text", "text": "The three main causes of the French Revolution were economic"}],
    "stop_reason": "max_tokens",
    "usage": {"input_tokens": 18, "output_tokens": 500},
}

if truncated_response["stop_reason"] == "max_tokens":
    print("warning: response was cut off before finishing — consider raising max_tokens")`} />

`stop_reason: "max_tokens"` here is exactly
[the scenario Lesson 6 demonstrated numerically](/01-llm-foundations/06-context-windows-and-kv-cache/02-max-output-length-vs-context-window/)
— the response genuinely ran out of room mid-sentence, and this field is
how you'd actually detect that happened programmatically, rather than
just guessing from an incomplete-looking response.

</Subsection>
