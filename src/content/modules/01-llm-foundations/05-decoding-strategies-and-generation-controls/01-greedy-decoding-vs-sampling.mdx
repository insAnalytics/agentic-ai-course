<Subsection title="The question Lesson 4 deferred" variant="a">

[Lesson 4 established the full generation loop](/01-llm-foundations/04-how-llms-generate-text/02-autoregressive-generation/)
— logits, softmax, a probability distribution over the entire
vocabulary, one step deliberately left open: exactly *how* does a
single token actually get picked from that distribution? That's this
lesson's job, starting with the two most basic answers.

</Subsection>

<Subsection title="Greedy decoding: always take the top candidate" variant="b">

The simplest possible choice: always pick whichever token has the
highest probability.

(This distribution is hand-written for illustration: close to, but not
exactly, the `63.2%` for `"mat"` that Lesson 4's softmax produced.)

<LiveDemo client:load code={`distribution = {"mat": 0.618, "floor": 0.207, "chair": 0.153, "moon": 0.008, "xylophone": 0.002}

def greedy_choice(probabilities: dict) -> str:
    return max(probabilities, key=probabilities.get)

print(greedy_choice(distribution))
print(greedy_choice(distribution))
print(greedy_choice(distribution))`} />

`max(probabilities, key=probabilities.get)` —
[the exact same pattern used for finding the most frequent pair back in Lesson 1's BPE demo](/01-llm-foundations/01-tokenization/02-subword-tokenization-bpe/) —
always returns `"mat"`, every single time, since it's always the single
highest-scoring candidate. Greedy decoding is fully deterministic: the
same distribution always produces the same choice. The real drawback
shows up over a long generation, not a single token: always taking the
"safest" option at every step tends to produce text that's noticeably
repetitive, bland, and predictable, sometimes even getting stuck
looping on the same phrase — never taking a genuinely
less-likely-but-still-reasonable path, because greedy decoding
structurally can't.

</Subsection>

<Subsection title="Sampling: actually drawing from the distribution" variant="a">

The alternative: instead of always taking the top candidate, genuinely
sample a token according to the probabilities themselves — a token with
a `20%` probability should actually get chosen roughly `20%` of the
time, not simply lose to whichever token happens to be highest:

<LiveDemo client:load code={`import random

def sample_choice(probabilities: dict) -> str:
    tokens = list(probabilities.keys())
    weights = list(probabilities.values())
    return random.choices(tokens, weights=weights, k=1)[0]

distribution = {"mat": 0.618, "floor": 0.207, "chair": 0.153, "moon": 0.008, "xylophone": 0.002}

random.seed(42)   # fixes randomness for this demo's output -- real sampling wouldn't do this
for _ in range(5):
    print(sample_choice(distribution))`} />

`random.choices(tokens, weights=weights, k=1)` is a new tool worth
naming directly: it draws one item from `tokens`, where each item's
chance of being picked is proportional to its corresponding entry in
`weights` — precisely "draw according to these probabilities," rather
than "always pick the biggest one." `"mat"` still comes up most often in
this run, since it genuinely has the highest probability, and `"floor"`
also shows up, reflecting its own real, nonzero share of the
distribution — run this same seeded demo again and you'll get this exact
same sequence every time, but drop the fixed seed (as real generation
always does) and a different run could just as easily surface
`"chair"`, or, far more rarely, `"moon"` or `"xylophone"`, each roughly
as often as its actual probability. `random.seed(42)` is only present to
make this specific demo's output reproducible for teaching purposes;
real generation never fixes a seed this way, which is exactly why
sampling produces genuinely different output across separate runs, even
from an identical prompt.
