<Subsection title="Closing synthesis — choose settings for a real use case" variant="a">

This isn't graded — it's a chance to apply the whole lesson to a
practical decision, extending
[the decoding playground built across the greedy, temperature and top-p/top-k concepts](/01-llm-foundations/05-decoding-strategies-and-generation-controls/01-greedy-decoding-vs-sampling/#sampling-actually-drawing-from-the-distribution)
into an exercise in choosing settings.

For each scenario, decide roughly what you'd set — temperature (low,
medium, high), whether top-p/top-k would help, and whether a
repetition penalty matters — before checking your reasoning against the
playground on a similar prompt:

1. **A customer support bot answering account-specific factual
   questions.**
2. **A brainstorming tool generating varied marketing taglines.**
3. **A code-generation assistant.**

<DecodingPlayground client:load showTemperature showTopKTopP />

The playground has sliders for temperature, top-k, and top-p; the
repetition penalties aren't modeled there, so reason about those
directly from the frequency/presence-penalty concept.

*Reasoning to check your choices against:* (1) wants low temperature,
close to greedy — consistency and precision matter far more than
variety here, and
[nondeterminism at temperature 0](/01-llm-foundations/05-decoding-strategies-and-generation-controls/06-stop-sequences-and-nondeterminism/#a-common-wrong-assumption-temperature-0-means-identical-output-always)
is a real caveat worth knowing about even in this exact use case. (2)
wants meaningfully higher temperature, and top-p is genuinely useful
here — allowing real variety in word choice is the entire point, and a
presence penalty helps avoid the same few taglines dominating
repeatedly. (3) is the most interesting case: mostly low temperature,
since exact syntax matters enormously and a wrong token can break
working code — but not *zero*. It also wants *no* repetition penalty:
code legitimately repeats identifiers, brackets and keywords constantly,
and a frequency penalty pushes the model away from exactly the tokens it
needs. To contain a model stuck in an actual repetition loop (like
re-emitting the same broken line), a real failure mode
[the opening concept named directly](/01-llm-foundations/05-decoding-strategies-and-generation-controls/01-greedy-decoding-vs-sampling/#greedy-decoding-always-take-the-top-candidate),
rely on
[`max_tokens`](/01-llm-foundations/06-context-windows-and-kv-cache/02-max-output-length-vs-context-window/)
and
[stop sequences](/01-llm-foundations/05-decoding-strategies-and-generation-controls/06-stop-sequences-and-nondeterminism/#stop-sequences-controlling-when-generation-ends-not-which-token-comes-next)
to cap how far it can run instead.

The pattern worth taking away: every one of these settings is a genuine
trade-off, not a "better" or "worse" direction in the abstract —
choosing well means matching the control to what the specific use case
actually needs, exactly the same reasoning this lesson has built toward
one mechanism at a time.

</Subsection>
