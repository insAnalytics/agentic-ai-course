<Subsection title="The total token budget for one request" variant="a">

A **context window** is the maximum number of tokens a model can
process in a single request — everything counted together: the prompt,
any conversation history, documents provided, and (as
[the next concept covers directly](/01-llm-foundations/06-context-windows-and-kv-cache/02-max-output-length-vs-context-window/)) the response itself. It isn't an arbitrary business
limit — it comes from how the model is built
([the architecture covered in Lesson 3](/01-llm-foundations/03-attention-and-transformer-architecture/00-intro/))
and how it was trained.

</Subsection>

<Subsection title="Why there's a limit at all: three constraints" variant="b">

Three separate things limit how long a context can be. Each one gets
harder as the number of tokens grows, and a real model's window is set
where all three are still manageable.

**1. Compute.** [Attention, from Lesson 3](/01-llm-foundations/03-attention-and-transformer-architecture/02-the-attention-mechanism/#query-key-value-the-mechanism-that-produces-those-weights),
computes a relevance score between *every pair* of tokens in the
sequence — every token compares its Query against every other token's
Key. That means the amount of computation required grows with the
*square* of the sequence length, not linearly with it:

<LiveDemo client:load code={`def attention_pair_count(sequence_length: int) -> int:
    return sequence_length ** 2

for length in [10, 100, 1000, 10000]:
    print(f"{length} tokens -> {attention_pair_count(length):,} pairs to compute")`} />

A 10× increase in sequence length produces a 100× increase in the
number of pairwise comparisons attention actually has to compute. An
arbitrarily long sequence would need an arbitrarily, impractically large
amount of computation.

**2. Memory.** To avoid recomputing work for every new token, a model
keeps each earlier token's Keys and Values in memory, in every layer.
That store,
[the KV cache this lesson covers shortly](/01-llm-foundations/06-context-windows-and-kv-cache/03-kv-cache/#what-actually-doesn-t-need-to-be-recomputed),
grows by one entry per token for as long as the request runs. For a large
model and a long context it can take many gigabytes of accelerator
memory, for a single request. Efficient attention implementations such
as FlashAttention cut attention's *own* working memory substantially,
but they don't change the quadratic compute above, and the KV cache
still grows with every token.

**3. Training length.** A model is trained on sequences up to some
length. Positions beyond that range are ones it has seen rarely or never
during training, so
[the position information it relies on](/01-llm-foundations/03-attention-and-transformer-architecture/03-positional-encoding/#how-most-current-models-do-it-rotary-position-embeddings-rope)
stops being familiar, and the quality of its output degrades even if the
hardware could keep going. A model's advertised window is the length it
was actually trained (or specifically extended) to handle well.

So the limit isn't a policy choice. It comes from how much compute,
memory and trained experience a model has for long sequences.

</Subsection>

<Subsection title="What happens when you exceed it" variant="a">

Exactly what happens past the limit depends on the specific system, but
falls into a few common patterns: an outright error, rejecting the
request entirely until it's shortened; silent truncation, where older
content (often from the very beginning) simply gets dropped to make
room; or a sliding window, keeping only the most recent portion of a
long conversation and discarding what came before it. A fourth pattern
is **context compression**: rather than dropping older content
outright, the system has the model *summarize* it, then replaces the
original turns with that shorter summary so the essentials stay in the
window. AI coding assistants such as Claude Code do exactly this — as a
long session approaches its context limit, the earlier conversation is
condensed into a summary and the work continues from that. It
preserves the gist far better than blind truncation, but it is lossy:
exact wording, small details, and anything the summary didn't think to
keep are gone from the model's view afterward. None of these are
universal — the important, portable fact is simply that a context
window is a hard ceiling, not a soft suggestion, and something concrete
happens once content exceeds it, whether or not that behavior is
visible or obvious from the outside.

</Subsection>
