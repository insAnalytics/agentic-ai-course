<Subsection title="The basic pricing mechanics" variant="a">

LLM APIs typically charge per token, usually with **different rates for
input and output tokens** — output tokens are generally priced higher,
since generation is the actual compute-intensive part of the process,
[one full pass per token, as established back in Lesson 4](/01-llm-foundations/04-how-llms-generate-text/02-autoregressive-generation/#why-this-matters-computationally).

</Subsection>

<Subsection title="Every cost driver from this module, combined into one calculation" variant="b">

<LiveDemo client:load code={`def estimate_request_cost(
    input_tokens: int,
    output_tokens: int,
    cached_tokens: int,
    input_price_per_1k: float,
    cached_input_price_per_1k: float,
    output_price_per_1k: float,
) -> float:
    fresh_input_tokens = input_tokens - cached_tokens
    fresh_input_cost = (fresh_input_tokens / 1000) * input_price_per_1k
    cached_cost = (cached_tokens / 1000) * cached_input_price_per_1k
    output_cost = (output_tokens / 1000) * output_price_per_1k
    return fresh_input_cost + cached_cost + output_cost

# a support bot: large, stable system prompt (mostly cached), short question
cost_standard = estimate_request_cost(
    input_tokens=2000, output_tokens=150, cached_tokens=1800,
    input_price_per_1k=0.003, cached_input_price_per_1k=0.0003, output_price_per_1k=0.015,
)

# the same request, but routed through a reasoning model
cost_reasoning = estimate_request_cost(
    input_tokens=2000, output_tokens=150 + 2000, cached_tokens=1800,
    input_price_per_1k=0.003, cached_input_price_per_1k=0.0003, output_price_per_1k=0.015,
)

print(f"standard: \${cost_standard:.4f}")
print(f"reasoning: \${cost_reasoning:.4f}")`} />

(Illustrative pricing figures — real rates vary by provider and model.)

This one calculation already combines two threads from across this
module:
[cache-friendly prompt structure from Lesson 6](/01-llm-foundations/06-context-windows-and-kv-cache/04-prompt-structure-and-cache-hits/#why-this-is-a-real-cost-and-latency-lever-not-just-a-style-choice)
— `1800` of the `2000` input tokens hit the cheaper cached rate, because
the stable system prompt sits first — and
[reasoning tokens from Lesson 8](/01-llm-foundations/08-scaling-laws-and-emergent-behavior/04-test-time-compute/#the-real-cost-made-concrete),
roughly `10×`-ing the cost when the same request routes through a
reasoning model. (Lesson 8's output-only demo showed roughly `14×`; here
the input side is a fixed, mostly-cached cost the reasoning tokens don't
touch, so the whole-request multiple comes out a little lower.)

Two more real drivers this exact same calculation would need to account
for in practice, both already covered earlier in this module:
**[language](/01-llm-foundations/01-tokenization/03-tokens-in-practice-and-cost/#why-language-itself-changes-the-cost)**
— the identical conversation conducted in a language poorly represented
in the tokenizer's training data would inflate both `input_tokens` and
`output_tokens` well beyond what the same meaning costs in English — and
**[non-text inputs](/01-llm-foundations/01-tokenization/04-non-text-inputs-as-tokens/)**
(and [how they're actually sent](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/04-sending-non-text-inputs/))
— an image attached to that support request adds real tokens to
`input_tokens`, often several hundred, before a single word of the actual
question is even considered.

</Subsection>

<Subsection title="The habit worth building" variant="a">

None of these four factors — language, caching, reasoning, non-text input
— acts alone in a real system; a genuinely cost-aware agent backend is
affected by some combination of all four on nearly every request. The
actual skill this lesson has been building toward isn't memorizing any one
of these facts individually — each was already taught where it belongs —
but developing the habit of checking all four together when actually
estimating what a real workload will cost, rather than reasoning about
pricing as if only one factor were ever in play at a time.

</Subsection>
