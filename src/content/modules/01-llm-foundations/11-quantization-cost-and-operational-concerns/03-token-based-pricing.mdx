<Subsection title="The basic pricing mechanics" variant="a">

LLM APIs typically charge per token, usually with **different rates for
input and output tokens** — output tokens are generally priced higher.
Input tokens go through every layer too, but they're processed all at
once, in parallel; output tokens are produced one at a time,
[each needing its own pass through the model, as established back in Lesson 4](/01-llm-foundations/04-how-llms-generate-text/02-autoregressive-generation/#why-this-matters-computationally).

</Subsection>

<Subsection title="Every cost driver from this module, combined into one calculation" variant="b">

<LiveDemo client:load code={`def estimate_request_cost(
    input_tokens: int,
    output_tokens: int,
    cached_tokens: int,
    input_price_per_1k: float,
    cached_input_price_per_1k: float,
    output_price_per_1k: float,
) -> float:
    fresh_input_tokens = input_tokens - cached_tokens
    fresh_input_cost = (fresh_input_tokens / 1000) * input_price_per_1k
    cached_cost = (cached_tokens / 1000) * cached_input_price_per_1k
    output_cost = (output_tokens / 1000) * output_price_per_1k
    return fresh_input_cost + cached_cost + output_cost

# a support bot: large, stable system prompt (mostly cached), short question
cost_standard = estimate_request_cost(
    input_tokens=2000, output_tokens=150, cached_tokens=1800,
    input_price_per_1k=0.003, cached_input_price_per_1k=0.0003, output_price_per_1k=0.015,
)

# the same request, but routed through a reasoning model
cost_reasoning = estimate_request_cost(
    input_tokens=2000, output_tokens=150 + 2000, cached_tokens=1800,
    input_price_per_1k=0.003, cached_input_price_per_1k=0.0003, output_price_per_1k=0.015,
)

print(f"standard: \${cost_standard:.4f}")
print(f"reasoning: \${cost_reasoning:.4f}")`} />

(Illustrative pricing figures — real rates vary by provider and model.)

This one calculation already combines two threads from across this
module:
[cache-friendly prompt structure from Lesson 6](/01-llm-foundations/06-context-windows-and-kv-cache/04-prompt-structure-and-cache-hits/#why-this-is-a-real-cost-and-latency-lever-not-just-a-style-choice)
— `1800` of the `2000` input tokens hit the cheaper cached rate, because
the stable system prompt sits first — and
[reasoning tokens from Lesson 8](/01-llm-foundations/08-scaling-laws-and-emergent-behavior/04-test-time-compute/#the-real-cost-made-concrete),
roughly `10×`-ing the cost when the same request routes through a
reasoning model. (Lesson 8's output-only demo showed roughly `14×`; here
the input side is a fixed, mostly-cached cost the reasoning tokens don't
touch, so the whole-request multiple comes out a little lower.)

Two more real drivers this exact same calculation would need to account
for in practice, both already covered earlier in this module:
**[language](/01-llm-foundations/01-tokenization/03-tokens-in-practice-and-cost/#why-language-itself-changes-the-cost)**
— the identical conversation conducted in a language poorly represented
in the tokenizer's training data would inflate both `input_tokens` and
`output_tokens` well beyond what the same meaning costs in English — and
**[non-text inputs](/01-llm-foundations/01-tokenization/04-non-text-inputs-as-tokens/)**
(and [how they're actually sent](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/04-sending-non-text-inputs/))
— an image attached to that support request adds real tokens to
`input_tokens`, often several hundred, before a single word of the actual
question is even considered.

</Subsection>

<Subsection title="An agent task is many requests, and each one resends the history" variant="a">

Everything above prices a *single* request. An agent task is many
requests: one per step of the loop. And because
[the API has no memory between calls](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/03-multi-turn-conversations/#the-api-itself-has-no-memory-between-calls),
every step resends the whole conversation so far: the system prompt,
every earlier tool call, every earlier tool result. Each step's input is
bigger than the last one's.

<LiveDemo client:load code={`def agent_task_cost(steps: int, cache: bool) -> float:
    # illustrative: a 2,000-token system prompt, and each step adds the model's
    # 150-token tool call plus a 500-token tool result to the history
    input_price, output_price = 0.003, 0.015            # per 1k tokens
    cache_write, cache_read = 1.25, 0.10                # multipliers on the input price
    history, already_cached, total = 2000, 0, 0.0
    for step in range(steps):
        if cache:
            new_tokens = history - already_cached      # only the part not cached yet pays the write price
            total += (already_cached * cache_read + new_tokens * cache_write) / 1000 * input_price
            already_cached = history
        else:
            total += history / 1000 * input_price      # the whole history, at full price, every step
        total += 150 / 1000 * output_price
        history += 150 + 500
    return total

for steps in [1, 5, 10, 20, 40]:
    plain, cached = agent_task_cost(steps, cache=False), agent_task_cost(steps, cache=True)
    print(f"{steps:>2} steps: \${plain:6.3f} without caching, \${cached:6.3f} with it")`} />

(Illustrative prices and multipliers. Cache pricing varies by provider.)

Twice as many steps costs much more than twice as much. The input sent
at step *n* includes every step before it, so the total input across a
task grows roughly with the **square** of the number of steps: 40 steps
here costs about 30 times what 5 steps does, not 8 times. That's the
most important cost fact for agents, and it's why a task that runs for
"just a few more steps" can cost far more than expected.

Caching helps a lot, because each step's history is the previous step's
history plus a little more: a perfect stable prefix. Two details make it
less than free:

- **Writing to the cache can cost more than a normal input token.** Some
  providers, Anthropic among them, charge a premium on the tokens that
  go *into* the cache, and a much lower rate for reading them back. The
  demo charges every new token the write price once, then the read price
  on every later step. That's why a single request costs slightly *more*
  with caching: the premium is paid and never earned back.
- **Caches are conditional.** Depending on the provider, caching may need
  you to mark where the cached prefix ends, may only apply above a
  minimum prompt length, and expires after a few minutes without use. A
  slow agent, or one waiting on a person, can find its cache gone.

Even with caching, the history still grows every step, and it still has
to fit in the context window. Keeping it short, by trimming, summarizing
or offloading what the agent no longer needs, is
Module 4's subject, on memory and context. For
work that doesn't need an answer right away, many providers also offer a
**batch API**: requests are processed within hours instead of seconds,
at roughly half the price.

</Subsection>

<Subsection title="The habit worth building" variant="b">

None of these four factors — language, caching, reasoning, non-text input
— acts alone in a real system; a genuinely cost-aware agent backend is
affected by some combination of all four on nearly every request, and
multiplied by the number of steps the agent takes. The
actual skill this lesson has been building toward isn't memorizing any one
of these facts individually — each was already taught where it belongs —
but developing the habit of checking all four together when actually
estimating what a real workload will cost, rather than reasoning about
pricing as if only one factor were ever in play at a time.

</Subsection>
