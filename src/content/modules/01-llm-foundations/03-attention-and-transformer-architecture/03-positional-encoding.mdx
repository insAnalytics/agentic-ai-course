<Subsection title="Attention has no inherent sense of order" variant="a">

[Attention, from the previous concept](/01-llm-foundations/03-attention-and-transformer-architecture/02-the-attention-mechanism/),
computes relevance between tokens by comparing each token's Query
against every other token's Key. Nothing about that comparison depends
on *where* either token sits in the sequence — only on the tokens' own
content. That's a real gap: word order carries enormous meaning in
language.

```
"The dog bit the man."
"The man bit the dog."
```

Both sentences contain the exact same set of tokens — `the`, `dog`,
`bit`, `the`, `man` — just in a different order, and mean something
completely different as a result. Attention, exactly as described in
the previous concept, has no built-in way to tell these two orderings
apart — comparing Query against Key gives the same relevance scores
either way, since neither depends on sequence position at all.

</Subsection>

<Subsection title="The original fix: adding a position vector to the input" variant="b">

The original transformer, and early GPT models including GPT-2, solved
this with **positional encoding**: each *position* in the sequence —
1st, 2nd, 3rd, and so on — gets its own distinct vector, added onto a
token's embedding once, before the first layer runs. The same token
appearing at two different positions ends up with two different
starting representations, purely because of where it sits. It's the
easiest version of the idea to picture, so it's worth seeing first:

<LiveDemo client:load code={`token_embedding = {"the": [0.10, 0.10]}   # the same vector every time "the" appears

# a simplified stand-in for real positional encoding -- one distinct
# vector per position (real positional encodings are computed with a
# formula, not hand-set like this, but the shape of the idea is the same)
positional_encoding = {
    1: [0.00, 0.00],
    5: [-0.03, 0.08],
}

def position_aware_representation(token: str, position: int) -> list:
    base = token_embedding[token]
    pos = positional_encoding[position]
    return [base[i] + pos[i] for i in range(len(base))]

print(position_aware_representation("the", 1))
print(position_aware_representation("the", 5))`} />

The exact same word, `"the"`, produces two genuinely different starting
vectors — `[0.1, 0.1]` at position `1`, `[0.07, 0.18]` at position `5`.
Once position is baked into each token's representation this way,
attention's Query/Key comparisons — computed *on top of* these
position-aware vectors — can reflect order, because order is now part of
what each token's representation encodes.

</Subsection>

<Subsection title="How most current models do it: rotary position embeddings (RoPE)" variant="a">

Most current LLMs, open and closed, use a different design called
**rotary position embeddings**, or **RoPE**. Instead of adding a vector
to the input once, RoPE works *inside attention*, at every layer. Right
before a token's Query and Key are compared, each one is **rotated** by
an angle that depends on the token's position: a token at position 10 is
rotated further than one at position 2.

Rotation has a useful consequence. When you rotate two vectors and then
take their dot product, only the *difference* between their angles
affects the result. So the Query·Key score ends up depending on how far
apart two tokens are (their **relative position**), not on where each one
sits in absolute terms. "The word three tokens back" scores the same way
at the start of a document as it does deep inside it.

Here's that property in two dimensions. Rotating a 2D vector `[x, y]` by
an angle uses `math.cos` and `math.sin` (angles are in radians, so a full
turn is about 6.28): the rotated vector is
`[x·cos − y·sin, x·sin + y·cos]`. The Query and Key *content* stays the
same in every line below; only their positions change:

<LiveDemo client:load code={`import math

def rotate(vector: list, angle: float) -> list:
    x, y = vector
    return [x * math.cos(angle) - y * math.sin(angle),
            x * math.sin(angle) + y * math.cos(angle)]

def dot(a: list, b: list) -> float:
    return a[0] * b[0] + a[1] * b[1]

query = [1.0, 0.5]   # the same Query content every time
key = [0.8, -0.2]    # the same Key content every time
step = 0.3           # radians of rotation per position

for query_pos, key_pos in [(2, 5), (10, 13), (40, 43), (2, 3), (2, 9)]:
    q = rotate(query, query_pos * step)
    k = rotate(key, key_pos * step)
    print(f"query at {query_pos}, key at {key_pos} (gap {key_pos - query_pos}): score {dot(q, k):.4f}")`} />

Positions 2 and 5, 10 and 13, 40 and 43: three very different places in
the sequence, one identical score, because the gap is 3 each time.
Change the gap and the score changes. A real model does this across
every pair of dimensions in its Query and Key vectors, with each pair
rotating at its own speed, but the principle is exactly this one.

</Subsection>

<Subsection title="Where this sits in the architecture" variant="b">

Either way, attention's core comparison is order-agnostic on its own.
Position has to be supplied from somewhere, and the two designs put it
in different places:

- **Additive positional encoding** (the original transformer, GPT-2):
  a position vector is added once, right after the token embedding
  lookup, before the first layer. Every later layer works on vectors
  that already carry position.
- **Rotary position embeddings** (most current models): nothing is added
  at the input. Instead, inside every attention layer, each Query and Key
  is rotated according to its position just before they're compared.

So "is position part of attention?" depends on the model. In the
original design it isn't; it's a preparation step. In RoPE models it is,
applied fresh in every layer. What both have in common is that neither
Query nor Key *content* alone carries order. Without one of these
mechanisms, a transformer couldn't tell "the dog bit the man" from "the
man bit the dog".

</Subsection>
