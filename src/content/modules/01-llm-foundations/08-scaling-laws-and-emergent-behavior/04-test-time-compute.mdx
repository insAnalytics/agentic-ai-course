<Subsection title="A different axis of scaling: at inference time, not training time" variant="a">

Every concept in this lesson so far has been about **training-time**
scaling — a bigger model, more data, more compute, all spent before the
model is ever actually used. **Test-time compute** is a genuinely
different axis: improving performance not by training a bigger model at
all, but by letting a model spend *more compute at the moment of
actually answering a specific question* — generating more tokens of
reasoning before producing its final answer.

</Subsection>

<Subsection title="Where this behavior actually comes from" variant="b">

This is the direct practical consequence of
[RL for reasoning, from Lesson 7](/01-llm-foundations/07-the-training-pipeline/04-rl-for-reasoning/)
— the training stage that specifically rewards generating extended
intermediate reasoning leading to correct final answers. A reasoning
model, faced with a genuinely difficult problem, will generate
substantially more reasoning tokens before answering — and
[every one of those tokens is a real, full generation step](/01-llm-foundations/04-how-llms-generate-text/02-autoregressive-generation/#the-model-never-generates-more-than-one-token-at-once),
the same cost as any other token.

</Subsection>

<Subsection title="The real cost, made concrete" variant="a">

<LiveDemo client:load code={`def estimate_cost(num_tokens: int, cost_per_1k_tokens: float) -> float:
    return (num_tokens / 1000) * cost_per_1k_tokens

standard_response_tokens = 150            # a direct answer, no extended reasoning
reasoning_response_tokens = 150 + 2000    # the same final answer, plus ~2000 reasoning tokens

cost_per_1k = 0.015   # illustrative price per 1,000 tokens

print(f"standard: \${estimate_cost(standard_response_tokens, cost_per_1k):.4f}")
print(f"reasoning: \${estimate_cost(reasoning_response_tokens, cost_per_1k):.4f}")`} />

*(illustrative figures — real pricing and reasoning-token counts vary
by model and provider)*

The same final answer, roughly **14× more expensive**, purely because of
the added reasoning tokens — and those tokens are typically billed the
same as any other output token, as
[this module's token-pricing concept](/01-llm-foundations/11-quantization-cost-and-operational-concerns/03-token-based-pricing/#the-basic-pricing-mechanics)
covers. This is real, measurable cost, not a hypothetical
concern.

</Subsection>

<Subsection title="The practical tradeoffs, as a real design decision" variant="b">

- **Slower** — more tokens generated means more generation time,
  [directly following from Lesson 4's per-token cost](/01-llm-foundations/04-how-llms-generate-text/02-autoregressive-generation/#why-this-matters-computationally).
- **Costs more** — thinking tokens are billed,
  [as shown above](/01-llm-foundations/08-scaling-laws-and-emergent-behavior/04-test-time-compute/#the-real-cost-made-concrete).
- **Helps most on genuinely multi-step problems** — math, code, planning
  tasks where working through intermediate steps actually improves the
  correctness of the final answer.
- **Often unnecessary for simple tasks** — a straightforward factual
  lookup or a basic format transformation rarely benefits meaningfully
  from extra reasoning tokens; the added cost and latency there is often
  simply wasted.

This is a genuine, practical design decision when building an agent, not
an academic curiosity: routing every request through a reasoning model
regardless of difficulty spends real money and time for often negligible
benefit, while routing genuinely hard, multi-step tasks through a
standard model can mean settling for a worse answer than a bit more
compute would have bought. Matching the tool to the task's actual
difficulty is the real skill this concept is building toward.

That choice doesn't always mean picking between two models. Many current
models are hybrid: the same model can answer directly or think first,
controlled per request by a thinking-token budget or an effort setting
(low, medium, high). So the dial is often a request parameter rather
than a model choice. The decision itself is the same either way.

</Subsection>
