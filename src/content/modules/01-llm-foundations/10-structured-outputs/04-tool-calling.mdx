<Subsection title="The model doesn't call anything — it produces structured data" variant="a">

**Tool calling** is worth understanding as exactly one specific
application of
[the same constrained-decoding mechanism from Concept 2](/01-llm-foundations/10-structured-outputs/02-constrained-decoding/),
not some separate, new capability where the model somehow executes code.
A model never literally "calls a function" — it produces structured
output, guaranteed to match a schema (typically a tool name plus a set of
arguments), using the exact same token-masking mechanism as any other
structured output. Your own code is what actually reads that structured
output and decides whether and how to execute anything real.

</Subsection>

<Subsection title="The full shape, concretely" variant="b">

*The Pydantic parsing and the function call below genuinely run live; the
model's tool-call response itself is illustrative, not fetched live.*

<LiveDemo client:load code={`from pydantic import BaseModel

class GetWeatherArguments(BaseModel):
    location: str

def get_weather(location: str) -> str:
    # a real, callable Python function -- what your own code actually executes
    return f"It's sunny in {location}."

# an illustrative model response, requesting this specific tool call
tool_call_response = {
    "name": "get_weather",
    "arguments": {"location": "Paris"},
}

# your code parses the structured arguments, then decides to actually run it
args = GetWeatherArguments.model_validate(tool_call_response["arguments"])
result = get_weather(args.location)
print(result)`} />

`GetWeatherArguments` —
[an ordinary Pydantic model, exactly like `AgentConfig` from the previous concept](/01-llm-foundations/10-structured-outputs/03-from-a-pydantic-model-to-a-schema/)
— defines what a valid `get_weather` call's arguments look like; that
schema is what gets sent to the API, as part of the tool's definition
alongside a name and a description, so the model's `"arguments"` output
can be held to it. `get_weather` itself is a completely ordinary Python
function, with no special relationship to the model at all — the model
never touches it, never runs it, and has no way to execute anything on
its own.

Two details differ from real APIs. The response shape above is
simplified: Anthropic's API returns a `tool_use` content block with an
`id`, the tool's `name`, and its arguments under `input` (already a
dictionary), while OpenAI-style APIs return the arguments as a JSON
*string* that you parse yourself. And the schema guarantee is typically
opt-in — Anthropic, for instance, offers `strict: true` on a tool
definition to enforce it — so without that setting, arguments are
usually well-formed but not guaranteed, which is exactly why validating
them with `model_validate` before running anything, as the demo does,
stays worthwhile.

</Subsection>

<Subsection title="Why this separation matters" variant="a">

This is worth being explicit about as a real design point, not just a
technical detail: the model's job is *deciding which tool to use and
what arguments to pass*, expressed reliably as structured data thanks
to constrained decoding. Actually *executing* that tool call is
entirely your code's decision and responsibility — nothing forces your
code to actually run whatever the model requested; a well-built system
can validate, log, rate-limit, or outright refuse a requested tool call
before ever executing anything real, exactly because the model's output
is just data your code chooses what to do with, not a command that
executes itself.

</Subsection>
