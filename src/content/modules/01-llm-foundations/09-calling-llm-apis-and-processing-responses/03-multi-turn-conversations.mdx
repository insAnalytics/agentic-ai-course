<Subsection title="The API itself has no memory between calls" variant="a">

An LLM API call is completely stateless — nothing about a previous
request is remembered anywhere on the server side. For a multi-turn
conversation to work at all, the *client* has to resend the entire
conversation history — every prior user message and every prior
assistant response — with **every single new request**, not just
whatever's newly being said. (That's true of the Messages and Chat
Completions-style APIs this course uses. Some APIs, such as OpenAI's
Responses API with a previous-response ID, can keep the conversation on
the server for you, but the model itself is still stateless: the
provider is just resending the history on your behalf.)

<LiveDemo client:load code={`conversation = [
    {"role": "system", "content": "You are a helpful assistant."},
]

def send_turn(conversation: list, user_message: str, assistant_response: str) -> list:
    conversation = conversation + [{"role": "user", "content": user_message}]
    print(f"this request sends {len(conversation)} messages")
    # ...the API call would happen here, returning assistant_response...
    return conversation + [{"role": "assistant", "content": assistant_response}]

conversation = send_turn(conversation, "What is the capital of France?", "The capital of France is Paris.")
conversation = send_turn(conversation, "What about Germany?", "The capital of Germany is Berlin.")
conversation = send_turn(conversation, "And Italy?", "The capital of Italy is Rome.")`} />

By turn 3, the client's request actually sends all `6` messages — the
original system message, plus both prior exchanges (a user message and
an assistant reply each), plus the new user message — even though the
user only typed two new words, `"And Italy?"`. Every earlier message
travels along again, every single time.

</Subsection>

<Subsection title="This is REST's statelessness, showing up concretely" variant="b">

This is a direct, satisfying instance of
[statelessness, one of REST's guiding principles from Module 0's FastAPI lesson](/00-python-essentials/09-building-apis-with-fastapi/01-rest-api-fundamentals/#rest-s-guiding-principles):
every request carries everything the server needs to process it, with
the server never remembering anything about a client between one call
and the next. That principle wasn't just an abstract REST design rule —
it's the literal, practical reason a chat application has to manage and
resend its own growing conversation history on every turn.

</Subsection>

<Subsection title="The real, compounding cost consequence" variant="a">

Since every message in the history counts as *input tokens* on every
single request,
[not free just because it was already sent before](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/02-the-response-shape/#usage-tokens-finally-readable-after-the-fact),
a long-running conversation's cost grows with every turn — not linearly
with just the new content, but with the entire accumulated history,
resent in full each time. In practice the growth is gentler than full
price per turn: the resent history is exactly the stable prefix that
[prompt caching, from Lesson 6](/01-llm-foundations/06-context-windows-and-kv-cache/04-prompt-structure-and-cache-hits/#the-cache-benefit-extends-across-separate-requests-not-just-within-one),
bills at a discounted rate after the first time. It still counts, though,
every turn. This is also exactly why
[Lesson 6's shared context-window budget](/01-llm-foundations/06-context-windows-and-kv-cache/01-what-a-context-window-is/#what-happens-when-you-exceed-it)
eventually becomes a real constraint in any sufficiently long
conversation: the history itself keeps growing, consuming more and more
of that fixed, shared budget on every single turn, until eventually
something has to give — truncation, summarization, or hitting the limit
outright.

</Subsection>
