<Subsection title='Where the "thinking" from Lesson 8 actually shows up' variant="a">

*Same caveat as this lesson's earlier concepts: the response shown is
illustrative, not fetched from a live call.*

[Lesson 8 established that reasoning models generate substantial extra reasoning tokens before their final answer, and that those tokens are billed](/01-llm-foundations/08-scaling-laws-and-emergent-behavior/04-test-time-compute/).
This concept covers the actual API mechanics: a reasoning-capable
model's response typically includes a **separate content block** for
that reasoning — distinct from the final answer text — rather than
mixing the two together as one undifferentiated block:

```json
{
  "content": [
    {"type": "thinking", "thinking": "The user is asking about the capital of France. This is a well-established, unambiguous fact..."},
    {"type": "text", "text": "The capital of France is Paris."}
  ],
  "stop_reason": "end_turn",
  "usage": {
    "input_tokens": 24,
    "output_tokens": 187
  }
}
```

*(illustrative — not fetched from a live call)*

<LiveDemo client:load code={`response_data = {
    "content": [
        {"type": "thinking", "thinking": "The user is asking about the capital of France. This is well-established..."},
        {"type": "text", "text": "The capital of France is Paris."},
    ],
    "usage": {"input_tokens": 24, "output_tokens": 187},
}

for block in response_data["content"]:
    if block["type"] == "thinking":
        print(f"[reasoning]: {block['thinking'][:50]}...")
    elif block["type"] == "text":
        print(f"[final answer]: {block['text']}")

print(f"total output tokens billed: {response_data['usage']['output_tokens']}")`} />

Notice `output_tokens: 187` here, compared to `output_tokens: 9` for
[the exact same simple question, answered without reasoning, back in the response-shape concept](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/02-the-response-shape/)
— a concrete illustration of
[Lesson 8's point](/01-llm-foundations/08-scaling-laws-and-emergent-behavior/04-test-time-compute/#the-real-cost-made-concrete)
that a reasoning model can spend meaningfully more tokens (and cost) even
on something that plainly didn't need extended reasoning at all.

</Subsection>

<Subsection title="This varies by provider" variant="b">

Worth noting: not every provider necessarily exposes the raw reasoning
content in the same way, or at all — some keep the actual reasoning
text internal, showing only a summary or nothing beyond the final
answer, even though the reasoning tokens were still generated and still
billed regardless of whether you can actually read them. Claude's API,
for example, returns the model's raw reasoning to no one: depending on
the model and a request setting, a `thinking` block comes back with a
readable summary or with its text left empty, and the reasoning is
billed as output tokens either way. The specific structure a real API
returns is worth checking against that provider's own documentation;
the concept worth carrying forward from this lesson is simply that
reasoning content, when present, generally sits separate from the final
answer, and always contributes to the token count you're actually
billed for.

</Subsection>

<Subsection title="Sending thinking back: leave it exactly as it came" variant="a">

A conversation continues by resending the history,
[as the multi-turn concept showed](/01-llm-foundations/09-calling-llm-apis-and-processing-responses/03-multi-turn-conversations/#the-api-itself-has-no-memory-between-calls).
With a reasoning model, the assistant turns in that history contain
thinking blocks too, and they come with a rule that's easy to break by
accident: **send them back exactly as you received them.**

On Claude's API a thinking block carries a `signature` field, an
encrypted value the API uses to check that the block is the model's own
and hasn't been altered. It matters most in the middle of a tool call:
when the model thinks, then asks for a tool, the thinking block must go
back unchanged in that assistant turn alongside the tool result, so the
model can pick up its reasoning where it left off. Deleting it,
shortening it, or rebuilding the turn from just the text drops or
invalidates that reasoning, and some models reject the request outright.
Editing *earlier* turns of the history can invalidate the thinking that
followed them, too.

The practical habit is simple: append the model's response content to
the history whole, every block, and don't tidy it up. How much of an old
thinking block the model actually reads on later turns is the API's
business, and it varies by model; your code's job is only to not tamper
with it. The agent loops in Module 2 follow exactly this habit.

</Subsection>
